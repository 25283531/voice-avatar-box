## 二、屏幕 ⚠️ 与调研结论冲突

```
Physical size: 800x480
Physical density: 240
mCurrentRotation=0
```

**是 800×480 横屏，不是调研资料说的 480×800 竖屏。**

触摸上报范围也印证：`ABS_MT_POSITION_X` max 800、`ABS_MT_POSITION_Y` max 480。

截图（`device-backup/screen-now.png`）确认：界面横向铺满，**四周没有物理黑边/非显示区**。

### 对「两侧各留 5mm 色带」的影响

用户要的两侧 5mm 色带**只能画在屏幕上**，不是利用黑边：

- 5mm @ 240dpi = 5 / 25.4 × 240 ≈ **47px**
- 左右各 47px 竖向色带，中间内容区 = 800 − 94 = **706px**
- 高度 = 480px（满高）

> ✅ 代码已按横屏更正（2026-11-05）：Manifest 锁 `landscape`、
> `LedBandView` 用 `COMPLEX_UNIT_MM` 按运行时 density 折算 5mm（不再写死 24/46px）。
> ⚠️ **`MainScreen` 的 dp 布局仍待装机后做截图/点按复核** —— 尺寸算对了不等于
> 实机排版对了，尤其触摸坐标翻转这一条还没在 App 内验过。

`screen_off_timeout = 2147483647`（永不休眠），`screen_brightness = 102`。

## 三、按键 ⚠️ 核心风险已解决

### 输入设备

| event | 设备名 | 支持按键 |
| --- | --- | --- |
| event0 | `mtk-kpd` | `KEY_VOLUMEDOWN`、`KEY_VOLUMEUP` |
| event1 | `mtk-pmic-keys` | `KEY_VOLUMEDOWN`、`KEY_POWER` |
| event2/3 | `fts_ts` / `tlsc6x` | `KEY_POWER`（触摸屏控制器） |
| event4 | `mtk-tpd` | 多点触摸（X 0–800, Y 0–480） |

### 实测：中间键确实是 `KEY_POWER`

`getevent` 抓到原始扫描码 `KEY_POWER`，同时 logcat 出现：

```
PowerManagerService: Going to sleep due to power button (uid 1000)...
```

**这就是之前担心的坑**：中间键上报 POWER，系统直接熄屏/亮屏。
如果不处理，老人长按"服药确认键"会弹出关机菜单。

### 解法：改 keylayout 重映射（已验证成功）

`mtk-pmic-keys` 原本没有专属 kl 文件，走 `Generic.kl` 的 `key 116 POWER`。
新建 `/system/usr/keylayout/mtk-pmic-keys.kl`：

```
key 114   VOLUME_DOWN
key 116   F1
```

重启后 `dumpsys input` 确认加载：

```
2: mtk-pmic-keys
   KeyLayoutFile: /system/usr/keylayout/mtk-pmic-keys.kl
```

**实测验证**：连续按 5 次中间键，`getevent` 每次都有 `KEY_POWER DOWN/UP`，
但 logcat **零** `Going to sleep`，`mWakefulness=Awake`、`Display Power: state=ON`。

⇒ 内核照常上报 116，Android 层映射成 `F1`，系统不认识 F1，什么也不做。
**中间键从此可安全用作服药确认键。**

### 副作用与取舍

- 中间键的**屏幕开关功能永久消失**。这是用户明确要求的（中间键改确认键），
  但意味着屏幕不会自己熄。
- 需要 App 自己做"无人时降亮度"（`window.attributes.screenBrightness`），
  而不是依赖熄屏。
- 音量键不受影响：`mtk-kpd.kl` 里 `key 115 VOLUME_UP` / `key 114 VOLUME_DOWN` 保持原样。

### 对代码的影响

✅ 已按本节结论落地：`TopKeys.CONFIRM_KEY_CODES` 只认 **`KEYCODE_F1`**（单一值）：

```kotlin
val CONFIRM_KEY_CODES: Set<Int> = setOf(KeyEvent.KEYCODE_F1)
```

> 保留 POWER 会造成误判：万一有别的路径（触摸屏 event2/3）上报 POWER，
> 我们的 App 会把它当确认键，而系统同时会熄屏。

## 四、麦克风 ⚠️ 最大的隐藏障碍

### 现象

开机后麦克风**一直被占用**，`dumpsys media.audio_flinger`：

```
Input thread AudioIn_1E, type 3 (RECORD)
  Standby: no              ← 一直在录
  Sample rate: 16000 Hz    ← 唤醒词标准采样率
  Audio source: 6 (voice recognition)
  1 Tracks of which 1 are active
    Active Client = pid 373, session 9
```

### 占用者不是桌面，是独立系统服务

- `pid 373` = **`/system/bin/MiVpmService`**（小米语音处理模块，VPM = Voice Processing Module）
- init 服务名 **`mivpm`**，定义在 `/vendor/etc/init/hw/init.project.rc`
- `getprop init.svc.mivpm` → `running`

> 我先 `am force-stop com.xiaomi.micolauncher` 试过：进程死了（`ps` 计数 0），
> **麦克风仍然 `Standby: no`** —— 说明禁桌面并不能释放麦克风。

### 解法：停 `mivpm`（已验证成功）

```
stop mivpm
```

结果：
- `init.svc.mivpm` → `stopped`
- `MiVpmService` 进程数 → 0
- **`dumpsys media.audio_flinger | grep 'Input thread'` 返回空** —— 输入线程消失

### 录音实测

`mivpm` 停掉后用设备自带 `tinycap` 录 3 秒：

```
tinycap /data/local/tmp/cap.wav -D 0 -d 1 -c 1 -r 16000 -b 16 -T 3
Captured 49152 frames
```

音频分析（`device-backup/cap-test.wav`）：

| 指标 | 值 |
| --- | --- |
| 格式 | 1ch / 16bit / 16000Hz / 3.07s |
| 峰值 | 31981 / 32767（**97.6%**） |
| RMS | 2269.7 |
| 非零采样 | 48824 / 49152（**99.3%**） |
| 分段 RMS | 7862, 72, 15, 7, 12, 17, 17, 17, 15, 15, 15, 13 |

⇒ **硬件通路完好，能录到真实声音**（不是全 0、也不是固定底噪）。

### 对方案的硬约束

**必须禁掉 `mivpm`，我们的 App 才能拿到麦克风。** 这不是可选项。

永久禁用的做法（三选一，推荐前两个组合）：

1. 改 `/vendor/etc/init/hw/init.project.rc`，把 `service mivpm` 段落注释掉
   （`/vendor` 是 `ro` 挂载，需先 remount）
2. 重命名二进制：`mv /system/bin/MiVpmService /system/bin/MiVpmService.disabled`
3. 临时测试用 `stop mivpm`（重启后失效）

> 禁掉 mivpm = 小爱彻底听不到唤醒词。这与用户「只能进入我们的系统，
> 不能再进入原来的小爱音箱」的要求一致，但**米家语音控制也会一起失效**。

## 九、语音链路断链诊断（2026-11-05）

> 这一节记录的是**实机现象 → 根因 → 修复**的完整链条。
> 现象：按顶部中间键，屏幕表情和侧边收听色带**都切换成功**，
> 但**没有任何答复**（不识别、不出声）。

### 9.1 现象与证据

UI 切换成功说明按键 → `beginListening()` 这条路是通的，
所以故障在**上行音频**和**服务端应答**这两段。

生产服务端日志（设备 `8c53c3a7cf93`，2026-11-05）：

```
10:21:21,280 listen start（mode=auto）
10:21:21,479 进入待机：连续 120s 没有有效内容     ← 199ms 后
10:21:26,156 listen stop                          ← 没有 ASR、没有 TTS

10:22:26,204 listen start（mode=auto）
10:22:29,816 listen stop
10:22:29,822 ASR 失败：腾讯云 ASR 收到的音频为空 —— 上层可能没收到声音
10:22:30,071 ASR 返回空，音频指纹：rms=0.0000 peak=0.000 时长=0.0s 语音=0ms

10:24:54,552 listen start（mode=auto）
10:24:54,552 退下吧冷却中（还剩 149s），忽略 listen start
```

同一台服务器上，另一台设备（ESP32，`e80690a6c20c`）同时段工作正常：

```
10:28:54,636 listen start（mode=manual）
10:28:59,043 ASR 前裁掉头尾静音 37 帧（2220ms）：52 帧 → 15 帧
```

⇒ **服务端没问题，LX04 客户端这一侧断链。**

### 9.2 两个独立断点

日志把两个故障分得很清楚，它们**互相独立**，必须分别修：

| # | 断点 | 证据 | 根因 |
|---|---|---|---|
| ① | 客户端上行一帧都没发出去 | `rms=0.0000 peak=0.000 时长=0.0s` | Concentus 编码器被**两个线程并发踩**，断言触发后整轮静音 |
| ② | 服务端把这一轮掐掉 | `listen start` 后 199ms「进入待机」 | 客户端**从不发 detect**，服务端的空闲看门狗与 180 秒冷却把这一轮丢弃 |

#### 断点①：编码器并发踩踏

设备日志里的 `编码失败: null` 打堆栈后是
`Inlines.OpusAssert` 抛的 `AssertionError`（message 为 null，所以只打
message 只会得到一行没用的"null"），位置：

```
at org.concentus.Inlines.OpusAssert(Inlines.java:40)
at org.concentus.Resampler.silk_resampler(Resampler.java:196)
```

Concentus **不是线程安全**的：编码器内部有可变状态（SILK 的自适应分析
状态、重采样器的历史缓冲）。两个线程同时 `encode()`，内部状态被写乱，
下一帧就在断言里炸 ⇒ `encode()` 返回 null ⇒ 上层 `return@AudioCapture`
⇒ **整轮一帧都发不出去**。

并发窗口在实机上是真实存在的：
`AudioCapture.stop()` 原本先 `join(300)` 再 `record.stop()` ——
而采集线程正阻塞在 `rec.read()` 里，**不会**因为 `running=false` 立刻醒
（标志只在 read 返回后才被检查）⇒ join 常常超时 ⇒ 旧采集线程还活着；
下一次按键又起一个新线程 ⇒ 两个线程踩同一个编码器。

**已实测验证**（纯 Java，同一份 Concentus 源码）：

| 场景 | 4 线程 × 50 轮 | 结论 |
|---|---|---|
| 无锁 | **200 / 200 次失败** | 复现实机故障 |
| 加锁 | **0 次失败** | 修复有效 |

这条对照同时证明：并发回归单测**不是假绿**（去掉锁它必红）。

> 顺带排除的可能：真实采集的 WAV（`cap-test.wav`）与 13 组极端输入
> （直流、方波、满量程、500 帧连编）在**单线程**下全部 51/51 通过，
> 8/12/16/24/48k 各采样率的构造也都正常。
> ⇒ **不是输入内容的问题，也不是 32 位 vs 64 位的问题。**

#### 断点②：服务端待机看门狗 + 冷却

服务端 `_on_listen` 的两个分支是这样配合的：

- `detect` → 清 `_dismissed_until`（解除 180 秒待机冷却）
  **并刷新 `_last_active_at`**（会话空闲锚点）
- `start` → 先查 `_dismissed_until`，**还在冷却里就直接 return**
  （这一轮 listen 被整个丢掉）

而 `_last_active_at` 只有两个刷新点：**有效识别**和 **detect**。

本客户端此前只发 `listen start`、**从不发 detect**（`VoiceClient.listenDetect`
定义了但没人调用，且表达不了 `greet:false`）。于是：

1. 会话空闲超过 120 秒后，`listen start` 刚到，静音看门狗在 **0.2 秒内**
   就判"连续 120s 没有有效内容"→ 进待机 → `state` 变成 `idle`；
2. 随后的 `listen stop` 走 `_finalize()`，那里第一句就是
   `if self.state != "listening": return` ⇒ **不做 ASR、不出 TTS**；
3. 待机还会拉起 180 秒冷却，期间连 `listen start` 都被忽略
   （日志：「退下吧冷却中（还剩 149s），忽略 listen start」）。

固件那边 2026-11-03 就加了同一处理（`application.cc:1007-1013`），
判据是 **Idle → Listening** 这一次跃迁。本客户端没有"自动回 listening"
这条路（只有按键/调试命令会调 `beginListening`），所以每次
`beginListening` 都对应"有人明确让设备开始听"，发 detect 是正确的。

### 9.3 已落地的修复

| 位置 | 改动 | 对应断点 |
|---|---|---|
| `MainActivity.beginListening` | **先发 `detect`（`greet:false`）再发 `listen start`** | ② |
| `VoiceClient.listenDetect` | 支持 `greet` 开关，用 `JSONObject` 拼装 | ② |
| `OpusCodec.init` | 编码器与解码器**分别**构造（解码失败不再连带废掉编码器） | ① |
| `OpusCodec.encode` | 失败后**重建编码器并重试一帧**（断言只坏一次状态） | ① |
| `OpusCodec.decode` | 补上同步锁（解码器同样非线程安全） | ① |
| `AudioCapture.stop` | **先 `record.stop()` 再 `join`** ⇒ 采集线程确定退出 | ① |

#### ⚠️ 2026-11-05 的教训：门禁绿 ≠ 编译得过

修这个 bug 时连续三次推送被 CI 的 `compileReleaseKotlin` 打回：

| CI run | 错误 | 静态门禁 |
|---|---|---|
| 41972423369 | `AudioCapture.kt:248 Unresolved reference: !`（`Thread.join` 返回 **void**） | 全绿 |
| 41972940902 | `OpusCodec.kt:233 A 'return' expression required in a function with a block body` | 全绿 |
| 41973478969 | 多一个右花括号 ⇒ companion object 被挤出类体 ⇒ `TAG`/`encoder` 全未解析 | 全绿 |

三次都是**纯 Kotlin 语义错误**。前两次我用"括号总数配平 + 关键字存在"这类静态检查，
**一次都没报红** —— 而第三次那个多余的 `}`，括号总数是**配平的**，
所以"数括号"这种检查在原理上就抓不住它。

⇒ 结论写在这里，别再犯：

> **静态门禁绿，只说明"形状对"，不说明"编译得过"。**
> 任何"改了 Kotlin 却没跑编译器"的验证都是不完整的。

因此本机补上了 `tools/kcompile.py`：用 Maven 上的 kotlin-compiler 1.9.24
（与项目一致）+ `tools/androidstub/` 下 48 个最小 Android stub 做**类型检查**，
**不需要 Android SDK**，30 秒出结果。已验证它能抓住上表三个错误。
CI 上它跑在 gradle 之前 —— 快速失败，比等 gradle 快得多。

（它**不能**替代 gradle：不打 APK、不做资源合并、不做 lint。所以两个都跑。）

#### stub 本身的坑（记下来免得重踩）

写最小 Android stub 时踩过的：

- Kotlin 的**属性语法要求 getter/setter 成对存在**：`setColor` 没有 `getColor`，
  写 `paint.color = x` 就是编译错误 —— 而 Android 真身是有 `getColor` 的。
- `BatteryManager.EXTRA_LEVEL` 在真 Android 里是 **String**，不是 Int。
- `View.onVisibilityChanged` 新版是 **2 参数**（`View, Int`），旧版 3 参数。
- `Thread.join(long)` 返回 **void** —— 这条直接造成了 CI run 41972423369。

stub 写错会造成**假绿**（stub 的错把真实代码的错盖住），
所以 stub 必须**跟着真实 Android 的签名写**，不能凭印象。
本机的教训：stub 里 `TextView.setTextSize` 少了 `(unit, size)` 重载，
结果真实代码的错被这条假绿盖住，检查看起来"通过"。
