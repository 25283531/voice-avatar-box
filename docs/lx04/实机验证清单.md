## 2. ★ 三个顶部按键的真实 KeyCode（最关键的一条）

**不能猜。** 猜错的两种后果：

- 猜成 `KEYCODE_HOME` → 中间键变成"回桌面"，我们的默认桌面被自己触发，逻辑打架
- 猜成 `KEYCODE_POWER` → **长按 1 秒弹关机菜单**，老人按服药键把音箱关了

### 抓法 A：静态查键位表

```bash
adb shell getevent -lp
```

输出里找 `mt6392keys` 或类似的 `key` 设备，看它的 `keycodes = [...]`。
MTK 常见在 `/system/usr/keylayout/mtk.kl`：

```bash
adb shell cat /system/usr/keylayout/mtk.kl
adb shell cat /system/usr/keylayout/gpio_keys.kl
```

### 抓法 B：动态实测（更可靠）

```bash
adb shell getevent -lt
```

然后依次按：**音量+ → 音量- → 中间键**，记录每次的 `keycode` 与 `value`。

### 结果填入

✅ 已实测并落地（内核 `KEY_POWER` 116 ⇒ keylayout 重映射为 F1）：

```kotlin
// lx04/app/src/main/java/com/elder/lx04/input/TopKeys.kt
val CONFIRM_KEY_CODES: Set<Int> = setOf(
    KeyEvent.KEYCODE_F1    // 只认 F1；放 POWER 会熄屏 + 弹关机菜单
)
```

配套的系统侧改动：`/system/usr/keylayout/mtk-pmic-keys.kl` 写入
`key 114 VOLUME_DOWN` / `key 116 F1`。**光改 App 没用** —— POWER 在
`interceptKeyBeforeQueueing` 阶段就被系统吃掉，应用层拦不住。

> 音量± 预期是 24 / 25（`KEYCODE_VOLUME_UP` / `KEYCODE_VOLUME_DOWN`），
> 但也要实测确认 —— 有些 ROM 会把音量键上报成别的。

## 4. ★ 麦克风是否被小爱占用（决定自建唤醒能否成立）

```bash
adb shell dumpsys media.audio_flinger | grep -iA3 -E "Client|Active"
```

- **看到小爱进程常驻在 Client 列表** → 原厂固件下我们抢不到麦，
  必须先 `pm disable` 它的语音包，或走「精简 system」路线（小爱物理消失）
- **Client 列表干净** → 可以直接共存，我们的唤醒可期

### 验证 AudioRecord 能拿到数据

装上我们的 App 后：

```bash
adb shell dumpsys media.audio_flinger | grep -A5 "com.elder.lx04"
```

能看到自己的 Client 且状态正常 ⇒ 采集通路 OK。

## 5. 触摸坐标方向（SWAP_XY / FLIP_Y）

TWRP 的 `BoardConfig.mk` 里有：

```
RECOVERY_TOUCHSCREEN_SWAP_XY := true
RECOVERY_TOUCHSCREEN_FLIP_Y  := true
```

**说明原厂触摸坐标是翻转过的。** 我们的 UI 是自绘的，必须确认：

```bash
adb shell dumpsys input | grep -iE "SurfaceOrientation|viewport"
```

实测方法：装一个显示「触摸点圆点」的测试 App，看点击位置与实际手指位置是否对得上。

> ⚠️ 实机更正：屏幕是 **800×480 横屏**，触摸上报 `ABS_MT_POSITION_X` max 800、
> Y max 480，与显示方向一致。但**App 内的实际点按位置还没做实机复核** ——
> 这一条不确认，自绘 UI 仍可能整体错位，装机后必须补测。
