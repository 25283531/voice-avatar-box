# 米家（智能家居）功能能不能保留？

> 结论：**能保留，但方式和你想的可能不一样。**
> 「保留米家」和「我们的系统完全接管设备」在原厂固件上**互斥** ——
> 因为"小爱 → 控制米家设备"这条链路的**设备端部分就是小爱语音服务本身**。

---

## 1. 先拆清楚：米家能力依赖什么

| 环节 | 在哪 | 精简 system 后还在吗 |
| --- | --- | --- |
| 唤醒词引擎 | `vendor/etc/voicecommand/`、`vendor/etc/hrsc/*wakeup_xiaoai*` | ✅ 在 **vendor** 里，不受影响 |
| ASR + NLU + 技能调度 | 原厂 `/system` 里的原厂签名应用 | ❌ 会没 |
| IoT / MiOT 客户端 | 小米云 + 设备端 IoT agent | ⚠️ 云端仍在，设备端会没 |
| **语义解析** | **云端**（"语义的识别与解析是由小爱同学完成的"） | ✅ 不在设备上 |
| 账号 | 小爱 = 米家 = 同一个小米账号 | ⚠️ 登录态在 `/data`，精简时若 factory reset 就要重登 |
| 绑定关系 | **云端**（`urn:miot-spec-v2:device:speaker:0000A015:xiaomi-lx04:2`） | ✅ 设备列表**不会消失** |

### 一个关键推论

**「小爱 → 米家」的语义解析全在云端**，设备端只负责"唤醒 → 录音 → 上传文本 → 播报"。

所以：

- ✅ **只禁 launcher（桌面）不影响 IoT 链路** —— 桌面只是 UI，语音与 IoT 是分开的。
  社区有先例（deepin DeepHub、mydigit 双系统方案都证实"换桌面后小爱唤醒和米家照常"）。
- ⚠️ 反过来，**设备端小爱没了，云端 IoT 就够不着我们了** ——
  但**我们不需要它够**：我们自己的 ASR 已经出文本，服务端直接调米家 API 就行。

---

## 2. 四条路线

| 路线 | 做法 | 工作量 | 米家可用性 | 结论 |
| --- | --- | --- | --- | --- |
| **A** 保留原厂 system，只禁桌面 | `pm disable` 桌面 + 接管 HOME | **1 天** | ✅ 100%，但小爱**抢麦** | ❌ 违背「不再进小爱」，且我们的唤醒不可靠 |
| **B** 精简 system，挑出米家组件留下 | 砍掉桌面娱乐、留 IoT | **不可行** | — | ❌ 原厂应用依赖 MIUI 私有 framework，无先例 |
| **C** 小爱开放平台做技能 | 把我们的 AI 接进小爱 | 2–3 周 | ❌ 技能**不能控制用户已有的米家设备** | ❌ 且违背接管要求 |
| **D** **服务端调米家云 API** | 我们的 ASR → 服务端 → 米家 API | **2–5 天** | ⚠️ 受凭据/合规限制 | ✅ **推荐** |

### 路线 D 的链路

```
音箱（我们的 App，自建唤醒 + AudioRecord）
   ↓ 音频
我们的服务端（已有 ASR / LLM / TTS）
   ↓ LLM 解析意图「打开客厅灯」
米家云 API（mijia-api / ha_xiaomi_home）
   ↓
米家设备开灯 → 音箱播报确认
```

**服务端加一个米家适配层 + 扫码绑定流程即可，不需要任何 ROM 改动。**

## 3. ⚠️ 路线 D 的真实成本：凭据与合规

| 方案 | 授权方式 | 商用许可 |
| --- | --- | --- |
| [`mijia-api`](https://github.com/Do1e/mijia-api)（扫码登录，token 自动刷新，自带 MCP） | 扫码 | **GPL-3.0 + 免责声明「不得商用」** |
| [`ha_xiaomi_home`](https://github.com/XiaoMi/ha_xiaomi_home)（小米官方，OAuth 2.0） | OAuth | ❌ 许可明写**仅限非商业用途**，不授权用于开发 APP/Web 服务 |
| `hass-xiaomi-miot` / `python-miio` | 账号密码 | 账号密码登录 100% 触发验证码 |

→ **自用 / 内部试点可行；要做商用产品，米家云没有合规通道**，只能走小米 BD 或放弃「控米家」。

## 4. 顺带一条平行路线：MiGPT

[`mi-gpt`](https://github.com/idootop/mi-gpt)（MIT 许可）跑在 PC/服务器上：
通过小米账号轮询小爱云端会话拿到 ASR 文本，再发 MIoT TTS 指令让 LX04 念出来。

- ✅ **社区已在 LX04 实测跑通**（MiGPT v4.2.0 + DeepSeek，稳定）
- ⚠️ **LX04 不支持流式连续对话**（`playingCommand` 不可用），只能一问一答
- ⚠️ 账号风控 `securityStatus:16` 需固定 DeviceId + passToken 绕过
- 💡 **副产品很有用**：通过 MIoT TTS 指令 `[5,1]` 让**原厂 LX04 直接播报**服药提醒文案 ——
  连我们的 App 都不用装就能提醒（但设备必须保持原厂小爱在线）

## 5. 米家值得保留吗？

**值得，但不值得为它牺牲主体验。**

- 老人用米家主要是「开灯 / 开空调」这类一次性指令 —— 而这正是米家 App 本身能做的
- 本产品的核心价值是**服药提醒 + 语音陪伴**，不该被「必须喊小爱同学」绑架
- 保留原厂小爱进程的代价：抢麦、1–2 秒延迟、不能连续对话

所以：

- **米家 = 锦上添花的附加能力**，通过服务端 API 顺带提供
- **不为此保留原厂小爱进程**

### 如果完全不做米家

老人不会觉得「音箱废了」—— 他们本来就把这台机器当「陪伴机」而不是「智能家居中枢」。
但要说清楚一件事：**米家 App 里这台音箱会变成离线状态**，
绑定关系在云端所以设备列表不会消失（灯、插座照常可控），只是音箱条目离线、不能再被远程唤醒。

## 6. 风险清单

| 坑 | 严重度 | 规避 |
| --- | --- | --- |
| 米家 API 凭据 / 封号 | 🔴 | 扫码 + 固定 DeviceId + passToken；商用另有许可问题 |
| 精简 system → 米家 App 里音箱显示离线 | 🟡 | 设备列表不会消失，只是音箱条目离线 |
| 小爱账号 = 米家账号 | ✅ | 同一账号，音箱与设备要绑同一账号 |
| 原厂小爱抢麦 | 🔴 | 精简 system 后天然消失；走 MiGPT 则必须共存 |
| **无「保留米家但换掉 system」的先例** | 🟡 | 有「换桌面保留小爱」的先例，没有「换掉整个 system 还保留米家」的 —— **本方案最大不确定性** |
| LOS device tree 已停更（2023-01-27） | 🟡 | 只影响编译 ROM 路线，不影响路线 D |

## 7. 需要拍板

| 问题 | 影响 |
| --- | --- |
| 这个项目是**自用/内部试点**还是**对外商用**？ | 自用 → 路线 D 直接上；商用 → 米家云无合规许可，要么走小米 BD，要么放弃「控米家」 |
| 老人场景更看重**开机就是我们的界面**，还是**还能喊小爱同学开灯**？ | 前者 → 精简 system（路线 D）；后者 → 保留原厂 system（路线 A），但接受抢麦与延迟 |
