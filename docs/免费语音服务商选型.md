# 免费 TTS / ASR / VAD 服务商选型

> 调研日期：2026-10-17；**§0.5 落地现状补记于 2026-10-18**（代码已演进，
> 下面标「落地现状」的部分以代码为准）。所有"免费"政策以当日官网/官方文档
> 为准，免费额度变动频繁，**下单/接入前请以控制台显示为准**。文中不确定的
> 数字一律标注「待验证」，没有标注的均给了来源链接（见 §8）。
>
> ⚠️ **贯穿全文的第一约束**：本项目**不得依赖任何第三方服务器**
> （固件 `CONFIG_OTA_URL` 默认已指向自己的 `/api/voice/ota`）。因此凡是
> "必须把数据发到某家厂商的服务器"的方案，只能作为**用户自己配的厂商**存在，
> 不能成为平台默认或兜底。文中标「❌ 已否决」的即因此故。

## 这份文档怎么用

用户（项目所有者）的原话是：「哪些模型提供商可以提供免费的 TTS、ASR、VAD 服务」。
落点是**换掉或备份管理后台 `ai_providers` 表里现有的语音接入点**，减少对单一
云厂商的依赖与费用。所以本文每一项都回答三个问题：

1. 免费是真的免费，还是"新用户试用额度"（这个区别是本文最重要的判据）；
2. 能不能**不改代码**直接配进后台（我们的 ASR/TTS 客户端口径见
   `server/app/voice/asr_tts.py` 模块 docstring 与 §0.5）；
3. 对老人体验的影响（流式、中文音质、慢语速断句）。

## §0.5 落地现状（2026-10-18 补记，与代码核对过）

选型结论**大部分已经落地**，但落地形态与 10-17 写文档时的设想有几处关键差异。
**这一节优先于下面 §1-§5 的原始调研。**

### 0.5.1 三家 TTS 已预置 + 服务端自动分发

音色目录与厂商预置的**唯一真源**是 `server/app/voice/catalog.py`：

- `VOICE_CATALOG`：11 种 Edge TTS 音色，每条含 `id`/`name`/`gender`/`scene`/`note`，
  按老人友好度排序（温和在前、活泼在后）。前端改为 `GET /api/voice-catalog` 拉取，
  **不在 `index.html` 里硬编码**（否则会出现"下拉框里有的音色，恢复出厂默认后
  却是另一个"）。
- 出厂默认音色 `DEFAULT_PRESET_TTS_VOICE = "zh-CN-XiaoxiaoNeural"`
  （被 `main.py` 的种子依赖，**值不可改**：改了等于给所有已有部署换人，
  且不触发任何迁移）。
- `VENDOR_CATALOG`：三家厂商预置，供后台下拉选择。**下拉 + 自动填表消灭了
  "endpoint 填成官网首页"这类指不到真因的失败**：

| key | api_style | endpoint | model | 要 Key | 音色数 |
| --- | --- | --- | --- | --- | --- |
| `edge` | `edge` | （空，内置） | — | 否 | 11 |
| `volcengine` | `volcengine` | `https://openspeech.bytedance.com` | `volc.tts_async` | 是（AK:SK，英文冒号分隔） | 5 |
| `aliyun` | `openai_compatible` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-tts` | 是（百炼 Key，非主账号 AK/SK） | 4 |

**服务端自动切换**（`asr_tts.py::_tts_dispatch_style()`）判据顺序是
**provider 优先于 api_style**。⚠️ 这是修过的真 bug：预填的 `api_style` 会截胡
（`provider=edge` 但 `api_style` 被填成 `openai_compatible` 时会走错实现）。
两者都不匹配则回退 `openai_compatible`。**`tts_stream()` 内也做了同样分发**
——否则 Edge 会出现"非流式能出声、流式不出声"（下行去拼 `/audio/speech`
连到本机自己）。

### 0.5.2 Edge TTS 的三条硬事实（原文未写，实测得出）

1. ⚠️ **它不是 HTTP API**。它是**微软 Edge 浏览器的 WebSocket 非公开协议**，
   **只输出 mp3**。依赖 `edge-tts`（会拉入 aiohttp）。桥在
   `server/app/voice/tts_edge.py`，用 **PyAV（`av`）** 解码重采样到
   24kHz/mono/S16LE —— 原文 §1 写的"我们的客户端只剥 WAV 头，不解 mp3"
   已不成立，mp3 解码这一层是桥自己做的。
2. ⚠️ **实测限制：连续 3 次调用，第 3 次会 `ConnectionTimeoutError`（上游限流）**。
   这不是代码问题，是微软侧限流。**任何依赖 Edge 的方案都必须假设它会掉线**：
   后台要能真测（`POST /api/providers/test-voice` 会真打一次合成，回
   `audio_bytes`/`duration_ms`），生产要配多行 `priority` 兜底。
3. ⚠️ 无商业授权、非公开接口，**不得作为平台默认或唯一依赖**。

### 0.5.3 火山引擎已实现私有协议，但签名无法本地实测

私有协议，**AK/SK + 四级派生 HMAC-SHA256**（kDate → kRegion → kService →
kSigning），自定义报文，base64 音频。**V3 API 支持 24k pcm 直出**（正好命中
我们的音频契约）。实现在 `server/app/voice/tts_volc.py`。

⚠️ **签名本地无法实测**（需真实 AK/SK），所以真机首次使用**必须**用后台
"真实测试"按钮验证——这一条要写进运维手册，不能靠"CI 绿了"推断它能用。

### 0.5.4 本地 TTS 为什么最终没做（硬件约束，不是偷懒）

`server/docker-compose.local.yml` 提供两个**可选旁路服务**：
`local-asr`（`modelscope/funasr` / FunASR-SenseVoice，254MB，纯 CPU）与
`local-vad`（`ghcr.io/snakers4/silero-vad-server`，2MB 级 ONNX）。

⚠️ **怎么加载**：这个文件是**compose 叠加文件**，必须与主文件一起加载：
```
cd server
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d
```
它**不是主文件内置的 profile**——文件里**没有任何 `profiles:` 字段**
（全仓 grep `profiles` 只在 `docker-compose.yml:6` 的一句历史注释里出现）。
所以叠加即启动，不存在"按 profile 开关"这一层。

⚠️ **刻意不含本地中文 TTS**。原因是从生产部署形态倒推的：
生产是 **iStoreOS 软路由、无独显**，而 CosyVoice 2 推理需要 **8GB 显存起**
（本文 §2 A7 已写明）。塞进软路由的结果是"容器能起、但合成一句话要几十秒"——
**对老人场景比用云端 TTS 更糟**，表现为设备一直不吭声。
所以用户当初建议的"加本地中文 TTS"按硬件约束裁剪掉了。
这是**取舍，不是遗漏**：将来有了带显卡的机器，按 §2 A7~A9 接本地 TTS，
把 `local-asr` 的写法照抄一份即可。

这些本地服务的端口**只绑 `127.0.0.1`**（服务本身无鉴权，谁都能调去识别音频）。
⚠️ 起起来之后**仍需在管理后台「AI 接入」里手工添加两行**并指向本地地址——
本项目刻意不自动写库，自动写会在"只想临时试试"时留下脏数据，
而删掉它比留下它更麻烦。

### 0.5.5 ⚠️「零配置即可服务」被实测证伪

管理后台 AI 接入页顶部有「服务就绪度」卡片（`GET /api/providers/readiness`），
返回四层事实 `configured` / `resolved`（脱敏）/ `hint` / `critical`。

⚠️ **全新空库下 asr/tts/vad/chat 四项的 `resolve_plan` 全为空，
`resolve_provider` 返 503。** 也就是说**"不配置也能用"这个假设不成立**。
就绪度面板的作用正是**如实反映未就绪**，不是粉饰——
`smoke_voice_catalog` 里有一条断言专门守"零配置必须报未就绪"，
防止有人为了"体验好"把未配置的用途硬报成已就绪。

- **关键项**（`critical`）：`asr` / `tts` / `chat`，缺任一则无法提供完整服务。
- **VAD 不算关键项**：断句已由设备端esp-sr 承担。

### 0.5.6 ❌ 已否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 任何把设备/语音数据发到**第三方托管服务器**的方案（含直接复用 `xiaozhi-esp32-server` 官方容器） | 违反"不依赖任何第三方服务器"。固件 `CONFIG_OTA_URL` 必须指向自己的 `/api/voice/ota` |
| 本地中文 TTS（CosyVoice 2 等） | 生产 iStoreOS 软路由无独显，8GB 显存跑不动（见 §0.5.4）。**这是本轮唯一的"用户建议过但被裁掉"的项** |
| 讯飞 / MiniMax | 私有协议 + 免费档不可商用，与"面向老人家庭的产品"定位冲突；接入成本高于百炼而中文优势边际不足 |

## §0 三分钟版结论

| 需求 | 首选 | 一句话理由 |
| --- | --- | --- |
| TTS 零成本 | **保持 Edge TTS**（现状，已预置为默认厂商） | 唯一"真免费"的云端 TTS，但无商业授权、非官方协议，且**实测连续 3 次第 3 次会超时** |
| TTS 可商用零成本 | **CosyVoice 2（本地，Apache-2.0）**——⚠️ **当前硬件跑不动** | 开源里唯一"可商用 + 中文强 + 原生流式"三合一，但需 8GB 显存，生产 iStoreOS 软路由无独显（§0.5.4） |
| TTS 云端备胎 | **阿里云百炼 qwen-tts**（已预置）+ 火山引擎（已预置） | 百炼真OpenAI 兼容、零代码；火山中文最好但私有协议、签名无法本地实测 |
| ASR 零成本 | **FunASR / SenseVoice（本地）** | 254MB纯 CPU，中文约为 whisper-small 的 3 倍准，官方 OpenAI 兼容端；已作为 `local-asr` profile 提供 |
| VAD 升级 | **Silero VAD（服务端）** | 已作为 `local-vad` profile 提供（2MB ONNX）；⚠️ **不是就绪度关键项**，断句已由设备端 esp-sr 承担 |
| 低成本云端备胎 | **阿里云百炼 qwen-tts + qwen3-asr** | 唯一同时"OpenAI 兼容 + 国内直连 + 按量便宜"的云端组合 |

**最重要的四条人话结论**：

1. 国内云厂商（火山/讯飞/阿里/ MiniMax）的"免费"几乎都是**新用户试用额度
   （几千字符～几万字符，90 天～半年有效期）**，不是永久免费。真正的"永久
   免费"只有两类：微软 Edge TTS（非官方接口）和**本地开源模型**（自担硬件）。
2. ⚠️ **我们的客户端不再"只实现 OpenAI 兼容风格"了**——这一条是本轮最大变化。
   TTS 侧已实现三条独立路径（`openai_compatible` / `edge` / `volcengine`），
   服务端按 `provider` 优先于 `api_style` 自动分发（§0.5.1）。
   **但 ASR 侧仍只有 OpenAI 兼容一种**。所以准确的说法是：
   **TTS 可以接私有协议了，ASR 还不行。**
3. VAD 换神经网络模型（Silero/TEN）主要解决两件事：**老人句中长停顿被误判
   成"说完了"**（现在靠 2000ms 静音兜底 + 自适应放大到 6s 硬扛，见
   `server/app/config.py`），以及**说完后立刻接话的响应速度**。代价是一个
   onnxruntime 依赖和服务端一点点 CPU。
4. ⚠️ **"不配置也能用"是错的**。全新空库下四项 `resolve_plan` 全空、
   `resolve_provider` 返 503（§0.5.5）。就绪度面板的存在就是为了**如实报未就绪**。

## §1 我们的硬约束（选型前提）

这些是从代码里确认的事实，决定了后面每一家的"接入方式"一栏：

- **配置入口**：管理后台「AI 接入」写 `ai_providers` 表，且**厂商从
  `VENDOR_CATALOG` 下拉选**（见 §0.5.1），不要手填 endpoint。字段口径：
  `endpoint`（**带版本号的基址**，如 `https://api.deepseek.com/v1`，
  不自动补 `/v1`）、`api_key`、`model`、`api_style`（**决定走哪条实现**，
  见 §0.5.1 的分发判据）、`params`（JSON，TTS 音色放 `params.voice`）、
  `priority` / `enabled` / `timeout_sec`。
- **TTS 调用形态**：`POST {endpoint}/audio/speech`，JSON 体
  `{"model": ..., "input": ..., "response_format": "pcm", "voice": ...}`，
  期望返回 **24kHz 单声道 S16LE 裸 PCM**（`TTS_RESPONSE_FORMAT="pcm"`、
  `TTS_SAMPLE_RATE=24000`，与固件解码口径一致）。厂商无视 `pcm` 回 WAV 时
  自动剥 44 字节头；`tts_stream()` 已实现增量读取，**厂商用 chunked
  分片发送才是真流式**，一次性发完整段则自动退化为"只 yield 一次"，
  不假装流式。
  ⚠️ **这条只对 `api_style=openai_compatible` 成立**。`edge` 与 `volcengine`
  走各自独立实现（`tts_edge.py` / `tts_volc.py`），不经这条 HTTP 路径。
  分发逻辑见 §0.5.1，**provider 优先于 api_style**。
- **ASR 调用形态**：`POST {endpoint}/audio/transcriptions`，multipart：
  `file`（服务端手写 44 字节 WAV 头的 16kHz mono PCM）、`model`、
  `language=zh`、`response_format=json`，取返回体的 `text`。
  ⚠️ ASR **仍只实现 OpenAI 兼容一种风格**，没有像 TTS 那样的多厂商分发。
- **音色回落链**：角色 `tts_voice` → 形象 `tts_voice` → TTS 配置行
  `params.voice` → 都不填则请求不带 voice 字段。
  出厂默认音色 `zh-CN-XiaoxiaoNeural`（`voice/catalog.py` 的
  `DEFAULT_PRESET_TTS_VOICE`，**单一真源**）。
- **⚠️ 音色目录单一真源**：`server/app/voice/catalog.py` 的 `VOICE_CATALOG`
  （11 种 Edge TTS 音色）。前端从 `GET /api/voice-catalog` 拉取，
  **不在 HTML 里再抄一份**。火山音色清单住在 `tts_volc.VOLC_VOICES`
  （跟协议实现放一起，改音色 ID 时不会漏改前端）。
- **VAD 现状**：服务端能量阈值 + 迟滞 + 底噪跟随（`ELDER_VOICE_SILENCE_MS`
  默认 **2000ms**，检测到长停顿后自适应放大到最多 6000ms）。固件AEC 开启时
  走 realtime 模式、自己不断句，**服务端是唯一断句判据**。
  ⚠️ VAD 在就绪度面板里**不算关键项**——断句已由设备端 esp-sr 承担。

## §2 A. TTS（文本转语音）

### A1. Edge TTS（微软，当前默认）

| 项 | 内容 |
| --- | --- |
| 官网 / 仓库 | 无官网；开源实现 `github.com/rany2/edge-tts` |
| 免费额度 | **永久免费，无需 API Key**。模拟 Edge 浏览器的 WebSocket 协议调用微软 Azure 神经网络 TTS 服务端 |
| 中文 | 支持。100+ 神经音色，含 `zh-CN-XiaoxiaoNeural`（晓晓，当前默认）、`zh-CN-YunxiNeural`、`zh-CN-XiaoyiNeural` 等，覆盖粤语/台湾腔等方言 |
| 流式 | **原生流式**（WebSocket 边合成边返回） |
| 接入方式 | ❌ **不是 HTTP API**。它是**微软 Edge 浏览器的 WebSocket 非公开协议**，**只输出 mp3**。依赖 `edge-tts`（会拉入 aiohttp）；桥在 `server/app/voice/tts_edge.py`，用 **PyAV（`av`）** 解码重采样到 24kHz/mono/S16LE。⚠️ 因此 `VENDOR_CATALOG` 里`edge` 的 `endpoint` **刻意留空**（不是 HTTP 服务，填了反而误导） |

| 适合本项目？ | **保持作为零成本默认 + 基线对照**，但**不得作为唯一依赖**（无商业授权 + 实测会限流掉线）。正式商用请另配一家并用 `priority` 兜底 |

### A3. 阿里云（两条产品线，选错线接入成本差一倍）

### §3.1 特别篇：本地 ASR 能不能上 ESP32-S3？

结论先行：**自由对话的 ASR 只能上服务端；设备端最多做"命令词识别"。**

| 方案 | ESP32-S3 可行性 | 依据（人话） |
| --- | --- | --- |
| SenseVoice / FunASR | **跑不动** | 模型 254MB、要跑完整 encoder 推理；ESP32-S3 只有 512KB SRAM + 外扩 PSRAM，算力差数量级 |
| faster-whisper | **跑不动** | 最小 tiny 39M 在 ESP32 上也远谈不上实时；社区无 ESP32 案例 |
| Vosk | **基本不可行** | 模型 45MB+ 且解码吃内存；树莓派才是它的下限，ESP32-S3 无成熟案例（待验证） |
| sherpa-onnx | **理论边缘，无成熟案例** | 有 14M 参数的 zipformer 能在低端 ARM 上跑（官方称 Cortex-A7 可跑），但那是手机 SoC；ESP32-S3 上无官方支持与实测（待验证） |
| **esp-sr MultiNet（乐鑫官方）** | **可行，限命令词** | 本项目固件已在用。ESP32-S3 上 MultiNet6_cn：内部 RAM 32KB + PSRAM 4100KB、每帧 12~18ms、AISHELL 字错误率 5.2%，支持约 200~300 条自定义命令。**它不是对话 ASR，是"固定指令识别"** |

所以设备端语音识别的现实分工是：**唤醒词 + 固定指令走 esp-sr（设备本地，
已在跑）；自由对话音频上传服务端走 SenseVoice/百炼**。把对话 ASR 塞进
ESP32-S3 不是本轮该考虑的方向。

## §4 C. VAD（语音活动检测）

先说清 VAD 在我们链路里的位置：固件 AEC 开启时走 realtime 模式、**自己
不做断句**，服务端的静音判决是唯一断句判据。现在用的是"能量阈值 + 迟滞
+ 底噪跟随"（`ELDER_VOICE_SILENCE_MS=2000`，检测到长停顿后自适应放大到
最多 6000ms）——能用，但能量法分不清"响亮的键盘声"和"轻声的老人"。

### C5 重点：换更准的 VAD 能解决什么、代价是什么？

**能解决的（都是当前能量法的真实痛点）**：

1. **句中停顿误判**：老人想一下、换口气，能量掉到阈值以下，现在的兜底是
   "多等"（静音阈值放到 2000ms，检测到长停顿再自适应放大到 6000ms）。
   神经网络 VAD 能分辨"停顿"和"说完了"，而不是无脑多等——**该接话的
   时候不用干等 2 秒**。
2. **噪声误触发**：键盘声、关门声、风扇声够响就会被能量法当成一句话的
   开始，送去 ASR 识别出一串乱码。Silero/TEN 在这类场景明显更稳。
3. **响应速度**：说完最后一个字到服务端 finalize 之间，能量法要等满静音
   计时；TEN VAD 对语音结束的判决比 Silero 还快几百 ms（官方对比口径）。
4. **省钱/提准确率**：VAD 挡在 ASR 前面，纯静音/纯噪段不送 ASR——按量
   付费的云端 ASR（百炼/OpenAI）直接少花钱。

**代价（如实说）**：

1. **依赖**：服务端多一个 onnxruntime（或 silero-vad 包）。本项目部署形态
   是单容器，多一个 pip 依赖 = 多一份 CVE 面——这是本项目 `asr_tts.py`
   docstring 里反复强调的纪律，需要一轮正经的依赖评审，不是 `pip install`
   完就算完。
2. **判决迟滞**：VAD 自身不是零延迟。Silero 官方对比里被 TEN 点名有几百
   ms 尾迟滞；TEN 更快但生态更新。 whichever 选哪个，静音阈值都要重新
   标定（建议直接复用现有 `ELDER_VOICE_SILENCE_MS` 作为"VAD 判停后的
   确认窗口"，而不是推翻重来）。
3. **设备端路线不现实**：Silero/TEN 都上不了 ESP32-S3（见 C1/C3）。设备端
   要更准的 VAD 只有两条路：WebRTC VAD（C 移植，KB 级）或 esp-sr 自带的
   VADNet（固件已在用，但 AEC 开启走 realtime 模式时设备侧断句结果没有
   上报给服务端——**这是固件改动，超出本文档范围，记在此处备查**）。
4. **调参工作量**：阈值要从真实老人音频标定。好消息是现有
   `ELDER_VOICE_SILENCE_MS` 那套"宁可多等不可截断"的标定方法论可以直接
   沿用。

**一句话**：VAD 升级是全清单里**性价比最高、风险最低**的一项（服务端
2MB 模型换掉一坨阈值魔法），建议最先做；但它救不了"设备端断句"，那是
固件议题。

### D2 推荐组合（三个，按"愿意付多少成本"排序）

#### 组合一：零成本全本地（服务端自托管）

> ⚠️ **2026-10-18 现状：本组合只在"有带显卡的机器"时成立，当前生产不适用。**
> 生产是 iStoreOS 软路由无独显，CosyVoice 2 的 8GB 显存跑不动
> （见 §0.5.4）。当前实际用的是**组合一的 ASR + VAD 部分**
> （`docker-compose.local.yml` 的 `local-asr` / `local-vad`）+ **组合三的 TTS**。

- **TTS**：CosyVoice 2（本地 GPU，Apache-2.0 可商用，流式首包 150ms）——⚠️ 当前**未部署**
- **ASR**：FunASR / SenseVoice（本地 CPU，254MB，官方 OpenAI 兼容端）
- **VAD**：TEN VAD 或 Silero VAD（服务端，2MB 级 ONNX）
- **适用场景**：想把语音链路完全攥在自己手里、不接受任何云的依赖与授权
  风险、愿意维护一台机器。
- **代价（说在前面）**：一台带 GPU 的服务器（TTS 推理 8GB 显存起）+ 电费；
  CosyVoice 的私有 API 要写一层 OpenAI 兼容薄适配（复用 `asr_tts.py`
  的前提，约一天工作量）；标点/数字读法要按老人场景调；模型更新自己跟。
- **接入提示**：ASR 行 `endpoint` 指向本机 FunASR 服务（内网地址会自动
  绕过代理，见 `asr_tts.py` 的 `_LOCAL_NETS`）；TTS 行指向自建薄适配层。

#### 组合二：低成本云端（国内直连，按量付费）

- **TTS**：阿里云百炼 qwen-tts（OpenAI 兼容；试用 1 万字符/90 天后约
  1000 字 ¥0.013）
- **ASR**：阿里云百炼 qwen3-asr（OpenAI 兼容；试用 10 小时/90 天后
  ¥0.00022/秒 ≈ ¥0.79/小时）——**同一个 key、同一种报文，TTS/ASR 一起换**，
  这是它相对所有组合的最大工程优势
- **VAD**：TEN/Silero（服务端，可选升级）
- **适用场景**：不想维护 GPU，想花小钱把"无商业授权"的隐患换掉。
- **代价**：按量费用（陪伴场景按每设备每天 20 轮、每轮 60 字估算，
  百炼 TTS 月成本约几元/设备量级——**此估算方法待验证**）；额度用完
  即停（要做好 `ai_providers` 多行 priority 兜底，掉话时有备用行顶上）；
  文本/音频过云（隐私口径与 Edge TTS 同级）。

#### 组合三：当前默认（基线对照，不动）

- **TTS**：Edge TTS + `zh-CN-XiaoxiaoNeural`（零成本）。已预置为后台下拉
  默认厂商（`vendors_payload()` 的 `default_vendor="edge"`），选它**什么都不用填**
- **ASR/VAD**：现有配置 + 服务端能量阈值兜底；可选叠加 `local-asr`（FunASR）
  与 `local-vad`（Silero）两个旁路服务
- **适用场景**：继续零成本跑，把组合一/二作为"将来某天必须去掉无商业授权
  依赖时"的预案
- **代价（这就是基线的问题，写在这里作为对照）**：无商业授权；非官方接口
  有被限速/封堵风险（**且已实测：连续 3 次调用第 3 次就`ConnectionTimeoutError`**，
  见 §0.5.2）；mp3→PCM 桥是单点
- ⚠️ **无论选哪个组合，都必须多配几行做 `priority` 兜底**：就绪度面板
  （`GET /api/providers/readiness`）会告诉你缺哪几项，而实测**全新空库下
  四项 `resolve_plan` 全空、直接 503**（见 §0.5.5）——"零配置即可服务"不成立。

## §6 在 `ai_providers` 里怎么配（可直接照抄的填法）

> ⚠️ **首选姿势不是手填，而是从下拉选**。管理后台的厂商下拉直接来自
> `server/app/voice/catalog.py` 的 `VENDOR_CATALOG`（`GET /api/providers/catalog`），
> 选中即自动填好 `api_style` / `endpoint` / `model` / 音色清单。
> 手填 endpoint 的实际后果本项目已吃过亏：把「阿里云百炼」的 endpoint 填成
> 官网首页、或把火山的 AK:SK 只填一半 ⇒ 服务端报的是「返回不是合法 JSON」
> 或「连接被拒绝」，**完全指不到真因**。

`endpoint` 填**带版本号的基址**（不自动补 `/v1`）；TTS 的 `voice` 放
