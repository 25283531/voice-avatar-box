# 系统架构设计（单一镜像目标）

> 本文是**规范性文档**：所有平台级能力必须在同一个 Docker 镜像内完成。
> 与本文冲突的历史设计一律以本文为准。

---

## 1. 目标与硬性约束

### 1.1 一句话目标

**一个 Docker 镜像 = 完整平台。** 用户只需要 `docker compose up -d`，不需要任何外部语音服务、
不需要额外的 AI 服务容器、不需要访问任何第三方平台。

### 1.2 硬性约束（不可妥协）

| 约束 | 说明 |
| --- | --- |
| **单一容器** | 只用 MySQL 时才多一个容器（可选），且仅为数据库。语音链路、记忆、角色全在同一进程 |
| **对外单端口** | 默认只暴露 `8064`（容器内 8080）。HTTP API、WebSocket 语音、OTA 全走这一个端口 |
| **默认零外部依赖** | 不配任何 AI Key 也能**启动**（只是不能对话），不配 SMTP 也能启动（只是不能发邮件）。⚠️ 注意"能启动"≠"能服务"：全新空库下 asr/tts/vad/chat 四项 `resolve_plan` 全为空、`resolve_provider` 返 503，**必须先在后台配好至少 asr/tts/chat 才能真正提供语音服务**（见 §11服务就绪度面板） |
| **用户不接触管理后台** | 注册、找回密码、绑邮箱、改密码、建角色、建形象、绑定设备、付费开通设备使用权——**全部在浏览器完成**（用户端 `/user`），手机 APP 只是另一层封装 |
| **不依赖任何第三方服务器** | 语音链路自研（`server/app/voice/`，xiaozhi 公开协议服务端）。固件 `CONFIG_OTA_URL` 默认指向自己的 `/api/voice/ota`，**不得指向任何第三方** |
| **不绑定任何第三方服务** | 不依赖 mem0 / Letta / Zep 等托管服务，也不依赖第三方语音服务器，算法可以借鉴，调用不可以依赖 |
| **固件编译只在 GitHub** | 本地不编译固件，CI 结果以 Actions 为准 |

### 1.3 容量分界

- **默认：内置 SQLite**，面向家用 / 单机 / 小规模部署
- **用户量上来后：叠加 MySQL**（`docker-compose.mysql.yml`），**只换数据库，不拆分服务**

## 2. 历史问题（已修复，仅存档）

早期为快速验证，语音链路直接复用了 `xiaozhi-esp32-server` 官方容器：

```yaml
# ❌ 旧做法（已删除）
xiaozhi-server:
  image: ghcr.io/xinnan-tech/xiaozhi-esp32-server:server_latest
```

设备拿到的地址是 `ws://xiaozhi-server:8000/xiaozhi/v1/`，意味着**角色、音色、记忆、大模型调用
全部跑在第三方进程里**。这与「自成一体」的目标相悖。

**现状**：已改为自研语音链路（`server/app/voice/`），与本服务同进程同端口。
设备地址由服务端按请求 Host 自动推导（`_voice_endpoints()`），无需手工配置。

> 关键认识：`hello/listen/stt/tts/mcp/abort` 这套 JSON-over-WebSocket + Opus 协议是**公开的**，
> 就像 HTTP 谁都能实现一样，不绑定任何厂商。因此固件侧一行未改。

## 4. 语音链路（自研）

### 4.1 端点

| 路径 | 用途 |
| --- | --- |
| `WS  /api/voice/v1/ws` | 语音主通道（JSON 控制信令 + 二进制 Opus 帧） |
| `POST /api/voice/ota` | OTA 检查。⚠️ 固件 `CONFIG_OTA_URL` 默认已指向这里（在 `Kconfig.projbuild`），**不得指向任何第三方服务器**；只给已绑定设备签发 token，未绑定只返激活码 |
| `GET  /api/voice/health` | 链路自检（模型是否配好、计时状态） |

**Opus 编解码**：**ctypes 直连系统 libopus**（`server/app/voice/opus_codec.py`），
零新增 Python 依赖。Docker / CI 需 apt 装 `libopus0`。
⚠️ 本机没装 libopus 时相关测试会**静默跳过**——`smoke_voice` 前置有一条独立
`libopus_available()` 断言把"跳过"变成"红"，不允许假绿。

**TTS 音频契约（硬约束）**：客户端只吃 **24kHz / mono / S16LE 裸 PCM**
（`TTS_RESPONSE_FORMAT="pcm"`、`TTS_SAMPLE_RATE=24000`），固件按服务端声明的
采样率逐帧 Opus 编码。厂商无视 `pcm` 回 WAV 时自动剥 44 字节头。

**流式 TTS**：`asr_tts.tts_stream()` 增量吐 PCM；厂商不发流式时**降级为非流式、
不假装**。下行时序 `stt → tts start → sentence_start×N → tts stop` 不能改
（设备靠它回落idle）。

### 4.2 协议（与固件已实现的部分保持一致）

**设备 → 服务端**信令：

```json
{"type":"hello","version":3,"features":{"mcp":true},"transport":"websocket",
 "audio_params":{"format":"opus","sample_rate":16000,"channels":1,"frame_duration":60}}
{"type":"listen","state":"detect","text":"你好，小暖"}     // 唤醒词（DISPLAY 值，2026-10-18 改词）
{"type":"listen","state":"start"}                        // 开始录音
{"type":"listen","state":"stop"}                         // 停止录音（服务端开始 ASR）
{"type":"abort"}                                         // 打断当前 TTS
{"type":"mcp","payload":{...}}                           // MCP 工具调用结果
```

**服务端 → 设备**信令：

```json
{"type":"hello","transport":"websocket","session_id":"...","audio_params":{...}}
{"type":"stt","text":"今天中午的药吃了没"}
{"type":"tts","state":"sentence_start","text":"吃了就好"}
{"type":"tts","state":"sentence_end"}
{"type":"tts","state":"stop"}
{"type":"llm","emotion":"happy","text":"..."}            // 表情/情绪驱动 UI
{"type":"mcp","payload":{...}}                           // 请求设备执行工具
```

二进制帧为 Opus 编码的单声道音频（上行麦克风 16kHz，下行扬声器 24kHz）。

**提醒工具调用走服务端 function calling，不走设备 MCP 通道。**
固件侧那个叫"MCP"的东西是**设备本地 JSON-RPC 2.0 工具**（音量/电量/摄像头），
而提醒数据在服务端 `reminders` 表，设备本地根本没有。四个提醒工具定义在
`server/app/voice/tools.py`：`create_reminder` / `list_reminders` /
`delete_reminder` / `toggle_reminder`。
⚠️ **歧义时间必须反问**（「三点」不猜上下午、「每天」缺时间）——
静默建错时间的提醒对老人最糟。

### 4.3 一次对话的完整编排

```
1. 收到 hello        → 鉴权（device token）→ 回 server hello → 建 session
2. 收到 listen.start → 累积上行 Opus 帧到缓冲区
3. 收到 listen.stop  → 调 ASR 模型        → 得到文本
4. 服药/提醒类意图？  → 是 → 放行，不计入陪聊计时（`chat_usage` 里 `used_seconds`
   不累加，服药/提醒会话单独累计便于排查；见 `server/app/models.py` `ChatUsage`）
   ⚠️ 平台会员制已于 commit `e264200` 取消。但**陪聊时长上限本身没删**——
   它是 `chat_quota_config` 表里的**数据**（`free_daily_seconds`，由
   `app/chat_quota.py` 管、在管理后台改），**不是环境变量**。
   取消的是"分档 / 订单 / 人工核销"，以及随它一起删掉的那段环境变量配置
   （`ELDER_ORDER_TTL_HOURS` 等，`config.py:577-580` 留有记录注释）。
   ⚠️ `free_daily_seconds` 现在**只对未授权（未绑定）设备有意义**，
   已授权设备一律无限量——这是 `smoke_quota` 守着的硬不变量。
5. 检索记忆          → 多信号检索 Top-K 条（见第 6 节）
6. 组装 prompt       → 人格（可演化）+ 记忆 + 短期对话历史 + 工具定义
7. 调 LLM（流式）    → 逐句产出
8. 每产出一句        → 调 TTS → 推 Opus 帧给设备
9. 若 LLM 触发工具   → 服务端 function calling 直接执行（提醒类见 §4.2；
                        设备本地能力如音量/电量/摄像头才走 mcp 请求 → 等回执）
10. 对话结束         → 异步做一次记忆提取 + 人格信号更新（不阻塞本次响应）
```

第 10 步必须**异步**进行，否则每轮对话都要多等一次 LLM 调用，老人会觉得卡顿。

**老人语速与停顿（默认值即改善，不需运维调参）**：
`ELDER_VOICE_SILENCE_MS` 默认 1500 → **2000**；句中停顿自适应
（最长句中停顿 ×1.5 + 500ms，封顶 `ELDER_VOICE_SILENCE_MAX_MS`=6000）；
迟滞 enter 0.01 → **0.005** / keep 0.0025 + 软语音期限 2000ms。

⚠️ **踩过的"静默故障"**：轮数用尽的兜底话术只赋给 reply 而**不推 speaker**
⇒ 老人听一片静音而协议层不报错。这类"协议正常但老人听不到"的 bug
**必须有断言看守**，否则它会以"用户说声音小"的形式长期存在。

## 5. 多模型网关

平台需要按用途接不同的模型，配置集中在 `ai_providers` 表。

| kind | 用途 | 备注 |
| --- | --- | --- |
| `asr` | 语音转文字 | 流式优先 |
| `tts` | 文字转语音 | 音色由角色绑定 |
| `llm_main` | **大参数模型**，正式对话 | 贵但聪明 |
| `llm_light` | **小参数模型**，意图识别/结构化抽取/任务执行 | 便宜快 |
| `llm` | 兜底默认 LLM | **存量兼容**：`llm_main`/`llm_light` 没配时退回它 |
| `embedding` | **向量模型**，记忆检索、相似度 | 只做嵌入 |
| `rerank` | 重排（可选） | 检索二次打分 |
| `vision` | 视觉理解（预留） | — |
| `vad` | 端点检测 | **不是预留**：服务端有能量阈值兜底，另提供 `local-vad`（Silero）可选旁路。但就绪度面板**不把它算关键项** —— 断句已由设备端 esp-sr 承担 |

**调用层契约**（`server/app/llm_gateway.py`）：

```python
chat(kind, messages, ...)   # 按 kind 路由，失败自动退到同 kind 的次优先配置
embed(texts)                # 返回 list[list[float]]
```

错误必须**分类**，不能笼统 500：

| 类别 | 上层该怎么做 |
| --- | --- |
| 配置缺失 | 提示"请先在管理端配置 XXX 模型" |
| 401 | API Key 错了 |
| 429 | 限流，退避重试 |
| 超时 | 重试 / 换备用配置 |
| 5xx | 换备用配置 |

> ⚠️ 当前实现里 `record_type` 才是权威判据（`AIProvider.is_config()`），
> `kind` 空只是伴随现象。**读路径一律调 `is_config()`，不要写
> `kind.in_(DEVICE_KINDS)`** —— 那是黑名单式过滤，将来有人往 `DEVICE_KINDS`
> 里加一个 kind，角色行就会混进下发包把真实配置顶掉。正向断言没有这个漏法。

## 6. 记忆系统（借鉴 Mem0 2026 新算法，自行实现）

### 6.1 为什么不直接集成 Mem0 / Letta / Graphiti

| 方案 | Stars | 自托管外部依赖 | 结论 |
| --- | --- | --- | --- |
| Mem0 | ~63k | PostgreSQL + Qdrant（额外 2~3 容器） | ❌ 破坏单一镜像 |
| Letta | ~23k | PostgreSQL + pgvector，且它要接管 agent 生命周期 | ❌ 依赖 + 抢控制权 |
| Graphiti | ~31k | Neo4j / Kuzu | ❌ 依赖 |

它们都很好，但都会被塞进同一镜像的目标排除。**算法是公开的，实现是自己的。**

### 6.2 采用的核心机制

**① 单次 ADD-only 提取（关键）**
每轮对话结束后，用 `llm_light` 调**一次** LLM，从对话里抽出若干条独立事实（JSON 数组），
逐条写入。

> 为什么不做 UPDATE/DELETE：老算法要两遍 LLM（先抽再 reconcile），既慢又会在"覆盖"时
> 丢掉原始信息。**记忆只追加，永不覆盖**，让矛盾的信息并存，由检索时的时序打分决定用哪条。
> 顺带把提取延迟砍掉一半。

**② 多信号检索**
检索时三路并行打分后融合：

| 信号 | 作用 |
| --- | --- |
| 语义相似度（embedding 余弦） | 抓"意思相近" |
| 关键词（BM25 风格） | 抓"专有名词/订单号/药名"这种必须精确匹配的 |
| 实体匹配 | 抓"'张阿姨'在不同记忆里是同一个人" |

> 为什么不能只用向量：老人说"那个白色的降压药"，向量能懂语义但抓不准"苯磺酸氨氯地平片"
> 这种精确药名；而 BM25 反之。**两者必须融合。**

**③ 时序推理**
每条记忆带 `created_at`。检索时近期的记忆加权，且当用户改口时（"我以前养猫，现在养了条狗"），
后来的陈述自动压过先前的陈述 —— 靠时间衰减而不是靠删除旧记忆。

### 6.3 为什么可以用 SQLite，不需要向量数据库

单人记忆规模预估：**数百条量级**。

- 数百条 × 1024 维 float32 ≈ 每条 4KB → 1000 条才 4MB
- 暴力计算 1000 条余弦相似度 ≈ 毫秒级，远比一次网络往返快
- 避免引入 Qdrant/pgvector 这类额外运行时，正好满足单一镜像约束

**但当 MySQL 版本启用时可以选配向量库作为后端** —— 这是"量大之后"的事，不在默认路径。
存储层要抽象出 `MemoryStore` 接口，先实现 SQLite 版本。

### 6.4 数据模型（要点）

```
agent_memories          记忆条目
  id, user_id, agent_id（绑定哪个角色）
  content（事实文本）
  category（profile/preference/event/relationship/medicine/...）
  embedding（二进制 float 数组）
  salience（重要度）
  source_turn_id（可溯源到哪次对话）
  created_at, superseded_at（软失效，不真删）
  access_count, last_accessed_at（用于衰减）

agent_memory_entities   实体表（用于实体信号）
  entity, notion → 一组 memory_id

chat_messages           原始对话历史（召回层，Mem0 图的 Recall Memory）
```

记忆**按 `user_id` + `agent_id` 隔离**：换一个角色就是另一份人格记忆，符合用户"每个设备
绑定不同 agent 角色"的需求。

## 7. 人格与语气演化（让用户越用越贴合）

这部分解决的是"性格、语气、记忆越来越符合用户需求"。**不微调模型**（成本极高且不可逆），
用三条低成本路径：

### 7.1 偏好示例池（主要手段）

从真实对话里自动沉淀【用户反馈 → 偏好】：

| 信号 | 怎么识别 |
| --- | --- |
| **明确纠正** | 用户说"不是，我的意思是 X" / "别这么说话" → 把机器人的原话记成**反例**，用户的表述记成**正例** |
| **重试成功** | 机器人换个说法后用户接受了 → 前后两句自动组成偏好对 |
| **积极反馈** | 用户笑了、接梗、继续聊 → 该回复进成功示例池 |
| **消极反馈** | 用户打断、重复提问、明确说"算了" → 该回复进失败示例池 |

这些 entry 检索后作为 **few-shot 示例**动态注入 system prompt。

> ⚠️ 必须有**防污染机制**：老人的表达可能含糊，也可能被旁人逗弄。入库前要判断
> "这是否真的是有效反馈"，并且所有推断都留审计记录，让家属能看懂"机器人学到了什么"、
> 也能一键删掉某条错误学习。

### 7.2 语气画像（数值化、可解释）

持续统计并用自然语言描述：`回复平均长度 / 口头禅 / 是否爱开玩笑 / 称呼习惯 / 语速偏好`。
这份画像作为**可读文本**注入 prompt，同时**展示给家属看**（APP「我的角色」页），支持手动调。
机器自动 + 人工可纠，比纯黑盒演化可靠得多。

### 7.3 人工直接编辑（兜底）

用户始终能直接改角色的 system_prompt。自动演化是**增益**，永远不能锁死手动修改。

## 8. 用户自助闭环（浏览器完成，不接触管理后台）

平台是**双界面**，不是只有 APP：

| 界面 | 路径 | 静态文件 | 面向 |
| --- | --- | --- | --- |
| 管理后台 | `/` | `server/app/static/index.html` | 按 `is_admin` 过滤功能 |
| **用户端** | `/user` | `server/app/static/user.html` | 家属：绑定、开通、看自己的设备 |

⚠️ **用户端不推去 APP**：绑定与开通全部可在 web 完成。关键事实是后端端点
早就存在且只挂 `get_current_user`（`POST /api/devices/bind`），过去缺的只是
`user.html` 里那一次调用。手机 APP 只是浏览器之外的一层封装。

| 功能 | 落点 |
| --- | --- |
| 账号注册 | `POST /api/auth/register` |
| **找回密码** | `POST /api/auth/password/reset/request` → 邮箱验证码 → `/verify` |
| 邮箱绑定 / 更换 | `PATCH /api/auth/email` |
| 修改密码 | `POST /api/auth/password` |
| 创建 agent 角色 | `POST /api/providers`（`record_type='role'`、`kind` 为空的角色记录） |
| 选择 / 创建形象 | `POST /api/avatars`、设备绑定形象 |
| 绑定设备 | `POST /api/devices/bind`（用户端 `/user` 直接调） |
| 设备付费开通（**设备使用权**，与已取消的平台会员制是两件事） | 线下转账 + 管理员人工核销：4 位订单号 + 区间随机金额，按到账金额反查是唯一对账手段（无在线支付、无凭证上传）。用户端 `/user` 可自助完成，**不推去 APP** |
| **提交问题** | `POST /api/support/tickets`（工单，匿名也可提交） |

邮箱依赖平台 SMTP 配置，管理员配一次即可；**SMTP 不可用时要有优雅降级**（不能 500，要返回明确的"邮件服务未配置"）。

### 8.1 设备配网：不需要 APP

WiFi 配网固件**原生支持浏览器配网**。ESP32 自开热点（名字前缀 `XiaoNuan-`
加MAC 后两位），屏显热点名与 `http://192.168.4.1`，DNS 强制门户，HTML 页在
`firmware/xiaozhi/managed_components/78__esp-wifi-connect/assets/wifi_configuration.html`。
APP 只是另一层封装。

> ⚠️ **热点前缀是 `XiaoNuan-`，不是上游项目的 `Xiaozhi-`**。

## 8.2 服务就绪度：如实反映"还没配好"

管理后台 AI 接入页顶部有「服务就绪度」卡片（`GET /api/providers/readiness`），
返回四层事实 —— `configured` / `resolved`（脱敏）/ `hint` / `critical`：

- **关键项**（`critical`）：`asr` / `tts` / `chat`，缺任一则无法提供完整服务。
- **VAD 不算关键项**：断句已由设备端 esp-sr 承担。

⚠️ **"零配置即可服务"的假设已被实测证伪**：全新空库下四项 `resolve_plan`
**全为空**，`resolve_provider` 返 503。就绪度面板的作用正是**如实反映未就绪**，
不是粉饰——所以 §1.2 里"零外部依赖"只能理解成"零外部依赖也能**启动**"。

`POST /api/providers/test-voice` 会**真打一次** TTS 合成，回`audio_bytes` /
`duration_ms`；而旧的 `POST /api/providers/test` **不覆盖** asr/tts，
会掉进兜底返回"请先创建角色"。

**TTS 厂商预置**（`server/app/voice/catalog.py`的 `VENDOR_CATALOG`，供后台
下拉选择，避免管理员手填 endpoint）：

| key | api_style | endpoint | model | 要 Key | 音色数 |
| --- | --- | --- | --- | --- | --- |
| `edge` | `edge` | （空，内置） | — | 否 | 11 |
| `volcengine` | `volcengine` | `https://openspeech.bytedance.com` | `volc.tts_async` | 是（AK:SK） | 5 |
| `aliyun` | `openai_compatible` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-tts` | 是 | 4 |

服务端自动切换（`asr_tts.py::_tts_dispatch_style()`）的判据顺序是
**provider 优先于 api_style**——预填的 `api_style` 会截胡，这是修过的真 bug。
`tts_stream` 内也做了同样分发，否则 Edge 会出现"非流式能出声、流式不出声"
（下行去拼 `/audio/speech` 连到本机自己）。

音色目录的**唯一真源**是 `server/app/voice/catalog.py` 的 `VOICE_CATALOG`
（11 种 Edge TTS 音色，按老人友好度排序），出厂默认音色
`DEFAULT_PRESET_TTS_VOICE = "zh-CN-XiaoxiaoNeural"`（`main.py` 种子依赖，
**值不可改**）。详见 `docs/免费语音服务商选型.md`。
