## 2. 订单号规则

| 项 | 规则 |
| --- | --- |
| 长度 | **4 位** |
| 字符集 | `A-Z` + `0-9`（36 个字符） |
| 大小写 | **不区分大小写**，落库统一转大写，查询时也转大写 |
| 有效期 | **48 小时**，超时自动置为 `expired`，不再占用可用编码 |
| 唯一性 | **48 小时内不重复**（含所有状态的订单） |

### 为什么 4 位够用 + 必须服务端校验

36⁴ = 1,679,616 种组合。按生日悖论，约生成 **1500 个订单**后碰撞概率才到 50%。
本项目用户量级远小于此，但**必须做碰撞处理**，否则一旦撞号管理员就会核销错订单：

```
APP 生成 code → POST /api/membership/orders
                 ├─ 48h 内未占用 → 创建成功
                 └─ 已占用(409) → APP 重新生成再提交（最多重试 3 次）
```

APP 端生成必须用**安全随机**（不用 `Math.random()`），H5/小程序用
`crypto.getRandomValues()`，App 端用 `plus` 或降级到 `Math.random()` 并提示重试。

## 3. 金额区间随机（可对账，**不需要防重**）

### 设计动机

金额的作用是让「每一笔转账可被区分」，从而完成人工对账。它**不是**订单的
唯一标识 —— 唯一标识是订单号，而订单号与金额一一绑定。

因此核销有两个方向，任意一个都走得通：

- **订单号 → 金额**：用户付款后把订单号报给管理员（APP 通知时自动带上），
  管理员查出这笔该收多少钱，再去收款记录里核对有没有这笔入账。
- **金额 → 订单号**：管理员先在收款记录里看到一笔入账（比如 `11.21`），
  直接用这个金额反查是哪笔订单、哪个用户。

既然订单号能唯一定位订单，**金额就不必独占**。早期版本要求「48 小时内金额
不重复」，实际会很快把区间占满、导致新订单直接下不了单，而重复的金额并不会
造成混淆（管理员结合订单号、时间、用户名即可判断）。已废弃该约束。

### 规则

| 项 | 规则 |
| --- | --- |
| 配置位置 | **平台管理端**（管理员设置，不写死在代码里） |
| 配置内容 | 区间 `[min, max]`，单位**分**（避免浮点误差） |
| 默认区间 | `1000 ~ 1200` 分 = `10.00 ~ 12.00` 元（201 个候选值） |
| 生成 | 在区间内随机取一个整数分 |
| 唯一性 | **不做唯一性约束**，允许不同订单拿到相同金额 |
| 耗尽处理 | 不存在 —— 区间再窄也不会下不了单 |

> 区间跨度只影响「撞金额」的概率，不影响可用性。默认 10.00~12.00 元共 201 个值，
> 本项目量级完全够用；后续接入真实支付接口后，金额即由支付渠道生成，本节规则作废。

### 边界情况

- 同一金额命中多笔订单 → 反查接口按创建时间倒序**全部返回**，由管理员结合
  时间 / 用户名 / 套餐判断（接口返回的是列表，不是单条）
- 管理员修改区间后，已存在的订单金额不受影响（只影响新订单）
- 金额查不到对应订单 → 返回空数组，**不报 404**（「暂时没有」是正常结果）

### 元与分的换算

管理员输入的是元（`11.21`），库里存的是分（`1121`）。换算必须用 `Decimal`，
不能用浮点：`11.21 * 100` 在二进制浮点下是 `1120.9999...`，`int()` 后会变成
`1120`，与库里的 `1121` 对不上，反查就会查不到。

## 4. 订单状态机

```
                  ┌──────────── 48h 超时 ────────────┐
                  ▼                                   │
  [创建] ──▶ pending ──▶ notified ──▶ confirmed ──▶ (终态)
              │            │             ▲
              │            └──▶ rejected │
              │                          │
              └──▶ cancelled(用户放弃)   │
                                         │
                          管理员点「确认到账」┘
```

| 状态 | 含义 | 谁触发 |
| --- | --- | --- |
| `pending` | 已创建，等待用户付款 | APP 创建订单 |
| `notified` | 用户声称已付款，等待管理员核对 | APP 点「我已支付」 |
| `confirmed` | 管理员确认到账，会员已开通 | 管理端 |
| `rejected` | 管理员未查到入账，驳回 | 管理端 |
| `cancelled` | 用户主动放弃 | APP |
| `expired` | 48 小时未支付 | 后端定时任务 |

> **只有 `pending` / `notified` 会占用订单号**（金额不做占用，见第 3 节）。
> `confirmed` / `rejected` / `expired` / `cancelled` 的订单号在 48h 后释放。

## 5. "通知管理员"怎么做（无支付接口时）

按可实现程度排序，本项目**先做第 1、2 项**，第 3 项留配置位：

1. **管理端待办列表**（必做）：订单置为 `notified` 后进入「待核销订单」列表，
   管理员打开平台管理端即可看到，按创建时间倒序。
2. **订单号 + 金额醒目展示**（必做）：列表里直接显示
   `订单号 A3F9 · ￥11.21 · 用户 xxx · 12 分钟前`，管理员复制订单号即可。
3. **可选推送**（留 TODO，配置化）：管理端配置 webhook（钉钉 / 企业微信 / 飞书 / 邮件），
   订单 `notified` 时推送一条消息，内容包含**订单号**。未配置则静默跳过。

## 6. 管理员核销操作

核销有**两个入口**，管理员哪个顺手用哪个：

**入口 ①：已知订单号（用户付款后报号，或 APP 通知里带）**

```
管理端 → 会员核销 → 输入订单号 A3F9
   ↓
显示：订单号 / 金额 ￥11.21 / 提交时间 / 剩余有效期 / 关联用户 / 套餐（30 天）
   ↓
管理员打开自己的收款账号，核对是否有 ￥11.21 的入账
   ↓
┌── 有 ──▶ 点「确认到账」→ 会员立即开通，订单置 confirmed
└── 无 ──▶ 点「驳回」→ 订单置 rejected，可填备注（如"未查到该金额"）
```

**入口 ②：已知金额（管理员先在收款记录里看到钱，反过来找订单）**

```
管理员在收款记录里看到一笔 ￥11.21
   ↓
管理端 → 会员核销 → 输入金额 11.21（元）→ 反查订单
   ↓
返回候选订单列表（按时间倒序）：订单号 / 用户 / 套餐 / 提交时间
   ↓
结合时间和用户名确认是哪一笔 → 点「确认到账」
```

> 一个金额可能命中多笔订单（金额不独占），所以入口 ② 返回的是**列表**；
> 一个都没有时返回空数组，不报 404。

- 核销是**幂等**的：重复确认同一订单不会重复加时长
- 每次核销写审计日志（谁、何时、订单号、金额）

### 后台直接分配（不走订单）

管理员也可以完全跳过支付流程，直接给用户开通会员：
`POST /api/admin/membership/grant { user_id, days, note }`
——用于亲友、测试账号、补偿等场景。

## 7. 会员 / 非会员的差异：陪聊时长

### 7.1 计量口径（关键）

> **一次「会话」= 从唤醒开始，到最后一句答复为止；空闲超过 90 秒自动切断对话。**

```
   唤醒            对话中...              最后一句答复       空闲 90s
    ├──────────────────────────────────────┤                 ├────▶ 会话结束
    │◀────────────── 计入配额的时长 ───────▶│
```

- 会话时长 = `最后一句答复时刻 − 唤醒时刻`（**不含**尾部 90 秒空闲）
- 每日配额 = 所有会话时长累加
- 空闲切断：连续 90 秒无有效输入 → 结束当前会话，不再计入时长

| | 非会员 | 会员 |
| --- | --- | --- |
| 每日陪聊总时长 | **3600 秒（1 小时）** | 不限 |
| 单次会话空闲切断 | 90 秒 | 90 秒（体验一致） |
| 服药提醒相关 AI 调用 | **不限** | 不限 |

### 7.2 服药提醒相关不占用配额

用户的原话例子：非会员说「**今天中午的降压药已经服用了**」——
即使当天 1 小时陪聊额度已用完，**仍要能调用 AI 做语义解析**（提取药品、时间、确认意图）。

判定为「服药/提醒类」的三种信号（任一命中即放行）：

1. **处于提醒确认窗口内**：设备刚播报完一条服药提醒，在确认窗口（默认 5 分钟）内
   的任何语音输入，都视为对该提醒的回应 → 放行
2. **命中服药关键词**（本地词表，由服务端下发、可配置）：
   `药 / 吃药 / 吃了 / 服了 / 服药 / 降压药 / 胶囊 / 片 / 提醒 / 日程 / 确认 等`
3. **明确的确认/取消意图词**：`好了 / 知道了 / 已完成 / 取消 / 稍后 等`

> 关键词匹配在**设备端本地**完成，不消耗任何 AI token。
> 未命中关键词且配额耗尽 → 走本地离线话术（"今天的聊天时间用完啦，明天再聊"）。

### 7.3 配额存储

- **设备端本地**统计并兜底（离线也能限流）
- 联网后通过 `/api/device/chat-usage` 上报明细，服务端按日对账
- 服务端在 `/api/device/sync` 时下发当日：`已用秒数 / 上限 / 空闲切断秒数 / 服药关键词表`

## 10. 安全与风控

- 订单创建频率限制：同一用户 60 秒内最多 3 次，避免刷号占满号段
- **订单号占用**只对 `pending`+`notified` 生效，过期自动释放；金额不做占用
- 核销接口必须管理员权限（`is_admin`），并写审计日志
- 金额区间校验：`min < max`、`min >= 100`（至少 1 元）、`max <= 99999`
- 所有涉及金额的计算用**整数分**，禁止浮点；元↔分换算用 `Decimal`，禁止浮点乘法
- 按金额反查默认只看「仍可能待收款」的订单，避免历史订单干扰判断
