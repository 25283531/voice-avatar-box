## 2. 背景与问题

### 2.1 现状（已读码核实）

- **OTA 配置走环境变量**：`server/app/config.py:280-281` 的 `ELDER_FIRMWARE_VERSION` / `ELDER_FIRMWARE_URL`，默认空；`server/app/voice/__init__.py:122-139` 的 `_firmware_section()` 在**调用时**动态读 config 模块属性，两个都非空才在 OTA 响应（已绑定/未绑定两条路径）带 `firmware` 段。改配置 = 改环境变量 + 重启容器。

## 3. 需求池

优先级定义：**P0** = 本轮必须交付；**P1** = 本轮应交付（可顺带）；**P2** = 明确排期到后续轮次。

### 3.1 P0-1 OTA 配置后台化

**目标**：管理端新增「OTA 固件分发」配置能力，保存即生效（不重启容器），环境变量保留为初始值与回退。

**功能要点**（建议方案，依据见 §6）：

1. **存储**：新建 `firmware_config` 单行表（约定 `id=1`，照 `SmtpConfig` / `ChatQuotaConfig` 的既有单行表模式）：`version`、`url`、`updated_at`、`updated_by`。新建 `firmware_config_audits` 审计表（照 `AdminPresetAudit` 字段模式：`admin_id`、`admin_username` 快照、`action`、`diff` JSON、`created_at`）——现有 `persona.admin_audit.record()` 绑定 `AIProvider` 行，不能直接复用。
2. **API**（管理端约定：`/api/admin/*` 前缀 + router 级 `get_current_admin`）：
   - `GET /api/admin/firmware`：返回当前生效值与来源（`database` / `env` / `none`）。
   - `PATCH /api/admin/firmware`：保存 `version` + `url`；写审计（同事务一次 commit）。
3. **生效逻辑**（改造 `voice/__init__.py` 的 `_firmware_section()`）：**调用时查 DB**（保存即生效，不加缓存——缓存会引入「保存后不生效」的缺陷）；DB 两个字段都非空 → 用 DB 值；否则回退环境变量（两个都非空 → env 值）；否则返回 `None`（不返回 `firmware` 段，默认行为逐字不变）。
4. **校验**：`version` 非空、strip、长度 ≤ 32（与 `Device.fw_version` 的 `String(32)` 一致）；`url` 必须 `http(s)://` 且带主机名（非法 → 400 + 中文说明，参照 `config._validate_base` 的报错文案风格）。半配（只填一个）保存时拒绝并提示「版本号与下载地址必须同时填写」。
5. **冒烟**：`tools/smoke_voice.py` 的 `t_ota_firmware`（1d 组 12 条断言，钉住「默认无段/半配无段/配齐有段」）**必须保持全绿**——冒烟环境 DB 为全新空库，`firmware_config` 无行，env 回退路径天然生效；同时新增 DB 配置场景断言（保存后 OTA 响应带 DB 值、来源显示 `database`、env 与 DB 并存时 DB 优先）。

### 3.2 P0-2 用户端入口 `/`

**目标**：`/` 返回用户端（未登录即登录/注册页），`/admin` 返回管理后台；`/user` 保留兼容。

**功能要点**：

1. **路由**（`main.py:552-564` 一带）：`/` → `user.html`；`/admin` → `index.html`；`/user` → `user.html`（**同内容直接渲染，不做 301 重定向**——理由见 §6.3）。兼容期 ≥ 6 个月，到期后 `/user` 改 301 到 `/` 再下线。
2. **用户端链接**（`user.html`）：登录页文案「平台管理员请访问 管理后台」的 `href="/"` 改 `/admin`（125 行）；顶栏管理员入口 `href="/"` 改 `/admin`（137 行）。
3. **管理后台链接与文案**（`index.html`）：非管理员横幅按钮 `href="/user"` 改 `/`（1303 行，按钮文案「前往我的界面 /」）；约 8 处文案中的 `/user` 改 `/`（164/173/182/186/194/250/1249/1936 行附近，含注释 1384 行）。
4. **冒烟影响**：路由交换无 HTTP 层断言（冒烟只做文件内容检查），但 `smoke_frontend_hygiene.py` / `smoke_voice_catalog.py` 读 `index.html`/`user.html` 文本，文案改动**需工程师逐条核实既有断言**（团队纪律：不许静默跳过）。

### 3.3 P0-3 设备列表四缺口

**目标**：用户端「我的设备」表补硬件型号、绑定时间、固件版本列与升级入口。

| 缺口 | 方案 | 涉及端 |
| --- | --- | --- |
| **硬件型号** | 三端联动：① 固件 `elder_sync_cfg_t` 加 `hw_model` 字段，`sync.c` init 时用 `esp_chip_info()` 取芯片型号（如 `ESP32-S3`），心跳 URL 拼 `&hw_model=...`（沿用 `fw_version` 的 query param 形态）；② 服务端 `Device` 加 `hardware_model` 列（登记进 `schema_patch.NEW_COLUMNS`，带 `server_default`），`/api/device/sync` 收 `hw_model` query param 写入，`DeviceOut` 加 `hardware_model`；③ UI 新列。**存量设备显示「未知」，下次心跳自动补全** | 固件 + 服务端 + UI |
| **绑定时间** | `Device` 加 `bound_at` 列（可空，登记 schema_patch）；`routers/devices.py:177` 绑定处（`dev.owner_id = user.id` 旁）写 `dev.bound_at = utcnow()`；`DeviceOut` 加 `bound_at`；UI 新列。**语义：当前绑定的起始时间**（重新绑定会更新）；存量 NULL 显示「—」。与 `created_at`（设备登记时间）语义区分 | 服务端 + UI |
| **固件版本列** | `DeviceOut` 已有 `fw_version`，纯 UI 补列 | UI |
| **升级入口（务实定义）** | `DeviceOut` 加 `latest_fw_version`（服务端列表序列化时填入平台当前生效的最新版本，空 = 未配置 OTA）；UI 固件版本列内展示「当前版本 → 最新版本」对比 + 一行引导「重启设备后将自动检查并升级」。**不做服务端推送强制升级**——设备侧无远程重启通道（见 P2-4）。未配置 OTA 时只显示当前版本，不显示升级引导 | 服务端 + UI |

**P1（顺带，非用户明示）**：管理后台设备表（`index.html:205-231`）补「硬件型号」列——管理员排障时同样需要，改动仅 UI 一列。

### 3.4 诉求 4：离线提醒（已实现，无需开发）

**结论**：日程提醒**已同步存储在硬件本地**，断网可继续提醒。无需任何开发，PRD 仅作说明与限制条件披露。

**已实现机制**（已读码核实）：

- 提醒表存固件 NVS（Flash 持久化），1s 轮询，本地 RTC 驱动触发（`elder_reminder.h:18`、`reminder.c`）；
- 断网时的确认回执写持久化队列，联网后经 `/api/device/reminders/local` 补录对账（`device_api.py:274`，已存在）。

**限制条件**（UI/文档中应向家属披露）：

1. 单设备提醒上限 **16 条**（`ELDER_REMINDER_MAX`）；
2. 离线时间来自 RTC，**必须外挂 DS3231** 实时时钟模块，否则时钟不可信时触发被暂停（时间门控 `ELDER_MIN_TRUSTED_EPOCH`）；
3. 断网期间的新增/修改提醒需联网同步后才能下发到设备。

### 3.5 P2-4 真·一键升级（排期项，不在本轮）

服务端经 WS 自定义消息通知设备重启并触发 OTA。前置依赖：固件远程重启通道（当前不存在）。本轮明确不做。

## 6. 待确认问题与建议决策

用户已给方向「以使用方便为准则」，以下歧义点由产品侧直接给出建议方案（附理由），不留给用户一堆问号；工程师实现时按此执行，有异议再回退讨论。

| # | 问题 | 建议方案 | 理由 |
| --- | --- | --- | --- |
| Q1 | 硬件型号采集用 sync 新 query 参数还是 body？ | **query param `hw_model`**，与 `fw_version` 完全同形态 | ① 固件 `sync.c:614` 已是 URL 拼 query 的形态，改动最小（加一个 cfg 字段 + 一段 snprintf）；② `/api/device/sync` 是 POST 但 body 解析会引入额外复杂度，query param 对固件 HTTP 客户端最省事；③ 与心跳的既有契约一致，不搞两套传参风格 |
| Q2 | 升级入口是否要在未配置 OTA 时隐藏？ | **隐藏升级引导，只显示当前版本** | ① 没有新版本时显示「可升级」是误导，违背「使用方便」；② 与 OTA 响应「未配置不返回 firmware 段」的现有语义一致（设备永远不 OTA 时不该有升级 UI） |
| Q3 | `/user` 兼容是 301 重定向还是同内容渲染？ | **同内容直接渲染**（`/user` 与 `/` 都返回 `user.html`） | ① 用户端登录态在 localStorage，重定向零收益；② 直渲染无锚点/查询参数丢失风险，行为差异为零，最稳；③ 6 个月后下线时改成 301 到 `/` 即可，演进路径清晰 |
| Q4 | OTA 配置存哪里：新表还是复用？ | **新建 `firmware_config` 单行表 + `firmware_config_audits` 审计表** | ① 项目有单行表先例（`SmtpConfig`、`ChatQuotaConfig`），模式成熟；② `Device.settings` 是 per-device JSON，不是平台配置，语义不符；③ `admin_audit.record()` 绑定 `AIProvider` 行，审计需独立轻表（照 `AdminPresetAudit` 字段模式） |
| Q5 | URL 校验严格 https 还是 http(s)？ | **校验 `http(s)://`，UI 引导 https** | 用户原话是「公网 HTTPS 位置」，但 `DEPLOY.md §1.10` 明确「内网设备给内网地址」——严格 https 会砍掉内网 http 部署能力。校验放宽、UI placeholder 与说明用 https 示例，两头都顾 |
| Q6 | `bound_at` 语义与 `created_at` 如何区分？ | `bound_at` = **当前绑定的起始时间**，重新绑定则更新；`created_at` = 设备首次登记时间（不变） | 家属关心的是「这台设备什么时候到我名下的」；解绑再绑定应反映最新归属。存量 NULL 显示「—」而不是回落 `created_at`——两个时间语义不同，混显会造成「绑定时间」的误读 |
| Q7 | 管理后台设备表是否也补硬件型号列？ | **补（P1）** | 管理员排障（工单里问「这是什么板子」）同样需要；改动仅 UI 一列，成本极低 |

## 7. 不做的事（明确排除）

1. **6 位纯数字激活码**：上一轮已评估否决（现行 13 位结构：1 字母 + 12 数字含 Luhn 校验位），本轮不重启该议题。
2. **真·一键升级（服务端推送强制升级）**：设备侧无远程重启通道，属 P2-4，需 WS 自定义消息 + 固件远程重启 OTA，本轮不做。
3. **固件二进制托管**：本服务只在 OTA 响应里返回 URL，文件由部署方托管（Nginx 静态目录 / OSS / CDN），不引入托管能力。
