# 决策记录

用户（项目所有者）拍板的决策。每条注明轮次、结论与**边界**——结论离开了
边界就会被误用，这是本文件存在的理由。

## D1：测试可以动真实表（未上线期间）

- **轮次**：第 15 轮（2026-10-16，CI 守门人轮）
- **结论**：项目未上线，**不建测试/生产数据隔离机制**。冒烟与 QA 脚本
  直接连真实库跑，不另建影子库、不做数据脱敏管道。
- **边界（硬性）**：**上线前必须补隔离**。「上线」的定义：对真实用户
  开放注册/使用之日。补隔离的最小形态二选一——
  1. 冒烟/QA 一律指向独立 schema 或独立实例（推荐，改连接串即可）；
  2. 保留真实表但所有写操作限定在专属测试账号/测试设备名下，
     并在 CI 里断言「测试数据不外溢」。
  两种选哪种，都要在上线检查清单里留一条「数据隔离已补」。
- **代价**：当前跑一次冒烟会留下真实订单/提醒/角色数据；QA 判读失败
  样本时要知道「库里有什么」不一定是代码造的。指纹守卫
  （`tools/qa_fingerprint.py`）与「失败内容出现本脚本没造过的数据 ⇒
  结论作废」判据（PRD §5.1.7）即为此而设。

## D2：平台人格预设暂不做运营后台

- **轮次**：第 15 轮
- **结论**：人格预设目前**只能改代码 seed**（`server/app/main.py` 的启动
  seed，改一次发版一次），运营侧无法调人格。**运营后台下一轮做，本轮
  不碰。**
- **影响**：
  - seed 的每一次修改都是线上事实 —— 所以 `server/app/main.py` 在
    `.github/CODEOWNERS` 的危险路径清单里，改它必须走 review；
  - 运营临时想调人格（如活动期间放宽某条提示词风格）当前**做不到**，
    不要为此去改生产代码绕行 —— 等运营后台；
  - 下一轮做运营后台时，注意人格红线（`server/app/persona/`）本身
    **不在**运营可调范围内：可调的是非红线参数（语气、称呼、形象），
    红线仍走代码 seed + 黄金副本。

## D3：CI 守门人是本轮重点

- **轮次**：第 15 轮
- **背景**：项目新增了启动期写表机制（`server/app/schema_patch.py` 的
  backfill / dedupe / `_patch_version` 登记），历史上真实发生过 P0
  事故——重启时回填判据写错，用户派生角色被永久刷成 preset，角色变
  只读 + 全平台可见 = 跨用户数据泄漏。这类代码一旦判据写错就是数据
  损坏级事故，正需要人盯；而此前 CI 无 CODEOWNERS、无强制 review。
- **本轮落地**：
  - `.github/CODEOWNERS`：危险路径显式登记（见 README「分支保护与
    PR 流程」小节的清单与事故链路）；
  - `.github/workflows/pr-gate.yml`：常驻门禁「守门人自检」，每个 PR
    必跑（刻意不加 paths 过滤），判据脚本 `tools/ci_gate_check.py`
    CI 与本地共用；
  - `.github/dependabot.yml`：pip / github-actions / docker / npm
    四个生态 weekly 更新，`deps` 前缀。
- **边界（门禁守不住什么，写在这里防止误用）**：同时篡改代码与基准的
  自洽绕过、语义正确性、覆盖 ≠ 真的有人看——这三类没有机械判据，
  靠人工 review。详见 pr-gate.yml 文件头与 README 同名小节。
- ** ruff 的裁决**：本轮评估后**不加** ruff 门禁——F 规则 66 条
  （server/ 10 + tools/ 56）超过「≤30 条且能快速修」的准入线，且 23 条
  需人工甄别（含 ruff 对 `globals()` 动态注入的误报）。项目忌讳「引入
  一个从未跑过的门禁」，修绿 66 条本身是一轮独立工作，留待后续轮次
  先小范围试点（如只对 `server/app/` 开 F 规则）。

## D4：人格预设运营后台 —— 本轮遗留清单（记档，不修）

- **轮次**：第 16 轮（PR #19）
- **背景**：本轮交付人格预设运营后台（8 端点 + 前端 personas 页 +
  103 条断言）。QA 在独立验证阶段报 P0（`PATCH /api/roles/{pk}` 是审计
  旁路，且能无痕清空人格），已修（见下方附记）。此外 QA 还提了两条
  **低危**发现，经读码确认问题成立，但**本轮明确不修**，理由见下。
- **为什么不修**：两条都属于**既有行为**，修它们会突破本轮对外承诺的
  「**启动期净改动 = 0**」（见设计文档 §14.1 的 S16）。启动期逻辑是本项目
  历史上真实出过 P0 事故的地方（见 D3），动它必须单独立项、走
  CODEOWNERS review，而不是搭在运营后台这个 PR 里顺手改。
- **本轮记档的两条**：

  | # | 位置 | 现象 | 为什么危险 | 将来怎么修 |
  | --- | --- | --- | --- | --- |
  | L1 | `server/app/main.py` 的 `_seed()` | 用 `kind == ''` 判「这是 preset 行」，但**静默不匹配时不打 warning** | QA 实测：直连把某 preset 行的 `kind` 改成非空后重启，preset 行数 **1 → 2**（静默堆积重复 preset）。危险在**静默** —— 判据写错不会有任何信号，只表现为「库里怎么有两个小暖」，而那时已经晚了 | 换成**显式** `preset_key` 判据（设计文档 §2.3 已备好方案），并按 §9 的铁律格式重走论证 |
  | L2 | `server/app/routers/admin_presets.py` 的 `list_presets` | 不过滤 `deleted_at`，与同文件 `require_preset` 的口径不一致 | 软删的 preset 仍会出现在管理台列表里，运营会看到一个「删了但还在」的角色，可能重复操作 | 加一个 `deleted_at.is_(None)` 过滤（管理台列表不需要看软删行；要查历史走审计） |

- **D4 附记（P0 的修复方式，也是本轮唯一的对外行为变更）**：
  `POST /api/roles/{pk}/guardrails/soft` 与 `PATCH /api/roles/{pk}`
  对平台预设一律 **403**，判定收在 `roles.py` 的模块级函数
  `reject_preset_write(row)` 里，两个端点共用（刻意收在一处：两处各写
  一遍的话，改一处忘另一处就是下一个旁路，而这种旁路不会被任何断言抓到）。
  **选「堵写入口」而不是「修 `RoleIn` 默认值」** —— 后者会改动所有用户
  角色 PATCH 的语义（那是 APP 已依赖的契约），且解决不了审计旁路本身。
  完整论证见设计文档 §3.5 / §3.5.1 / §15 待决 9。
  **影响面为零**：这两个用户端写入口目前**没有任何 UI 入口**（管理台改走
  `/api/admin/presets`，APP 未接角色编辑），实际调用方为零，所以是行为
  变更而非线上功能回归。断言 **T23 / T31** 钉着，其中 T31-b 用**DB快照**
  逐字比对（不能用管理端读接口自证 —— 两边一起错时断言会假绿）。

## D5：改为直接提交到 main，不再走功能分支 + PR（2026-10-16 用户拍板）

- **背景**：第 16 轮的人格预设运营后台（PR #19）修完 P0 后，代码一直停在
  `feat/preset-admin-backend-v2` 分支上没进 main。用户手动从 main 构建 Docker
  镜像，自然拿不到新代码，于是质疑「为什么不把所有代码放 main、建那么多子分支
  干什么」。
- **根因（不是懒，是规则本身跑不通）**：单协作者仓库下，GitHub 拒绝自审 ——
  `POST /repos/{o}/{r}/pulls/19/reviews` 返回 **422**，
  `PUT /pulls/19/merge` 返回 **405「At least 1 approving review is required」**。
  分支保护要求「至少一人批准」，而仓库里只有一个人，于是**唯一的生产者被规则锁在
  门外**。这是「过严的守门人等于没有守门人」的实证。
- **决策**：所有改动**直接提交并推送到 `main`**，不再切功能分支、不再开 PR。
- **配套操作**：删掉 main 的**必需状态检查**「守门人自检」
  （`DELETE /branches/main/protection/required_status_checks`）—— 它是唯一会
  拦截直接 push 的规则。保留禁强推 / 禁删分支 / `enforce_admins`。
  `pr-gate.yml` 的 `push: branches:[main]` 触发**保留**，改为 push 后运行、
  结果可见但不再拦截。
- **代价（必须写清）**：从此 main 上**没有"合并前有人看过 diff"这道机械关卡**。
  因此 `.github/CODEOWNERS` 与危险路径清单的作用从"合并前关卡"降级为
  "**危险路径所有权登记簿 + push 后体检**"。README 的「分支保护与 PR 流程」与
  「危险路径清单」两节已同步改写，并在危险路径清单里补了动手前的三条自查
  （判据是否变义 / 重启时会发生什么 / 有没有断言能变红）。
- **恢复条件**：将来恢复多人协作者时，把必需状态检查加回即可
  （`PATCH /branches/main/protection`），README 已注明操作方式与
  「改名前先改仓库设置」的坑。

## D6：三项建设的分工与关键子决策（2026-10-16 用户拍板）

- **背景**：用户提出三项需求：① 业务平台区分管理员/用户界面，两者不一致；
  ② 音色资源方案（进 Docker 镜像 / 进硬件固件 / 调用大模型直接生成）由我决策；
  ③ 用户设置的形象、人格预设绑定到用户账户，同一形象/人格可绑多个设备。
- **用户拍板**：新建**用户端 Web 界面**（而非在管理后台藏 tab）；
  设备 token 用量**本轮做、从埋点开始建**；语音链路**落地自研**
  （断裂的语音链路怎么处理 → 自研，不复用外部 xiaozhi 容器）。
- **依赖顺序**：语音链路先行 —— 它是 token **真实**计量的前提（LLM 调用
  进本服务后才拿得到厂商返回的 usage）；其次是埋点与接口；最后是双界面。
  本轮三者并行施工、文件边界隔离，集成接线由 lead 统一做。
- **子决策及依据**：

  | # | 决策 | 依据 |
  | --- | --- | --- |
  | S1 | 音色作为**云端 TTS 音色标识符**，不进镜像也不进固件，运行时调云端 TTS | `tts_voice` 本就是配置字符串（如 `zh-CN-XiaoxiaoNeural`）；固件 597 个 `.ogg` 实测仅 136KB，是按 37 语言分布的**界面提示音**，ESP32 也跑不动 TTS 模型 |
  | S2 | Opus 编解码用 **ctypes 直连系统 libopus**，零新增 Python 依赖 | PyAV 要拖进整个 ffmpeg，与本项目「网关只用 stdlib」的纪律相悖；Docker/CI 用 apt 装 `libopus0`（Dockerfile 注释写清了为何这里可以用 apt 而 tzdata 走 pip —— libopus 没有纯 pip 替代） |
  | S3 | ASR/TTS V1 **只实现 OpenAI 兼容风格** | `ai_providers` 表本就按 `kind=asr/tts` 设计、管理后台已能配置；其余风格报明确错误，不假装支持 |
  | S4 | OTA **只给已绑定设备签发 token**，未绑定只返激活码 | 设备把 OTA 响应里的 websocket 段写进 NVS；给未绑定设备发 token 等于开一个无主账户。v2 HMAC 激活暂不支持（返 400），开发板走 v1 码流程 |
  | S5 | 计量表 `model_usage` **独立于** `chat_usage`，且 `provider_id` **不建外键** | 粒度（次 vs 秒）、用途（对账 vs 配额）、保留策略都不同；平台配置行可删，账本必须留存，外键级联会把账本删出洞 |
  | S6 | 记账失败**只记日志不抛异常** | 老人正在等回答，不能因为账本写不进去就不说话 |

- **V1 已知边界（写清，不假装）**：MCP 工具集成未做（设备 `mcp` 消息只记
  debug 日志）；realtime 聆听模式无 AEC，靠服务端静音兜底断句；ASR 为批量
  式（非流式）；中文音色需运维在管理后台为 TTS 配置行设有效 voice。
- **第 ③ 项的现状结论**：APP 层与数据层**已满足**「同一形象/人格绑多设备」
  （`Device.avatar_id`/`agent_id` 是可空 FK、无唯一约束），本轮补的是
  「在用户 Web 界面上也能做」。

## D7：与 xiaozhi 的关系是「协议兼容」，不是「依赖其服务」；设备配网走浏览器（2026-10-17 用户拍板）

- **背景**：README 开头曾写「语音与 AI 链路**复用**开源 xiaozhi-esp32 与
  xiaozhi-esp32-server」，这句话在语音链路自研落地（commit `d519aba` 落地、
  `d4c0141` 接进 `main.py` 的 `_voice.attach(app)`）之后**已经变成错的口径**；
  用户同时拍板设备配网沿用「设备自开热点 + 浏览器配网」的方式。
- **用户拍板**：
  1. **WiFi 配网不装 APP**：设备未配网时自己开热点（`Xiaozhi-XXXX`）、屏幕上
     显示热点名与 `http://192.168.4.1`，用户用手机/电脑连上热点后浏览器打开该
     地址选 WiFi、输密码即可。
  2. **语音链路口径**：**协议兼容 ≠ 依赖其服务**。我们复用 xiaozhi 的**公开
     协议**（设备侧 WS 帧格式、OTA 响应结构）与固件设计，从而在固件零改动的前提下
     自研服务端；**不部署、不调用 xiaozhi-esp32-server**。
- **边界（硬性）**：
  - 致谢可以留，但**任何文档/文案不得写成「运行时依赖第三方语音服务」**；
    改这些文字时要连带 grep `tenclass` / `xiaozhi-esp32-server` / `复用`。
  - `CONFIG_OTA_URL` **必须指向本服务自己的 `/api/voice/ota`**：OTA 响应会下发
    WebSocket 地址与 token，默认指向第三方等于把整条语音链路的控制权交出去
    （早期默认值是 `api.tenclass.net`，已改）。刷早期固件的设备要改
    `sdkconfig` 重编，或写 NVS 的 `ota_url` 覆盖。
  - 配网**不由服务端参与**：配网页面跑在设备自己的 `192.168.4.1` 上，配网期间
    服务端不需要可达；服务端只管配好网之后的激活码绑定与对话。
  - TTS 音色走管理员在 `ai_providers` 里配的云端 TTS，与 xiaozhi 无关。
- **V1 已知边界（沿用 D6，不假装）**：MCP 工具调用未做；激活 v2 HMAC 明确返
  400；TTS 为批量式（非流式）；realtime 聆听模式无真 VAD，只有服务端静音兜底
  `ELDER_VOICE_SILENCE_MS`（默认 1500ms）。

## D8：push 到 main 自动发布 latest；生产走 Cloudflare Tunnel + iStoreOS（2026-10-17）

> ⚠️ **本条的部署形态部分已被 D21 取代**（2026-10-18：新加坡线路死亡 + 域名被按
> SNI 阻断 → 生产迁国内 VPS + IP 直连）。本条中「push 自动发布 latest」的 CI 约定
> 仍然有效。

- **背景**：用户要求「在 GitHub 直接构建固件，Docker 镜像构建并发布为 latest」，
  并告知实际部署形态：iStoreOS（OpenWrt 软路由）+ Docker + cloudflared 隧道，
  对外 `https://voice.250886.xyz`，源站 `127.0.0.1:8064`（容器 8080）。
- **决定 1（`docker-build.yml`）**：push 到 `main`/`master` 且触及 `server/**`
  时，构建 + 容器冒烟通过后自动推送 `ghcr.io/25283531/voice-avatar-box`
  的 `latest` 与短 SHA tag。PR 保持只构建不推送（未审计代码不进公共 registry，
  且 PR 事件下 `GITHUB_TOKEN` 只读，`packages: write` 不生效）；
  `workflow_dispatch` 手动发布能力保留。**`latest` 的语义 = main 上最新一个
  通过冒烟的构建**，冒烟不过则不推送，latest 不被坏构建污染。
- **决定 2（`firmware-build.yml`）**：OTA 地址核实结论 —— `CONFIG_OTA_URL`
  默认值在 `main/Kconfig.projbuild`（`https://voice.250886.xyz/api/voice/ota`），
  工作流只覆盖 `CONFIG_ELDER_SERVER_URL`，不动 OTA_URL；CI 缓存只含
  `managed_components` 与 `/root/.ccache`，**sdkconfig 不在缓存路径**，
  干净 runner 每次由 `idf.py set-target` 重新生成，旧 sdkconfig 不会带入
  （本机 `build/` 那份指向 `api.tenclass.net` 的 sdkconfig 已被 gitignore，
  未入库）。新增「校验 OTA 地址」步骤把生效值打进每次构建日志兜底。
- **决定 3（部署文档，DEPLOY.md §4.1）**：隧道形态下必须显式设
  `ELDER_VOICE_PUBLIC_BASE=https://voice.250886.xyz` —— 当前镜像 uvicorn
  启动参数没有 `--proxy-headers`，`X-Forwarded-Proto` 不被采纳，
  `request.url.scheme` 恒为 `http`，不配则设备拿到 `ws://` 打 443，
  症状是「能心跳、一说话就断」。同时明确：**不得给 uvicorn 传
  `--forwarded-allow-ips=*`**（XFF 最左段可伪造，限速形同虚设）；
  XFF 由应用层 `ELDER_TRUSTED_PROXY_IPS` 按名单从右往左解析。
- **Cloudflare WS 空闲超时**：如实记录为「长连接空闲可能被对端断开，
  阈值以 Cloudflare 官方文档为准」，处置靠设备侧重连，不在文档里编造秒数。

## D10：部署模式字段 ELDER_DEPLOY_MODE（tunnel/direct/auto）+ 双域名 WS（2026-10-17 用户拍板）

- **背景**：用户的生产部署是 Docker on iStoreOS + Cloudflare Tunnel
  （`voice.250886.xyz`），并明确"最大可能部署在需要隧道的环境中"，同时给出
  退路："实在解决不了就部署在不需要隧道的公网服务器上，或者直接暴露带端口的
  服务，或者分别暴露两个不同的域名"。既有代码只有一个逃生舱
  `ELDER_VOICE_PUBLIC_BASE`，且"反代下要配它"这件事只活在文档里，没有校验。
- **本轮落地**：
  - `ELDER_DEPLOY_MODE`：`tunnel` / `direct` / `auto`（默认）。tunnel 模式
    **缺对外地址即启动失败**（SystemExit，非 WARNING）；direct/auto 按请求
    现场推导（= 历史行为，auto 额外在启动日志说明推断依据）。
  - 新变量 `ELDER_PUBLIC_BASE_URL`（HTTP/OTA，http(s)，始终校验）与
    `ELDER_WS_PUBLIC_BASE_URL`（WS 单独域名，ws(s)），支持"两个域名"形态；
    旧变量 `ELDER_VOICE_PUBLIC_BASE` **不废弃、语义逐字不变**，优先级
    新 > 旧，同时配置时 WARNING。只配 WS 不配 HTTP = 启动失败。
  - 启动摘要日志（`elder.deploy`）：模式、HTTP/WS/OTA 地址、"设备心跳将拿到"
    的完整 URL —— 排障第一现场。
  - 冒烟 `tools/smoke_deploy.py`（端口 8122）：86 条断言，含三模式推导、
    启动失败必红、**与 git 基线 c6f00e8 逐字比对**（auto/direct 行为未变的
    直接证明）、三处反向验证。
- **取舍（为什么 tunnel 缺地址是失败而不是告警）**：缺地址时服务端一切"正常"
  （心跳成功、管理台能开），只有设备一开口就断，运行期零信号；而修法只是一行
  环境变量。tunnel 是显式 opt-in，不影响存量部署。WARNING 方案会被启动日志
  淹没 —— 那正是本特性要消灭的失效形态。
- **取舍（为什么不给 uvicorn 加 `--proxy-headers`/`--forwarded-allow-ips`）**：
  沿用 D8 决定 3。顺带纠正一处流传的机制描述：不传参数**不等于**框架不处理
  XFP —— uvicorn 默认 `proxy_headers=True`、只信 `127.0.0.1`。生产中容器对端
  是 Docker 网桥网关（非回环）所以 XFP 不被采纳，结论不变，但机制是
  "信任名单"而不是"参数缺失"（docs/DEPLOY.md §4.1.3/§4.1.4 已按此改写）。
- **边界**：tunnel 模式下旧变量也要过 scheme 校验（显式声明的生产拓扑从严）；
  auto/direct 下旧变量**刻意不校验**（`wss://` 当 base 用会给出坏 OTA 地址，
  但那是今天的真实行为，静默改它属于改存量语义，冒烟 H4 钉死）。
- **用户该选哪种**：先试隧道（当前生产形态，不暴露入站端口）；公网直暴露
  是临时验证/内网场景的下策（明文 + 匿名注册可达 = token 被消耗的风险）；
  自管 Nginx/Caddy 终止 TLS 时同样按 tunnel 配对外地址最稳。

## D11：断网下的服药提醒 —— 离线能力边界（2026-10-17 记，2026-10-17 更新：MultiNet 已启用，见文末）

### 需求原文（医疗事故级，逐字引用）

> 「如果时间提醒依赖服务端的话，一旦用户设备断网，服药提醒就无法实现，
> 这是严重的医疗事故。我们要预置断网情况下的事件处理。包含以下内容：
> 1、提醒时间必须存储在设备中。2、新建服药提醒可以断网实现。

> 如果断网，就提醒用户"当前设备未连接网络，将使用设备自身能力进行处理"。
> 4、建议将部分关键词（语句）预置在固件中。」

### ⚠️ 诚实结论：离线语音识别目前**不能**用

这是本轮最重要的一条，**不要被 `elder_cmd.c` 这个名字误导**：

- `elder_cmd.c` 只做**意图 → 动作**映射，**不含任何语音识别**。
  它的输入是「一条已经识别好的文字」，由调用方喂进来。
- 固件里唯一能离线听懂人话的是 esp-sr MultiNet（`mn6_cn`，模型文件
  `model/multinet_model/mn6_cn/mn6_data` 确实在仓库里，约 3.6MB）。
  `firmware/xiaozhi/main/audio/wake_words/custom_wake_word.cc` 也确实
  实现了完整的 MultiNet 识别流程（`esp_mn_handle_from_name` /
  `esp_mn_commands_add` / `detect` / `get_results`）。
- **但它没被启用，两个硬阻塞**：
  1. **分区表没有 `model` 分区**。当前 `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME`
     指向 `partitions/v2/16m.csv`，该表只有 nvs/otadata/phy_init/ota_0/ota_1/assets，
     **没有 `model` 行**。esp-sr 的 `CMakeLists.txt` 只有在
     `partition_table_get_partition_info(... "model" ...)` 拿到 size+offset 时
     才会打包并烧写 `srmodels.bin` —— 拿不到就静默跳过，模型不会进 Flash，
     开机 `esp_srmodel_init("model")` 必然失败。
     （对照：`partitions/v1/16m_custom_wakeword.csv` 是**有** model 分区的，
     但它没有 assets 分区，与本项目 EAF 形象包冲突，不能直接换。）
  2. **Kconfig 没选 `USE_CUSTOM_WAKE_WORD`**。`main/Kconfig.projbuild` 的
     `WAKE_WORD_TYPE` 在 ESP32-S3 + PSRAM 下默认选 `USE_AFE_WAKE_WORD`
     （纯唤醒词，不含命令词）；`sdkconfig.defaults` 也没覆盖这一项。
- 因此：**断网时老人只能用按键确认**（长按 → 30s 内短按），
  语音命令词这套分发逻辑处于「已就绪但无人喂词」状态。
  `elder_cmd.h` 声明了 `elder_cmd_on_recognized()` 这个 C 入口
  （定义在 `elder_bridge.cc`，因为执行动作需要 bridge 才持有的屏显/提示音句柄），
  识别层接通时只需加一行调用，不用改分发逻辑。

  它只在源码层面存在。MultiNet 接通、加上那一行调用后，这些代码会自动

> 教训：在这个项目里，「加进 CMakeLists」和「真的在固件里」是两件事，
> 而「数据在固件里」和「调用它的代码在固件里」又是两件事。
> 任何声称"预置"的能力，都要用 `strings` 扫一遍最终产物来验证，

### 关于 emoji 形象（评估后决定不改）

评估过「形象改用 emoji」，结论是**性价比为负**：

- LVGL 内置字体 `font_puhui_common_20_4` **零 emoji 覆盖**（只含 CJK），
  要用 emoji 字形得另找彩色位图字体（Noto Color Emoji 之类），
  **单字体 8-10 MB，比当前全部资产还大**，且要走 `LV_USE_IMGFONT` 软解。
- 当前 assets 里的 21 个 twemoji 已经是 **PNG 图片**（58 KB），不是字体字形。
- 老人对**汉字**的熟悉度远高于 emoji；`💊` 未必被 70+ 老人理解为「吃药」。
- 屏是 320×240，twemoji_64 的细部（眉眼、手势）几乎不可辨。
- 彩色 emoji 在色弱下的区分度也低。

⇒ 形象、字体、emoji **全部保持原样**，没有为功能牺牲任何东西。


### 词表的安全取舍（为什么这么少、这么窄）

语音命令误判有两个方向，代价**完全不对称**：

- **漏识别** → 老人多说一句话，走按键兜底，代价 = 多一步；
- **误识别** → 可能把一次**服药完成**记成已完成，子女端不再告警，
  这一次漏服药就永远没人发现，代价 = **漏服药**。

所以词表刻意做窄（`elder_cmd_words.h`，共 9 条）：

- 新建 4 条：都是完整的「动词+时段+对象+提醒」长句，口语撞上概率极低；
- 确认 3 条：全是**完成体**短句（「吃过了」「我吃过了」「吃完药了」），
  **刻意不收疑问句**（如「我吃过药了吗」）—— 收了就等于允许误报漏服药；
- 查询 2 条：只读，误识别零伤害；
- **没有任何删除 / 改期 / 停用命令**：误删一条服药提醒不可逆，
  收益（少说一句话）远小于风险。

另有 `find_confirmable()` 兜底：只确认「今天已响过且未完成」的那一条，
没到点的提醒说「吃过了」不会被记成已完成（`test_elder_host.c` T3 有断言）。

### 数据安全：replace_all 绝不能抹掉本地自建

`elder_reminder_replace_all()` 是本仓**最容易写错、后果最重**的函数：
它做的是全量覆盖，而老人断网时建的服药提醒只存在于这台设备的 NVS 里，
**没有任何副本**。一次心跳同步就能让它们永久消失。

本轮三道防线：

1. 挑出 `server_id == 0` 的条目 → 保留，不进覆盖集；
2. 表格溢出时**优先保本地**（服务端数据能再拉，本地丢了找不回）；
3. 合并完成后**自检**：保留条目若一条都没在结果里找到，立即
   `ESP_LOGE` 报「服药提醒丢失属医疗事故级数据丢失」。

`tools/test_elder_host.c` T2 专门钉这一条，包含最狠的一遍：
**服务端下发空表**（孩子在 App 里把提醒全删了）时，本地两条必须还在。

### 时间/RTC 前提（关系到提醒准不准）

- **校时来源只有一个**：后端 `/api/device/sync` 返回的 `server_time`
  （ISO8601 带 +08:00），`elder_time_apply_server_time()` 解析后
  `settimeofday()` + 固定 TZ=CST-8。**没有 SNTP，没有 RTC 芯片驱动。**
- **未校时时设备拒绝触发提醒**：`reminder.c` 的 `tick()` 检测到
  `time(NULL) < ELDER_MIN_TRUSTED_EPOCH`（2020-01-01）就**直接 return**，
  只打日志。依据是用户自己的判断：「时间不准时，离线提醒就是错的，
  比不提醒更危险」。这条保护同时覆盖「刚出厂没联网」和「长期离线后 RTC 掉电归零」。
- **`elder_reminder.h` 顶部注释写着「离线必须外挂 DS3231」，这句是设计意图，
  当前代码里没有任何 DS3231 / PCF8563 / esp_rtc 的实现**（已全仓搜索确认）。
  也就是说：**一旦设备长期断电重启，掉电前的时间不保留，设备会认为未校时而
  拒绝响铃，直到重新联网。** 这在当前实现下是「安全失败」（不响错时间），
  但对老人意味着「该吃的药没人提醒」。
- **遗留风险**：若要做到「永久离线也能提醒准点」，必须外挂 DS3231 并实现
  I²C 驱动 + 定期校时；或接受「长期离线=不提醒」这一保守现状。
  **两者之间的取舍需要产品拍板**，本轮未擅自选。

### 新增服务端端点

`POST /api/device/reminders/local`（`device_api.py`，带 `get_current_device` 鉴权）：

- 设备把 `server_id == 0` 的本地自建提醒批量上报，服务端分配 ID 逐条回写；

### 为什么不需要 model 分区

★ **反过来新增 model 分区是有害的**：`espressif__esp-sr/CMakeLists.txt:78-101`
见到 model 分区会用 `movemodel.py` **另外烧一份** srmodels.bin ——

### 唤醒词短语没变，只换了识别引擎

「你好小智」这个短语是产品资产（老人和子女的肌肉记忆），**一个字没改**：
```
CONFIG_CUSTOM_WAKE_WORD="ni hao xiao zhi"
CONFIG_CUSTOM_WAKE_WORD_DISPLAY="你好小智"
```
改的只是引擎：WakeNet（专用唤醒模型）→ MultiNet（通用命令词模型）。

### AEC 未受影响（读码结论，非推测）

`afe_audio_processor.cc:59-65` 与 `application.cc:41-48,279` 都**只读
`CONFIG_USE_DEVICE_AEC`**，与唤醒词类型零耦合。原先「切过去会丢 AEC」的判断不成立。

### ⚠️ 三条**未验证**的风险（必须真机 + 真实老人语音测）

CI 绿只证明「代码能编译、断言能通过」，**不证明它在老人身上好用**。

1. **误唤醒率会上升。** MultiNet 是为「识别有限命令集」设计的，不是为
   「背景音里只对唤醒词起反应」训练。电视声、邻居说话、老人咳嗽都可能触发。
   设备放客厅，这个代价不小。阈值 `CUSTOM_WAKE_WORD_THRESHOLD=20`（0.2）
   是 Kconfig 默认值，**必须在真机实测后调整** ——
   宁可漏唤醒（按键兜底）也不要频繁误唤醒（老人会因此放弃用语音）。
2. **设备自己放音时可能被自己的声音误触发。**
   `audio_service.cc:228-250` 唤醒词与音频处理二选一、`continue`，
   `CustomWakeWord::Feed` 拿的是**未经 AEC 的原始单声道**。
   最坏情况：TTS 复述「您说吃过了就确认服药」时把「吃过了」识别出来 →
   **误确认一条还没吃的药** → 子女端不再告警 → 这次漏服药永远无人发现。
   现有两道防线（`find_confirmable()` 只认今天响过的、误识别有屏显+提示音）
   **都不消除「已响过的那条被误确认」这个风险**。
3. **方言口音下表现未知。** MultiNet 基于普通话训练。西南官话/闽南语/东北话
   的声母韵母偏离训练分布，召回率会明显下降；老人语速慢、停顿多，
   8 音节的「新建早上吃药提醒」尤其容易超出 3000 ms 窗口。
   多数情况是漏识别（可接受），但**「误识别成相邻命令」则是风险 2 的严重后果**。

### 兜底路径完好（刻意保住）

`elder_input.c` 的按键确认路径（长按 → 30 秒内短按）**完全未被本次改动触碰**，
不依赖任何语音识别 ⇒ 识别再不可靠也不会让设备变成砖。

### 未清理项

`CONFIG_SR_WN_WN9_NIHAOXIAOZHI_TTS=y` 成为死配置（choice 选了
`USE_CUSTOM_WAKE_WORD` 后 `build_default_assets.py` 不再打包 wakenet）。
留着无害但有误导性。

## D19：登录限速采「先验口令后过闸门」（2026-10-18）

- **背景**：登录接口需要限速防爆破，但**任何基于 IP 的限速器都可能变成
  DoS 武器**——攻击者只要狂打一个 IP 的登录，就能把同出口 IP 的真实用户锁在外面。
- **设计**（`server/app/ratelimit.py`）：默认 5 秒冷却 / 每分钟 6 次 /
  每小时 20 次，**只计失败次数**。关键在于
  **先验口令后过闸门：口令正确直接发证，不看配额**。
  所以"锁死"只作用于**不知道口令的人**，不会伤到正常用户。
- **⚠️ 配套硬约束**：**禁止配 uvicorn `--forwarded-allow-ips=*`**。
  那会取 `X-Forwarded-For` 最左段（可伪造），限速器形同虚设。
  真实客户端 IP 默认只认 `request.client.host`；
  可信反代用 `ELDER_TRUSTED_PROXY_IPS` 显式配置。
- **遗留 P1**：登录接口（`auth.py`）尚无失败次数上限之外的更多防护。

## D21：新加坡线路死亡，生产迁国内 VPS + IP 直连（域名按 SNI 被阻断）（2026-10-18 用户拍板）

- **背景**：用户实测新加坡云服务器走普通线路、**丢包率 15%**，不适合做本项目

  1. `Test-NetConnection 152.136.230.132 -Port 443` = True（TCP 通）；
  2. openssl 连 IP、**不带 SNI**：TLS 1.3 握手成功、证书链 Verification OK；

  同样做主机名校验。⚠️ 证书没就绪前，固件/APP 报「证书名不符」是**预期的
  中间态**，不是代码问题。
- **改动清单（代码级写死的三处真源 + 派生副本）**：
  - APP：`app/src/http/elder.ts` 的 `BASE_URL`、`app/env/.env` 的

  - 固件 OTA：`firmware/xiaozhi/main/Kconfig.projbuild` 的 `CONFIG_OTA_URL`
  - 固件 elder 组件：`firmware/components/elder/Kconfig.projbuild` 的
    `ELDER_SERVER_URL`，及 `firmware/xiaozhi/sdkconfig.defaults` 与
    `tools/merge_to_xiaozhi.py` 的同源副本（原默认值是内网占位符
    `http://192.168.1.100:8000`）
  - CI：`firmware-build.yml` 的 OTA 白名单同时放行 IP 与域名；

    （多一位 6，永远匹配不到）——**顺手修掉这个存量雷**
  - 冒烟：`tools/smoke_deploy.py` 新增 A2b「Host=IP ⇒ 下发 IP 形态的 ws/ota」
  - 服务端：`ELDER_PUBLIC_BASE_URL` 等注释示例同步
- **Nginx 形态**：IP 直连不带 SNI ⇒ 落到 `default_server`，必须挂 IP 证书；
  域名 server（带 SNI）继续用域名证书，两者并存（配置见 DEPLOY.md §4.3.3）。
- **备案后切回域名**：服务端先行（域名证书 + Nginx 域名 server 生效），

## D24：上游源码冻结在 v2.0.5，不再跟随上游更新（2026-10-19 用户拍板）

**用户原话**：「我们使用的小智项目的部分源码，固定为当前版本，上游代码更新时
不做同步，避免我们自定义部分被上游代码覆盖。」

### 问题
`firmware/xiaozhi/` 名义上是「只读镜像」，但实际有一部分定制是**直接改上游文件**的
（D23 的 70/30 布局就改了 `lcd_display.cc` 6 处）。`sync_xiaozhi.py` 的同步逻辑
只做「与上游内容比对」，**不认识「本地已定制」**⇒ 一次 `sync --force` 会把定制
全部静默覆盖，症状是「布局悄悄回退 / 唤醒词又变回你好小智」——不报错，只回退。

### 做法：让脚本默认拒绝同步（三道门）
1. 显式 `--unlock` 开关；
2. `--confirm 'I-ACCEPT-OVERWRITE-CUSTOM-PATCHES'` 逐字短语；
3. **交互式终端**里再手敲 `sync-xiaozhi`（非交互/CI 一律拒绝）。

`--dry-run`（只读统计）不受限。锁定版本写死在脚本顶部常量
（`PINNED_TAG` / `PINNED_COMMIT`）——改常量**不会**自动解冻，避免有人为让 CI 过
随手改值＝自己拆保护。`CUSTOM_PATCH_FILES` 显式登记全部 8 个直接改动点，
每次运行都打印它们，避免「忘了哪里改过」。

### 验证（负面测试，RC=3 拒绝）
- 默认运行 → 打印冻结横幅 + 受保护清单，RC=3；
- `--unlock` 无 confirm → 拒；`--unlock --confirm ...` 非交互 → 拒；
- `--dry-run` → RC=0 正常放行。
- 同时确认上游本地仓库（`D:/espdev/src/xiaozhi-esp32`）当前就是 v2.0.5/860d12a，
  与锁定版本一致（不一致时横幅会额外告警）。

### 不选的方案与理由
- **改成 git submodule**：CI 需要额外 clone 与 checkout 步骤，且本仓已有 vendor 机制，
  切换成本大于收益。
- **只在文档里写「不要同步」**：文档挡不住 `--force`——恰恰是救急时最容易有人手滑。
  冻结必须落在**脚本行为**上。

## D25：未绑定设备的绑定引导独立成模块，且必须在 app.Start() 之前启动（2026-10-19）

**用户原话**：配网完成后一直显示「云服务断开」标志、没有设备连接序列号，

原 `elder_bridge.cc` 第 8 步「未绑定时屏显激活码」**永远不会被执行**：

```
app_main():  app.Start()  ──►  CheckNewVersion()  ──►  while(true) { … }  永不返回
                                  │
elder_boot 任务：xTaskCreate 在 app.Start() **之后** ⇒ 任务压根不会被创建
```

`Application::Start()` 内部调 `CheckNewVersion(ota)`，而后者在未绑定时
`while(true)`：念激活码 → `ota.Activate()` 连试 10 次（V1 无 challenge，必败）→

- 新增 `firmware/components/elder/src/elder_bind_guide.cc` + `.h`，

- 就绪判据用 `Board::GetInstance().GetDisplay()`：Display 在 Board 构造函数里
  就 new 好，魔法静态保证只构造一次 ⇒ 非空即等价于屏幕就绪。
  （⚠️ `Application` **没有** `GetDisplay()`，只有 `GetAudioService()`——
  早期方案误以为有，代码核实后改用 Board。）
- 绑定态判据：NVS `websocket.token` 非空（ota.cc 只有收到 websocket 段才写，
  而服务端只对已绑定设备下发该段）。**不用** `elder_net_has_token()`——
  那是「配置态」（`CONFIG_ELDER_SERVER_TOKEN`），与绑定无关。
- 激活码改为向服务端 OTA 端点要真码（按 MAC 复用），删掉本地 `ShowActivationCode()`
  ——本地生成的码服务端不认，屏显一个输进去必失败的码比不屏显更糟。
- 节奏：15s 轮询 / 25s 屏显（>轮询周期，不留空白）/ 提示音 12s 后首次、之后 180s 一次。
- 与上游争用：OTA 循环每轮 `Alert(ACTIVATION,…)` 会写同一顶区，
  接受轻微顶替，**不改上游**（已冻结镜像，见 D24）。

   修法：`c2.encode("gbk")` + `cwd=build/`（相对 -I 以 build 为基准）。
3. **`BOARD_TYPE` 宏的斜杠陷阱**：compile_commands 里形态是
   `-DBOARD_TYPE=/"lichuang-dev/"`（CMake 在 Windows 的转义残留），
   在 rsp 里被当成**除号** ⇒ 宏展开成 `lichuang / dev` ⇒ 报一堆
   `'lichuang' was not declared`。修法：先剔除该 token 再补干净定义。
   ⚠️ 早期版本用字面串 `in` 判断「已存在」，因形态不同永远匹配不上 ⇒ 退化成
   「每次都加」⇒ `warning: redefined` 且 **rc=1**（又一个假象）。

**兜底防假绿**：脚本断言 `rc==0 且无 error 行`；若 `rc!=0` 而 error 行为 0，
明确报「疑似 rsp/编码/命令行问题，非源码错误」而不是混进编译错误。
变异测试验证：注入一个未定义函数调用 ⇒ FAIL(rc=1)；还原 ⇒ PASS(rc=0)。

## D28：编译前配置自检（sdkconfig 残留 = 「改了配置固件没变」）（2026-10-19）

**事故**：用户 10-18 要求把唤醒词改成「你好，小暖」，仓库里 `sdkconfig.defaults`
确实改对了。但 10-18 编译烧的固件**仍然只认「你好小智」**，用户报「离线唤醒不能用」。

**根因链（核实到具体文件行）**：
1. ESP-IDF 里 `sdkconfig`（本地生成、**不入库**、10-17 产出）优先级**高于**
   `sdkconfig.defaults`，后者只在**首次生成**时参与；
2. kconfig 对已存在选项默认**不覆盖** ⇒ 改了 defaults 也白改；
3. 全程**不报错、不告警**，症状与「模型没烧进 assets 分区」**完全一样**。

⇒ 顺带查明：`sdkconfig` 里 `CONFIG_USE_EMOTE_MESSAGE_STYLE=y`、
`CONFIG_USE_DEFAULT_MESSAGE_STYLE` 未设 —— **EAF 形象那条路确实是开着的**
（真机黑屏过一次才在 defaults 里注释掉，但 sdkconfig 残留把它留在了开启态）。

**做法**：新增 `tools/prebuild_check.py`，编译前必过，7 条断言：

| 断言 | 拦什么 |
| --- | --- |
| C1 | 我们 overlay 段的键与 `sdkconfig` 冲突（★ 本次真凶） |
| C2a | 显示风格是标准 LVGL（emote 已实证黑屏） |
| C2b | 唤醒词拼音与汉字都是新值 |
| C2c | mn7_cn 模型已选（否则 srmodels 不打包） |
| C3 | 分区表文件存在 |
| C3b | 目标芯片是 esp32s3 |
| C4 | merge 注入完整 |

已接进 `firmware-build.yml`，位置在「覆盖板卡与地址」**之后**、`set-target` **之前**。

**三个写判据时踩的坑（都会造成假红）**：
1. **拿 kconfig 解析器读 `sdkconfig.h`**：C3b 要的目标芯片只以
   `#define CONFIG_IDF_TARGET "esp32s3"` 形式存在于 .h 里，
   解析器一律返回空 ⇒ 永远判红。
2. **比对 defaults 的全部行**：上游按板型切了 `sdkconfig.defaults.esp32s3`
   等文件，它的 WiFi 缓冲区默认值（3/6）与我们的 overlay（6/8）本就不同，
   逐条比对 ⇒ `set-target` 之后永远 C1 失败，真信号被噪音淹没。
   改为**只比我们 overlay 段**（按 merge 脚本的 BEGIN/END 标记切）。
3. **PASS 时仍打印「⚠️ …」文案**：同一份文案在 FAIL 时是解释、在 PASS 时是
   噪音，`[PASS] … -> ⚠️ 这些配置的改动不会生效` 这种自相矛盾输出
   会让人怀疑脚本坏了。

变异测试两轮：放回旧 sdkconfig ⇒ 精准红 3 条；正常态 ⇒ 7/7 绿。

## D30：ccache 与中文路径冲突（编译全量失败，报错完全指不到真因）（2026-10-19）

**现象**：`set-target esp32s3` 成功后编译，12 个编译单元 FAILED，每个都带
```
what(): filesystem error: Cannot convert character sequence: Illegal byte sequence
```

**根因**：命令行第一个词是 `ccache`（ESP-IDF 的 `export.ps1` 自动启用），
而仓库路径含中文（`G:\workbuddy\语音助手\...`）。ccache 做自己的路径转换，
遇到无法映射的字节序列就抛这个错。**被编译的源码本身完全没问题**，
报错里也没有任何「中文路径 / ccache」的字样。

**与 D27 的呼应**：同一个中文路径问题，这次换个身份再出现一次。
凡是把路径当字符串再转换的工具（ccache、GCC 读 @rsp、CMake 打印路径）
在中文路径下都可能出问题——**报错信息与真因毫无关联**是共同特征。

**修法**：`tools/idfwin.py` 里**两层都**设 `IDF_CCACHE_ENABLE=0` ——
① 环境变量层（`build_env()`）、② PowerShell 脚本层。
   单设一处不可靠：`export.ps1` 自己会探测并启用 ccache，
   必须在它**之前**设，之后再补一次防它又打开。
CI（ubuntu）路径无中文，不需要这个开关，但同一份脚本两边都能跑。

**判据要认准**：12 个 FAILED 与 12 处 `ccache ... gcc.exe` **一一对应**
⇒ 全部经由 ccache ⇒ 问题在 ccache 而不在编译器。
看到"多个单元报同一个底层异常"时，先数它们与某个工具调用的对应关系。

## D31：固件内开机自检——把「配置没生效」变成设备看得见的证据（2026-10-19）

**背景**：D28 解决了「编译期」发现配置没生效（`tools/prebuild_check.py`）。
但烧进设备之后呢？串口上没有任何线索，现场只会得到一句「我明明改了」。
老人设备的现场日志往往只有开机那一段，没线索等于没修。

**决策**：新增 `firmware/components/elder/src/config_report.c`（纯 C，注册进 elder
组件的 CMakeLists），在 `elder_bind_guide_start()` 里调用一次，把编译期真正生效的
目标芯片 / 唤醒词 / 显示风格 / 后端地址全部 `ESP_LOGI` 打出来，不符项 `ESP_LOGE`。

**为什么落在绑定引导里而不是 elder_bridge**：`elder_bridge` 由 `elder_boot` 任务拉起，
而该任务在 `app.Start()` **之后**才创建；未绑定设备上 `app.Start()` 永不返回
（见 D24）⇒ 这段日志在「还没绑定的设备」上永远看不到 —— 而那恰好是最需要它的人群。
`elder_bind_guide_start()` 是本项目**唯一**在已绑定/未绑定两种设备上都会执行的最早钩子
（绑定态判断在任务内部才做）。且它在 `app.Start()` 之前 ⇒ 零 merge 改动。

**判据要写「实际值 == 期望值」而不是「值非空」**：非空只证明配过，证明不了配的是哪一个。
而要挡的恰恰是「配了但没生效」。期望值硬编码在 C 侧（可用 `-DEXPECTED_WAKE_WORD_DISPLAY=`
覆盖），因此新增 `prebuild_check.py` 的 **C5**：C 侧期望值必须与 `sdkconfig.defaults`
一致 —— 否则改了 defaults 忘了改 C 侧，真机每次开机都误报 ERROR。
**误报比不报更糟**：一直刷的 ERROR 会让人忽略后面真正的报错。

**已验证 / 未验证的边界**（不要混为一谈）：
- 编译期：`syntax_check_elder.py` 3/3 PASS、`prebuild_check.py` 8/8 PASS，
  C5 变异测试注入「你好小智」⇒ 精准红 RC=1、仅该条红，还原后 `cmp` 字节一致。
- 运行期：`ESP_LOGE` 那条路径**本机验证不了** —— xtensa 产物不能在 x86 上跑，
  本机也没有宿主 C 编译器。它只能上真机验证。**这就是为什么必须有 C5**：
  把能自动验的部分（期望值与配置一致）挪到编译期，运行期只负责「如实播报」。

## D32：语法检查必须按语言各用各的编译命令模板（2026-10-19）

**决策**：`tools/syntax_check_elder.py` 扩到覆盖 C 文件（`config_report.c`），
模板命令按**精确文件名**取：`.cc` ← `elder_bridge.cc`、`.c` ← `rgb.c`。

**踩到的坑**：一开始用 `endswith(".cc")` 找模板，结果匹配到上游 main 组件的
`audio_service.cc`，那条命令的 `-I` 只含 main 组件的头文件路径 ⇒ 三个文件全部报
`nvs_flash.h / config_report.h: No such file or directory`。
**每个组件的 `-I` 集合不同，模板必须来自同一组件。** 这是典型的「工具用错命令
被误读成源码有问题」——三个文件全红的假象比一条真错误更危险，因为它会让人
去改根本没错的源码。

C 与 C++ 也不能共用一份模板：IDF 对 `.c` 走 C 模式、对 `.cc` 走 `gnu++23`，
混用会让语言差异与真实缺陷报在一起，分不清是代码写错还是检查工具用错。

**另一个连带发现**：`firmware/xiaozhi/components/elder/` 是 merge 生成的副本，
改完 `firmware/components/elder/` 必须重跑 `tools/merge_to_xiaozhi.py`，
否则语法检查会报「头文件找不到」——看起来像编译错，其实是副本没同步。

## D33：门禁只能约束「已经存在的东西」——SKIP 是第三种状态（2026-10-19）

**背景**：GitHub 固件构建失败。查下来真因不是代码，是 D28 那个自检脚本**自己**
把流水线判红了：C3b「目标芯片是 esp32s3」在 `build/config/sdkconfig.h` 不存在时
判 WARN，而 `--strict` 把 WARN 升级为失败。但那个文件**正是 set-target 才生成的**，
而自检步骤刻意排在 set-target 之前⇒ CI 干净环境下它**必然**不存在
⇒ 编译还没开始就被拦下。

**这是同一个坑第二次犯**：当天早些时候在 `smoke_frontend_hygiene` 的 L4 上已经踩过
（找不到守卫变量时判红，把一张不存在的卡也要求存在），当时只在那一个点上打了补丁。
教训不该落在某一行，而要落成一条规则：**门禁约束的是「已存在的对象」，
对象不存在时正确答案是「无判据可查」，不是「有问题」。**

**决策**：给 `check()` 引入第三态 `SKIP`——
- 既不算通过也不算警告，`--strict` 不拦；
- 汇总里**单列「跳过 N」**，不混进「通过 N」里。
  把 SKIP 算成通过会让人以为每项都真查过了，而它们其实无判据可查；
  这跟「假绿」是同一类毛病，只是方向相反。

**配套**：CI 在 set-target **之后**加一次复检。第一次自检刻意排在 set-target 前
是为了校验「被覆盖完的 sdkconfig.defaults」，那时确实无sdkconfig 可查；
第二次才有真实判据——C1 能查残留冲突、C3b 能确认 `IDF_TARGET` 真是 esp32s3。
**一次自检不该只有一个时机**：同一个判据在不同阶段的可用性是不同的，
只在一个时机跑等于要么放过、要么假红。

**已验证**：干净 clone + merge 后 `--strict` RC=0（原 RC=1）；
变异注入「按 esp32 编」⇒ 仅 C3b 红 RC=1，还原后 RC=0；本地 8/8 绿。

## D34：模板内联的 uni.* 是假绿温床（2026-10-19）

**背景**：用户报「系统形象库 / 隐私政策 / 用户协议点不动」，三个症状。

**根因**：写法是 `@click="uni.navigateTo({ url: '...' })"`。`uni.*` 是
`@dcloudio/uni-app` 插件在**构建期**注入的，插件改写的是 JS 源码里的调用点；
写在模板表达式里它不参与改写，产物里原样是 `o.uni.navigateTo(...)`，
而 `o` 是 setup 上下文的解构对象 —— 它身上的 `uni` 不是那个 API 对象
⇒ 调用抛 TypeError。异常发生在 Vue 的事件处理器里、无全局 errorHandler
⇒ **被静默吞掉**；模板表达式语法又完全合法 ⇒ **构建也不报错**。

三件事叠加起来（不报错、不构建失败、行为错误）才是它能活到今天的原因。
**凡是「构建成功 + 点击没反应」的报障，第一件事是去产物里搜坏形态，
而不是读源码找逻辑错误** —— 源码看起来永远是对的。

**决策**：
1. 跳转一律写在 script 的具名函数里（已修 4 处，全产物坏形态 4 → 0）。
2. `onBackPress` 等生命周期钩子同理，只能在 script 里 —— 模板内联形态一样坏。
3. `smoke_frontend_hygiene` 加 L5 门禁正则钉死这个写法（变异测试精准红 + 字节还原）。

**关于「统一契约」的教训**：音色试听端点我第一版注释写「返回裸 PCM，
与设备链路契约一致」，随后自己推翻——设备 WS 吃裸 PCM，但 APP 交给
系统播放器，它只认 wav/mp3 这类带容器头的格式。**两个消费者要不同格式，
「统一」不是美德而是 bug**；硬要在端点上统一，前端就得各写一套解码分支。

## D35：找回密码——为什么以「用户名」开头，且把新密码寄进邮件（2026-10-19）

**需求**：登录页那句「忘记密码可在「我的 → 修改密码」处理」要变成可点的入口，
走四步：用户名 → 绑定邮箱 → 验证码 → 服务端把新密码发到该邮箱；
未绑邮箱时提示联系管理员 zxh@250886.xyz。

**为什么以用户名开头**：老人常常只记得自己注册时用的**用户名**，邮箱在哪张
卡片上、拼对没有都说不清。若让他先填邮箱，等于要求「必须先知道邮箱才能找回
密码」，而忘了密码的人恰恰最可能同时忘了邮箱 —— 原提示让人去「我的 → 修改
密码」也是同一个毛病：那是**需要先登录才能进**的页面，而用户正登不进来。

**为什么新链路与旧链路并存而不是替换**：旧的（邮箱 → 验证码 → 用户自设密码）
对口令不出现在邮件里更安全，是「知道邮箱的人」该走的路；新的服务「只记得用户名
的人」。删掉旧的等于逼所有人用更不安全的那条。

**两条必须守住的账号枚举红线**（前端服务端都按此实现）：
1. 「未绑邮箱」与「用户名不存在」返回**完全相同**的 `email_bound`；
2. 邮箱不匹配时只回 `matched=false`，**绝不回显正确邮箱**。
第 2 条一旦破了，「给定用户名 → 探测邮箱」就是现成的用户信息泄露接口，
而它在功能上完全看不出来（页面照样能用）。

**有意保留的弱侧信道**：两类账号的 `message` 措辞确实不同（一个去填邮箱、
一个联系管理员）。消除它就得把两种情况都做成「请联系管理员」，真正没绑邮箱
的用户会被挡在门外。权衡后保留 —— 用户名本身不是机密（登录页就要输入），
「某用户名绑过邮箱」不足以定位到具体的人。**这是取舍不是疏漏，别当漏洞「修」。**

**顺序不可颠倒**：邮件没发出去就**不改密码**。否则用户的新密码只存在于一封他
永远收不到的邮件里，等于把账号锁死。前端也据此明确提示「密码没有被修改」，
否则用户会去用旧密码登录、发现还能登，困惑于「到底改没改」。

**密码字符集刻意排除 0/O、1/l/I**：老人要把它抄到纸上，抄错一位就登不进来，
而他们通常不会回邮件里核对原值。

## D36：「红了但看不到为什么」本身就是缺陷（2026-10-19）

**背景**：`server-ci#95` 红了，但我拿不到任何有用信息—— GitHub 网页的日志正文
是**异步加载**的：web 页面只给空壳、API 要 token、日志下载端点未认证返回
Not Found。三条路都断时只能靠猜「哪步红了」，而本地与干净 clone 都绿，
猜了半天才发现不是代码问题。

**决策**：`server-ci` 加 `tools/run_smoke.py` 包装所有冒烟调用，输出落
`logs/<job>_<name>.log`；job 末尾加 `always()` 诊断步骤，把 FAIL 断言与汇总行
摘进 **job summary**，并上传完整日志 artifact。

**包装器的三个要点**（少一个就前功尽弃）：
1. **退出码必须透传**——忘了 `sys.exit(rc)` 就等于把整个后端 CI 变成永远绿灯；
2. **流式落盘**（不用 `capture_output`）——脚本若卡死/被kill，落盘里至少还有
   崩溃前的部分，而那正是「卡在哪一步」这个最关键的信息；
3. **stdout 与 stderr 同写**——traceback 走 stderr，只收 stdout 会丢掉真正的报错。

**推论**：本地复现不出来时，**不要再猜**。要么让 CI 自己把结论写进 summary，
要么在本地复现同样条件（干净 clone + 同样的环境变量）。「猜哪个 step 红了」
是纯浪费，且会让人把时间花在改错的文件上。

## D37：红灯的定位纪律——先拿日志原文，再写结论（2026-10-19）

**事故**：`server-ci` 连红两次（#95、#96），失败步骤是
`smoke_voice_catalog.py` 的试听组。本地跑该脚本却 **全绿**。

**⚠️ 本条最初被我诊断错了两次，两次都记在这里，因为错法各有代表性**：

1. **第一次：把失败步骤认错。** 我数 yml 里的 `- name:` 推断「step 13 =
   `smoke_proxy_headers.py`」，还煞有介事地说「本地 26/26 绿、干净 clone
   也绿」。实际上 GitHub 的 step number 还包含 `Set up job` / `Post` /
   `Complete job` 这些 `uses` 步骤，数出来必然偏。**拿到日志/API 后才看清
   step 13 是音色目录冒烟。**
2. **第二次：机理说错。** 我断言「真因是打真网络撞微软限流，端点返回 502
   ⇒ `C2 试听端点 200` 红」。拿到 #96 的 artifact 原文后被直接打脸：
   **`C2` 是 PASS 的，`C4/C5/C6`（真 wav 魔数、1ch/16bit/24kHz、音频数据）
   也全是 PASS** —— 说明 **Edge TTS 在 CI 上合成成功了**，
   唯一红的是 `C3 Content-Type 是 audio/wav -> got=None`。

**真因（以 artifact 原文为准）**：`req_bin` 里写了
`dict(resp.headers)`，把 `email.message.Message`（HTTP 头名**大小写
不敏感**）降级成普通 dict，**丢掉了大小写不敏感能力**，只剩精确匹配。
而 uvicorn/h11 发出的头名是**小写** `content-type` ⇒
`.get("Content-Type")` 必然 `None` ⇒ 断言恒红，**而服务端返回完全正确**。
**是测试的取法错了，不是被测代码错了。**

**这个坑本仓已犯过第二次**：`smoke_proxy_headers.py` 第一版就因为
「按 `Location` 取拿到空值」红过一次（那里是 h11 发小写、代码按驼峰取），
当时还专门写了注释。同一个坑换个文件再犯一次，说明**该修的是取法本身，
不是在每条断言里迁就**。

**决策（两条）**：
1. **修取法，不修断言。** 新增 `_lower_headers()` 把响应头统一转小写，
   调用方写 `content-type` 或 `Content-Type` 都取得到，且不再依赖
   「当前 server 恰好发小写」这个隐含前提。
   ⚠️ 我第一版只是把 C3 改成小写取值——**那只是碰巧对**（对应当前
   uvicorn/h11），换个发大写头的 ASGI 栈就又红。变异测试专门验了这一点。
2. **契约与环境无关地断言（这条仍然成立，但理由要改）。** 试听组改为
   打桩 PCM + 进程内直调端点函数，验 wav 容器/60 字限长/502/503，
   真网络合成改 `ELDER_SMOKE_EDGE_LIVE=1` opt-in 且默认 SKIP，
   汇总单列「另有 N 条跳过」。
   ⚠️ 但**这不该被当成 #96 的修复**——真网络其实能通。它解决的是
   「让主路径在任何网络状况下都被验到」这个**独立的**隐患：
   真网络分支依赖非公开协议 + 限流，随时会红，而红的原因与本仓代码无关。

**配套：跳过必须是第三态。** 汇总输出 `81/81 passed（另有 1 条跳过）`，
「跳过」绝不混进「通过」—— 否则「什么都没验」和「都验过了」在报告里同形。
（这是 D33 的 SKIP 第三态在本脚本的落地。）

**最贵的教训不是这个 bug，是「没拿到证据就下结论」**：
我曾三次声称「拿不到 CI 日志、只能靠猜」，并据此写出错误的根因。
实际 `G:/workbuddy/github-token.txt` 一直存在且有效（classic PAT，
用户 `25283531`，限额 **5000/小时** 而非匿名 60），日志与 artifact 都能下。
**根因修正过程见 D38。**

⚠️ **踩到的第三个坑（差点又造一个假绿）**：服务端是 **subprocess**。
最初的打桩是替换测试进程里的 `tts_edge.synth_pcm`，而端点在**另一个进程**里
读自己的模块属性 ⇒ **桩根本不生效**，但测试会「看起来在打桩地通过」。
修法：C2-C10 改为**进程内直调端点函数**（纯逻辑，无需服务），
只有 C1（鉴权，走路由依赖）仍走真 HTTP。

**验证**（不能只靠推理）：
- **复现 #96 红灯**：把 C3 改回大写取值（`git stash` 回旧版即可）⇒
  `C3 Content-Type -> got=None`，与 artifact 原文**逐字一致**。
  这一步同时证明「大小写」才是真因，与网络无关。
- **证明根修与大小写无关**：把 `_lower_headers` 改成转**大写**
  （模拟 server 发 `Content-Type`）⇒ C3 **仍然 PASS**。
  对比：旧代码在这个变异下必红。
- 其余变异测试：采样率 24000→16000 ⇒ 仅 C5 红；
  去掉 `[:60]` 限长 ⇒ 仅 C7 红（这条在旧版**根本无法验证**，因为它打真网络）。
- 双环境：本地无桩 81/81 绿；CI 模拟桩 81/81 绿。

**推论（比这一条事故更通用）**：**写测试时必须问「这段代码在 CI 上和在
我机器上跑的是同一条路径吗」。** 只要答案是「不是」，绿灯就不可信。
可选依赖（Edge/opus/云 SDK）都会制造这种分叉。

## D38：「我没有 X」之前必须先查——尤其当用户已经告诉你 X 存在（2026-10-19）

**事实**：用户指出 `G:/workbuddy/github-token.txt` 就是 token，并质问
「之前你一直在用，为什么现在又说没有 token」。**用户是对的。**
我确实在同一会话里多次声称「没有 token / 拿不到 CI 日志」，
并据此**写出了错误的根因**（见 D37 的两次误诊）。

**实测（拿到 token 后立刻验证）**：
- classic PAT，40 字符，`GET /user` → `25283531`，**有效**；
- 限额 **5000/小时**（匿名只有 60）⇒ 我之前反复撞的 `rate limit exceeded`
  是因为**没带认证**，而不是「没有 token」；
- `GET /actions/jobs/<id>/logs` → **200，51900 字节**（匿名是 403）；
- `GET /actions/artifacts/<id>/zip` → **200，27868 字节**，解出 7 个日志。

  拿到这份 artifact 后，D37 里我断言的根因**被原文直接推翻**。

**为什么会犯**：我把「curl 不带认证撞到 403/429」当成了「环境不允许」，
并顺势推广成「日志拿不到，只能靠猜」——**这是一个未经核实的自我设限**。
真实情况只是**我没带凭证**。更糟的是我据此**停止了尝试**：
不去 `ls` 一下用户早就指过的目录。

**决策（两条纪律）**：
1. **说「我没有 X / 做不到 Y」之前，必须先穷尽本地可查来源**
   （项目内配置、用户级目录、`~`、环境变量）。
   用户在对话里说过「X 存在」时，**默认自己还没找到，而不是用户记错了**。
2. **「工具返回 403/429」≠「没有权限/不存在」**。必须先确认**请求本身**
   是否完整（有没有带认证头、参数对不对），再下能力性结论。
   我上一轮把「匿名请求被拒」直接读成「环境不允许」，
   这是把**自己的调用缺陷**误报成了**世界的限制**。

**推论**：**最贵的错误不是不会用工具，是把「我没做到」当成「做不到」。**
前者会去找办法，后者会直接产出错误结论 —— 而错误结论还会被写进决策记录、
去指导后续工作。**在信息不足时，正确姿势是「我不知道」，不是「我做不到」。**

配套（可观测性优先级，从高到低）：
1. `github-token.txt` + `GET /actions/jobs/<id>/logs` ⇒ **完整 job 日志**，
   含每条命令的 stdout/stderr —— 定位失败原因的首选；
2. `GET /actions/runs/<id>/artifacts` + 下载 zip ⇒ 我自己落盘的
   `logs/*.log`（`run_smoke.py` 的产物）；
3. `GET /actions/runs/<id>/jobs` ⇒ 逐步骤 number/conclusion，
   定位「哪一步红」最快，且**不需要任何 token**（匿名即可）。

## D39：同一事实存在两份真源时，比「没有」更危险（2026-10-19）

**事故（发版前自查发现，尚未流出）**：`android-build.yml` 里写着

```yaml
VCODE: ${{ inputs.version_code || '100' }}
```

而版本号的另一份真源在 `android/app/build.gradle.kts`
（`versionCode = findProperty("VERSION_CODE") ?: 100`）。
**push 构建时 `inputs` 为空** ⇒ 恒定传 `-PVERSION_CODE=100`
⇒ 把 gradle 里刚改成 110 的值**盖回旧值**。

后果：产物文件名写着 `elder-companion-1.1.0-110.apk`，
包内版本号却是 **100** ⇒ 安卓判为低版本、**拒绝覆盖安装**
⇒ 症状是「新版发了但老人装不上」，且构建全程绿灯。
比「压根没有版本号」更坏：没有版本号时至少不会假装成功。

**为什么会长期存活**：两份真源**各自都正确**，只在组合使用时互相覆盖。
任何单看一处的人（包括我）都会认为它是对的。

**决策**：
1. **同一事实只留一份真源。** 版本号唯一真源放在 `build.gradle.kts`，
   yml 不再兜默认值 —— 「兜默认值」正是把两份真源缝在一起的那针。
2. **让程序自己报出它的值。** 新增 `printElderVersion` 任务，
   CI 据此给产物命名 ⇒ 「产物名 == 包内版本」成为**可断言的契约**，
   而不是靠人记得两处要一起改。
3. **读不回就中止，不猜。** 拿不到生效版本号时 `exit 1`，
   绝不用默认值兜底发包（兜底 = 又引入一份假真源）。
4. **门禁钉住「必须递增」**：`versionCode` 必须 > 上次发布值，否则 exit 1。

**推论**：加「默认值」之前先问一句 —— **这个默认值和另一处的默认值
是不是同一件事？** 是的话，它就是第二份真源，且会静默覆盖第一份。
「配置项有兜底」听起来是健壮性，实际上是让漂移变得不可见。

### D39 补记：同一个错误有三个藏身处，清一处不算修好（2026-10-19 补）

发 1.1.0 时，D39 那个「两份真源」的错误**在同一天复发了三次**，
而我第一次只清掉了其中一处：

| # | 位置 | 形态 | 谁会踩到 |
|---|------|------|----------|
| 1 | `android-build.yml` 的 `env:` | `inputs.x \|\| '1.0.0'` | push 构建恒定传旧值 |
| 2 | `android-build.yml` 的 `inputs.default` | `default: '100'` | **dispatch** 构建恒定拿旧值 |
| 3 | `app-pack.yml` | 两处都有 + 无条件改写 manifest | 走 DCloud 云打包时 |

**第 1 次修复的教训**：我只检查了自己**记得的那一处**。
第 2、3 处是「同一种错误的不同形态」：

- `inputs.x || '默认值'` 与 `inputs.default:` 在语义上**完全等价**
  —— 都是「没给就用旧的」。前者写在 env，后者写在 input 定义里。
- 更隐蔽的是「**空**的 default」与「**没有** default」行为不同：
  前者让 dispatch 恒定拿到旧版本号，后者才表示「用下游真源」。

**为什么三次都漏**：找 bug 时我用的是**记忆式检索**
（「我记得是 `env:` 里的 `||`」），而不是**机械式全量检索**
（`grep -n "1.0.0\|'100'\|versionCode"`）。
记忆式检索只能覆盖「已经知道存在」的位置。

**纪律（补进 D39）**：
1. 修「多处共有的错误」时，**必须用全量检索确认清干净**，
   不能靠「我记得在哪见过」。检索模式要在动手前先定好。
2. **同一个语义的不同写法要一起搜**：`|| 'x'` / `default: 'x'` /
   `or 'x'` / `: 'x'` 都是同一件事的不同形态。
3. 「某处留空用下游真源」和「某处兜一个默认值」**不能共存** ——
   前者才是意图的表达，后者是漂移的温床。

**一个值得记的正向结果**：第二次修复时，`#42` 的失败日志里
`##[error]versionCode=100 未高于上次发布的 100，发版前必须递增`
—— **门禁按设计生效了**。若没有它，#42 会绿，而产出的包
文件名写着 1.1.0、包内版本号 100，老人装不上、无人察觉。
新加的守卫第一次上场就抓到了一次真事故（虽然事故源是我自己的配置）。
这正是「绿灯不等于对」的又一例。

## D42：激活码从「1 字母 + 12 数字」改为「6 位数字 + 1 位校验位」（7 位全数字）

- **轮次**：第 18 轮（2026-10-20，用户实测第三轮）
- **结论**：激活码格式改为 **6 位随机数字 + 1 位 Luhn 校验位 = 7 位纯数字**，
  屏显分组 `123-4567`。服务端 `security.generate_activation_code()` 与固件
  `elder_activation_generate()` 同步改，算法逐位一致。
- **依据（用户原话）**：「播报依然只有数字，没有字母。更改设定，把激活码
  设定为 6 位纯数字 + 1 位校验码的格式。」
- **根因（为什么播报缺字母）**：上游 `Application::ShowActivationCode()`
  （`firmware/xiaozhi/main/application.cc:201-229`）逐字符查音效表，
  而 `assets/lang_config.h` 只有 `OGG_0..OGG_9`，**没有任何字母音** ⇒
  13 位码的首字母被 `find_if` 落空后静默跳过，老人只听得到 12 位数字，
  照输必被 APP 的 13 位校验拒掉。语音侧无解（补字母音要重烧资源分区），
  全数字是唯一能让「听到的」等于「要输的」的形态。
- **代价（硬性记录，不许淡化）**：密钥空间从 26×10¹¹ ≈ 2.6e12 降到 10⁶，
  **掉 6 个数量级**；校验位由前 6 位完全决定，**不增加任何熵**，
  只防手误不防攻击。因此下列三条是**同一决定的一部分**，缺一条就不该上线：
  1. **绑定接口限速**：`ratelimit.bind_gate()`，每 IP 每分钟 5 次 / 每小时
     40 次失败（成功不限速、并清零该 IP 计数）；
  2. **单码失败上限**：`ActivationCode.attempts / max_attempts`（默认 5），
     用尽即失效，换 IP 也不能对同一枚码无限试；
  3. **码与 MAC 强绑定**：`bind_device` 校验 `row.device_id` 与 APP 上报的
     `device_id` 一致，撞到别人的码也绑不到自己名下。
- **顺带修掉的两处结构性缺陷（7 位化之前被大空间掩盖）**：
  - `voice._reusable_activation_code()` 原先只复用「未过期」的码 ⇒ 设备每
    10 分钟新建一行且**全仓库没有清理任务**，一台长期未绑定的设备一周能攒
    上千行僵尸记录，10⁶ 空间会被直接吃光。改为「一台设备一辈子一枚码」
    （不看过期、复用时顺延有效期，跳过已用尽的行）。
  - `voice._ensure_activation_code()` 原先**零重试**，撞上唯一索引就是未捕获
    `IntegrityError` → 500（这是无鉴权端点，设备每 15s 撞一次）。改为 8 次
    重试 + 捕获 IntegrityError 回滚重试。
- **兼容策略**：**不做双长度过渡**。老库里 13 位未用行在复用路径上被
  `length(code) == ACT_CODE_LEN` 过滤掉，设备下一轮轮询（15s）即拿到新码；
  历史行保留不迁移（`code` 列宽 16 容得下 7 位）。
  上线顺序：**先服务端后固件** —— 反了会让在线设备在升级窗口内绑定失败。
- **断言守护**：`tools/smoke_server.py`（7 位 + Luhn6 + `123-4567` 分组）、
  `tools/smoke_voice.py`（OTA 下发 7 位全数字）、
  `tools/smoke_local_reminders.py`（7 位才能进入绑定流程）。

## D43：`/api/voice/ota` 加「新建激活码」配额（只限新建，不限复用）

**背景**：`/api/voice/ota` 是**无鉴权**端点（设备此刻还没有 token），身份就是
请求头里的 `Device-Id`（MAC）。7 位化之后（D42），未绑定分支会按 MAC
**建一行**激活码，于是产生两条无凭证可走的路径：

1. **写库放大**：随机 MAC 刷端点 = 无限建行，无需任何凭证；
2. **批量收割**：批量拉 MAC 就能收集别人的待绑定码，再配合绑定端点的
   限速（D42 的三道闸门）慢慢试。

D42 的三道闸门都在**绑定侧**（猜码），没有任何一条约束**发码侧**。

**决策**：`config.OTA_NEW_CODE_PER_HOUR`（默认 100/小时/来源），实现为
`ratelimit.ota_new_code_gate()` + `record_ota_new_code()`，复用同一个
`_FailureStore`（第三份规则表，不是第三份实现）。

**边界（三条都必须写清楚，否则会被"顺手优化"掉）**：

- **只记「新建」，不记「复用」**。设备端 `GUIDE_POLL_MS = 15s` ⇒ 单台设备
  约 240 次/小时。若复用也计数，正常设备会在 25 分钟内被自己的轮询打满，
  表现为「设备突然不显示激活码」——**那正是 D42 这一轮在修的症状**，
  绝不能自己再造一个。故配额实际约束的是「一个来源一小时能注册多少台
  **新设备**」。
- **被拦的请求不记账**（与登录同一条铁律）：否则持续敲就无限续期窗口，
  一小时上限退化成永久封禁。
- **100 台/小时不会误伤真实场景**（一天装 100 台都够）。但生产在 nginx
  后面且 `ELDER_TRUSTED_PROXY_IPS` 未配时，`client_ip()` 取到的是反代地址
  ⇒ 全站共用一个键，配额变成「全站每小时最多注册 100 台」。仍高于任何
  合理装机速度，故可接受；**要按来源精确限流必须配 `ELDER_TRUSTED_PROXY_IPS`**。

**断言守护**：`tools/smoke_ota_ratelimit.py`（端口 8127）。核心断言不是
「能拦住」，而是「**不会误伤**」：配额耗尽后，同一 MAC 复用仍须 200 且码不变。

## D44：激活码改「10 分钟严格有效 + 服务端锁定」，并补管理员解绑通道

用户 2026-10-20 拍板五条，本条目逐条记录落点与**代价**。

### 1. 有效期 10 分钟，过期换新码（取代 D42 的「一辈子一枚码」）

D42 当时刻意选了「一台设备长期一枚码 + 顺延有效期 + 24h 封顶」，理由是
10⁶ 空间经不起每 10 分钟建一行。**用户这次明确要求改回来**，理由是
「尽量避免撞库」，工程上成立：长期有效的码等于长期有效的凭据，一旦被
看到（拍照/录屏/旁人瞄一眼），攻击者有充分时间去撞。10 分钟把
「泄漏 → 可用」的窗口压到十分钟。

代价必须写清：一台设备一天换 144 枚（24h × 6 次/小时）。所以
`_purge_stale_codes()` 的保留期从 **1 天收紧到 1 小时**
（`_ACT_CODE_PURGE_GRACE`），否则 1000 台设备一周就能把 10⁶ 吃光。
保留 1 小时而不是立刻删，是为了让「刚过期就来输」的用户看到
「已过期，请在设备上重新获取」而不是更含糊的「不存在」。

### 2. 服务端锁定：同一台设备同一时刻只有一枚有效码

新增 `voice._retire_codes_for(db, mac, keep_id=None)`：把该 MAC 名下所有
**仍有效且未使用**的码置 `expires_at = now`（不是 `used = True` —— 后者
语义是「已被用于绑定」，拿它标记退役会让审计口径失真）。

三个调用点：
- 新建码成功后（换新码时旧码立即失效）；
- 绑定成功后（该设备名下不再残留任何可用码）；
- 已绑定设备每次打 OTA（第二道保险，防旧版本服务端或人工改归属留下的残留）。

### 3. 已绑定设备不再下发激活码、不允许重复绑定

- `ota_check` 已绑定分支**只回 `websocket` 段，绝不含 `activation` 段**；
- `POST /api/devices/{pk}/code` 对已绑定设备返回 **409**；
- `POST /api/device/activation-code` 对已绑定设备返回 `already-bound`
  （该接口要 device_token，而 token 只在绑定成功时签发 ⇒ 它必然已绑定，
  等于如实拒绝）。

### 4. 忘记用户名 ⇒ 邮件联系管理员 ⇒ 管理员后台解绑（唯一通道）

新增 `POST /api/devices/{pk}/unbind`（**仅管理员**，204）：
- 只清 `owner_id` / `bound_at`，**不删设备行** —— 真实诉求是「换个人来管」，
  不是「把这台设备从系统里抹掉」。删行会让老人正在吃的药提醒一起消失。
- 解绑后作废该设备残留码，设备下一轮 OTA（15s）重新显示激活码。
- 审计：`log.warning` 带 `device_pk / mac / 原归属用户 / 操作管理员 / 作废码数`。
- 前端：管理端设备表新增「解绑」按钮（仅对有主人的设备显示 + 二次确认）；
  用户端与 APP 增加求助文案，邮箱来自 `ELDER_SUPPORT_EMAIL`
  （新增只读接口 `GET /api/support-contact`，**不暴露其他配置**）。

### 5. 顺带修掉一个 P0：APP 端绑定全新设备必然失败

`bind_device` 原先在 `Device` 行不存在时要求 `payload.device_id` 非空，
否则 400「缺少设备标识」。但真实链路是：

    设备开机 → 打 /api/voice/ota → 服务端按 MAC 建**激活码行**（尚无 Device 行）
    → 家属在 APP 只输入 7 位码 → bind

而 APP 的 `doBind` 只传 `{code, alias}`（它**拿不到** MAC），全仓建 Device 行
的地方只有网页端「登记设备」表单与 bind 自己 ⇒ **只有先走网页登记的人能绑上，
纯 APP 用户一定卡在 400**。判据改为「这枚码知不知道自己是哪台设备的」：
码里带了 `device_id`（固件申领时写死）就足够建档。

### 6. 顺带修掉 MAC 口径分叉（R2/R3 的真实泄漏点）

同一台设备在系统里有两种写法：固件 `Device-Id` 头是 `aa:bb:cc:dd:ee:ff`，
`Device.device_id` 存量是 `aabbccddeeff`。原实现两处各用一种：

- `_find_device` 只做 `lower()` ⇒ 带冒号的请求匹配不到不带冒号的存量行
  ⇒ **已绑定设备被判成未绑定，照样下发激活码**（直接违反第 3 条）；
- 锁定按 `device_id` 做键 ⇒ 两种写法各持一枚，锁定在这台设备上失效。

新增 `app/macs.py` 作为唯一真源（`norm_mac` / `mac_variants`）：
入库与比较一律先归一化；清理存量时按两种写法分别作废。

**断言守护**：`tools/smoke_activation_ttl.py`（端口 8128，两阶段：
TTL=0 验「过期换新码」、TTL=10 验锁定/已绑定/解绑），其中一条专门断言
「网页按无冒号登记的设备，固件用带冒号请求时被认成已绑定」。

### 7. 残余风险：MAC 即身份（**v1 内无法封顶，需 v2 才能关闭**）

> 这一节是 `voice/__init__.py` 里「异地重签告警」那段代码所引用的
> 「D44 残余风险段」。**不要删**——它记录的是「已知未修」的正式接受，
> 删掉之后这条 P0 就会变成「没有决策记录的口头共识」，下次评审要从头吵一遍。

**现状**：`GET /api/voice/ota` 的已绑定分支只要 `owner_id is not None`
就**无条件现铸**一枚 `token_epoch` 正确的新 `device_token`。判据只有 MAC
（`Device-Id` 请求头），无鉴权、无挑战、读路径无限速。

**它意味着什么**：

- `token_epoch`（见 D44 §5 与 D45）让**已签出的旧 token** 失效 —— 这条已闭合，
  REST 与 WS 双侧都校验，`tools/qa_b_activation_gate.py` 有行为断言。
- 但**持有该 MAC 的一方**仍然可以直接换一枚新的。原主人的 APP 里存着这个 MAC
  （`BindOut.device_id`），所以「解绑 → 新家庭绑定」之后，原主人打一次 OTA
  就能拿到新 token，继续读**新家庭**的提醒与回执、继续开 WS 说话。

⇒ **口径必须写死**：解绑堵住的是 **stolen token**，不是 **MAC holder**。
「管理员解绑后原账户再也碰不到设备」**不成立**。

**为什么限速解决不了**（这条最容易写错，写错会让人以为已经缓解）：

- 枚举的定义就是「每请求换一个 MAC」，所以任何**按 MAC 计数**的限速器
  对枚举**永远不会触发**（它只能防「反复打同一台设备」= 单设备 DoS，是另一个威胁）；
- 唯一能约束枚举的是**按来源 IP 计数**，而它在生产反代下默认失效
  （`ratelimit.py` 未配 `ELDER_TRUSTED_PROXY_IPS` 时全站共用一个键）；
- 就算配了，也只是**抬高成本**（扫一个 OUI 从约 1.9 天变成 N 天），不是封顶。
  真要封顶需要全局 rps 桶，而它的下限被「全车队 15s 轮询」的合法负载顶住
  （1000 台 ≈ 67 rps），压不下去。

**结论**：限速只抬高枚举成本，**v1 内无法封顶**，根治必须依赖设备与服务端
共享密钥（activation v2 HMAC，`POST /api/voice/ota/activate` 当前直接返回 400
未实现）。

**为什么接受**：v1 固件没有共享密钥能力，改成 v2 需要固件与服务端**同时**
升级，会打断已部署设备（老人端不会自己升级）。在「现在能上线」与「等 v2
再上线」之间选前者，代价是这条风险保留到 v2。

**接受期限**：**v2 上线即关**。v2 落地时必须回来删掉本节，并把
`voice.ota_check` 的已绑定分支改成校验设备侧签名。

**当前缓解（只有可观测，没有阻断）**：

- `Device.ip` 记录最近一次取 token 的来源 IP，**变化时**打 WARNING
  （`设备 token 异地重签`）。正常家庭网络每天 0 条；前主人从自己家来续
  token 就是一条干净信号。
  ⚠️ **首轮必然静默**：该列在本版之前从没被写入过，存量行全是空串 ⇒
  第一次只记录、不告警。「部署后没看到任何告警」是预期，不是告警坏了。
- 该列原先是个**从不写入的死列**（只有 `home.py` 在读、恒为空），
  所以「前主人续 token」这件事在本版之前**没有任何痕迹**。

**给运营的一句话（不是给开发的）**：
解绑适用于**账号找回**，不适用于**设备转让**。把设备送给别人时，仅靠解绑
不能阻止原主人继续访问，必须等 v2。

## D45：把「解绑」做成真正的解绑——代次吊销、存量回填与热路径收口（2026-10-21）

D44 落地后安全复核对整条设备链路做了一次分层审计（L1~L9），本记录收口其中
**已修**的部分，并留下两条比具体修法更长期有效的方法结论。

### 1. 先说一条必须写死的元结论：**码长与安全无关**

这一轮反复有人（包括我）拿「10^6 够不够」来论证 7 位码的安全性。
**这个论证是错的，而且错得危险**，因为它会让人以为「码够长就安全」。

真实情况：激活码可以**按 MAC 从 OTA 端点免费领取**（`_ensure_activation_code`），
攻击者**不需要猜**。所以：

- 7 位 vs 13 位、Luhn 校验位增不增熵 —— 对这条路径**零影响**；
- 7 位该做，但理由是**可用性**（固件音表只有 `OGG_0..OGG_9`，字母会被静默
  跳过），**不是**「10^6 够用」；
- 真实攻击面是 **MAC 空间**（单 OUI 2^24，20rps ≈ 8.4 天），命中一台已绑定
  设备即得 365 天 `device_token`。见 D44 §7。

⇒ 后人请勿用「码空间够大」给 7 位背书，也**不要**用它去否掉 v2 HMAC
（v2 要解决的是「设备如何证明自己是设备」，不是「码有多长」）。

### 2. `token_epoch` 代次：为什么不做 token 黑名单

`device_token` 是无状态 JWT（365 天），签出去收不回来。管理员解绑后原家属
手上那枚仍然有效 —— 若之后有新家庭绑了这台设备，旧 token 会**直接读到新家庭
的提醒与服药回执**。「解绑若不能真正吊销凭证，就不是解绑。」

选**代次**而不是黑名单，理由三条：

1. 黑名单要为每一枚签出的 token 存一行，且必须随 token 过期清理 ——
   等于给「无状态」重新引入一张有状态表；
2. 校验点有两处（`deps.get_current_device` 的 HTTP 与 `voice.session` 的 WS
   握手），黑名单要在两处都查表，热路径多一次 IO；
3. 代次只是 `devices` 表上的一个整数，签发时写进 JWT 的 `ep`，
   校验时比一次整数 —— **零额外存储、零额外查询**。

**关键：两处校验缺一不可。** 只做 HTTP 不做 WS，等于「解绑后还能听老人说话」，
而这条路径**没有任何日志**，出问题也发现不了。QA 用变异测试验证过这一点：
删掉 `session.py` 里的代次校验后，HTTP 侧断言仍然绿、只有 WS 侧变红。

### 3. 存量回填：为什么判据是 `owner_id IS NULL AND token_epoch = 0`

补列带 `DEFAULT 0`，所以**所有**存量设备读出来都是 0；而老版本签出的 token
**根本没有 `ep` 声明**，校验端 `payload.get("ep", 0)` 缺省也是 0 ⇒ **0 == 0**
⇒ 老 token 全部继续通过。这批 token 有效期 365 天，而它们恰恰属于
「在本轮之前就被解绑过」的设备 —— 正是用户规则 4 最需要防住的那一批。

判据两个条件都在，各自回答一个独立问题：

- `owner_id IS NULL` —— 当前无归属（= 已解绑或从未绑定），这是 `unbind` 唯一
  会写出的「已解绑」状态；
- `token_epoch = 0` —— 代次从未被抬过。本轮之后的解绑都会 +1，
  所以这一条把「本轮之后才解绑」的设备排除在外，**不覆盖已经正确的值**。

⚠️ **不要简化成单条件 `owner_id IS NULL`**：那会让每次启动都 +1，
**所有设备的 token 在每次重启后集体失效**——比原来更严重的故障。
这条回填按铁律登记了 `patch_id`（`device_token_epoch_unbound_v1`），只执行一次。

### 4. MAC 查询：覆盖模型从「闭包」退化为「枚举」

`_find_device` 原先把列包进函数（`lower(replace(replace(device_id,':',''),'-',''))`），
**索引直接废掉**，而它处在 `GET /api/voice/ota` 这条**无鉴权、15s 轮询**的路径上
⇒ 每请求全表扫 `devices` = DoS 放大器。

改成 `device_id IN (mac_variants(mac))` 后索引可用，但**这不是等价替换**：

| | 旧写法（闭包） | 新写法（枚举 6 种） |
|---|---|---|
| 无分隔 / 全 `:` / 全 `-` × 全大写/全小写 | ✅ | ✅ |
| 混合大小写 `Aa:Bb:..` | ✅（`lower()` 逐字符折叠） | ❌ |
| 混合分隔符 `aa:bb-cc:..`、重复 `aa::bb..` | ✅ | ❌ |

**覆盖模型变了：从闭包退化成枚举。** 这是刻意的——枚举有可复核的上界，
闭包没有。6 种是从**写入路径的输出闭包**推出来的（固件 `GetMacAddress()`
统一冒号小写；网页表单手输统一写法统一大小写），不是"猜一些可能的值"。

⇒ 往 `mac_variants` 加写法之前先回答：**哪条写路径能产出它？**
答得出就加（"MAC 标签印成全大写" ⇒ 加，砍掉它就是一次真实回归）；
答不出就交给 `normalize_device_macs()` 收敛。

**回归是怎么发生的（值得记住）**：改造时只列了小写两种形态，
而旧代码的 `lower()` 是**刻意**用来容忍大小写的。于是
`AA:BB:CC:DD:EE:FF` 这种存量行两边都不等 ⇒ 已绑定设备被判成未绑定
⇒ 下发激活码。**性能修法把功能能力一起删掉了，而没有任何断言发现它**
（当时的断言输入全是小写，且断言自己还做了 `.lower()`）。

配套：`normalize_device_macs()` 把存量收敛成单一写法（Python 侧调 `norm_mac`，
唯一约束冲突时**只跳过冲突组、不自动合并**，且**不登记** patch_id 以便重试）。

### 5. 热路径三条纪律（都是「别在轮询路径上做无谓的事」）

| 位置 | 原来 | 现在 |
|---|---|---|
| `_retire_codes_for` | 每次轮询 2 条 UPDATE + 1 次 COMMIT，**全部匹配 0 行** | **读先行**：`SELECT ... LIMIT 1` 探一枚，无残留码直接 return，不进写事务 |
| 同上（写语句） | 按变体循环发 UPDATE（变体扩到 6 就是 6 条） | **单条 `IN`**，写次数与变体数解耦 |
| `Device.ip` | 死列（只读不写） | **条件写**：`cur_ip != prev_ip` 才写库并 commit |

规模感：1000 台设备，已绑定设备每 15s 一轮 ⇒ 原先每天约 576 万次空转写事务。
这些都在**无鉴权**端点上，攻击者并发刷就能让正常设备排队。

⚠️ 一条禁令（已写进 `_find_device` 的 docstring）：**禁止**在 `IN` 未命中时
回退到 `lower(replace(...))` 查询。miss 完全由调用方控制（随便报个假 MAC 就 miss），
回退等于把全表扫**无条件**暴露给无鉴权端点，比现状差一个量级。

### 6. 限速器：绑定成功不清 IP 键

`clear_bind_failures` 原先同时清 IP 键与账号键。原文理由是「绑定成功说明手里
有合法激活码，攻击者不可能靠撞中一次重置配额」——**这个前提不成立**：

攻击者可以**自造成功**：删掉自己的设备（他是 owner）→ OTA 按 MAC 领一枚码
→ 用这枚真码绑定 → 成功 → IP 桶清零。全程零猜测。

而「家属连续绑多台设备正需要清零」这条理由**本身也不成立**：
`record_bind_failure` 只记**失败**，每台都输对时桶里一个失败都没有，清不清一样。

⇒ 只清账号维。账号维挡的是「一个账号猛试别人的码」，成功一次说明这个账号
自己的码是对的，清掉合理；而账号可公开注册、量产，清它不损失防护强度。

### 7. 两条方法结论（比上面任何一条修法都更值得记住）

**（一）凡结论涉及「系统会做什么」，必须找到调用点；只看到定义不算核过。**

本轮为此白报了两条 P0：两名复核者各自只看了 `schema_patch.py` 的**补列 DDL**
就下结论（一个说"没有回填"、一个说"幂等可无条件跑"），而回填函数的实现与
`run_all()` 里的调用都在 300 行之外。**「已闭合」类结论尤其危险——它会让下一个
人不再去查**，错了代价最高。

同族事故还有一次：我写了 `normalize_device_macs()` 却忘了接进 `run_all()`，
函数在、索引建了、注册表也登记了——**唯独不会执行**。这类「静默未执行」
比没写更危险，因为 review 和冒烟都容易放过。

**（二）判据不能依赖它正在检验的那个机制。**

同一形状本轮出现三次：

1. 用 `SELECT ... WHERE device_id <> lower(device_id)` 去查「大小写脏数据」——
   在 MySQL 的大小写不敏感排序规则下**恒返回 0**，给出"没问题"的假阴性；
2. 用 SQL 的 `WHERE device_id != :v` 做归一化的更新守卫——SQLite 二进制比较
   会多计行数，MySQL ci 比较会**跳过更新**，同一段 SQL 在两种库上行为相反，
   且随后 `_mark_applied` 照常执行 ⇒ 迁移静默空转却标记成功、永不重试；
3. 冒烟里写 `d.device_id.lower().replace(":","") == mac.replace(":","")` ——
   两边都归一化，**服务端把大小写搞错时断言照样绿**。

⇒ 写断言/判据时先问：**这个判据本身依赖了什么？它是不是正好依赖了我要检验的
那个东西？** 是的话，换成硬编码期望值或与被测实现不同源的算法。

### 8. 断言守护

- `tools/smoke_schema_migrations.py`（新增，纯 SQLite 不起服务）：
  代次回填（已解绑抬到 1 / 已绑定不动 / 已抬过不重复）、MAC 归一化、
  **唯一约束冲突时零改动且不登记**、`norm_mac` 行为契约（硬编码期望值，
  与被测实现不同源）。
- `tools/qa_b_activation_gate.py`（QA 第二层独立验证，47 条）：
  R1~R5 全绿，含 **WS 握手侧代次校验**（含变异自检：删掉校验必须变红）。
- `tools/smoke_voice.py`：`1c` 原按 MAC 原值计数，归一化后恒为 0（**假红**），
  已改为按 `mac_variants` 计数。

## D46：品牌统一「小智」；提醒过期不补响、不谎报漏服（2026-10-21）

### 1. 称呼统一（用户需求第 4 条）

三处必须同名，否则老人喊的名字和听到的名字不是同一个：

| 位置 | 值 | 状态 |
|---|---|---|
| 唤醒词 | 「你好小智」（WakeNet `wn9_nihaoxiaozhi_tts`） | 2026-10-20 已回归上游 |
| 配网热点 | `XiaoZhi-XXXX` | 本次改（`wifi_board.cc:60`） |
| 服务端自我介绍 | 「你是「小智」…」（`voice/prompts.py` BASE_VOICE_PROMPT） | 本次改 |
| 平台预设角色 / 默认形象 | 小智（平台预设）／小智（默认） | 本次改 + 迁移 |

**⚠️ `XiaoZhi` 与上游 `Xiaozhi` 只差 Z 的大小写**，肉眼极易看错。这是按用户
明确要求实现的，但运维文档（烧录指南/架构设计/DEPLOY/user.html）都加了醒目提示。
若真机验收时出现「搜不到热点」，先查大小写，不要先怀疑固件。

**改名必须带迁移**，否则存量库永远显示旧名，而且 `_seed()` 的
`elif preset.name != PRESET_ROLE_NAME` 分支会**每次启动都打一条 warning**。
迁移判据三条同时成立才改名（`main.py` `_LEGACY_PRESET_NAMES`）：
`record_type == preset`（不是历史角色，否则会被改成全平台可见只读）、
`owner_id is None`（不是家属自建角色）、`name` 命中旧默认名（运营改过的不动）。
少任何一条都可能改到用户数据，而改名不可逆。

形象侧同理（`_LEGACY_AVATAR_NAMES`），但 **`eaf_pack_name` 保持 `xiaonuan`
不动** —— 那是素材包目录名，改了加载不到序列帧。

### 2. 提醒：过期不补响，也不谎报漏服（`reminder.c`）

评审（产品官 + 调查员）独立发现两个缺陷，都会让子女端收到**「老人漏服」的假告警**：

**(a) 过期项补触发。** 设备断电到 14:00 才开机，08:00 的药会在开机瞬间补响
「该吃降压药了」。这不只是体验问题 —— 老人补服后与次日晨药间隔过近，
低血压风险大于「少提醒一次」。

修法：超过 `ELDER_RMD_STALE_MIN`（60 分钟）直接判 `ELDER_RMD_SKIPPED`：
**不补响、不升级**，回执报 `ELDER_EV_SKIPPED`(4)。服务端
`EventState.SKIPPED` 早已存在且 `home.py` 已把它排除在「待服药」之外，
子女端看到的是「这次没提醒」而不是「漏服」。阈值取 60 分钟：比 15 分钟升级
阈值宽，容得下「重启/短暂断网后几分钟内补响」，又短到不会翻出半天前的提醒。

**(b) 升级计时基准错了。** 原判据 `(now_min - due) >= 15`，设备晚开机 20 分钟
就会在**响铃的同一个 tick 里**被判漏服 —— `set_state(PENDING)` 刚执行，
下一行就 `set_state(ESCALATED)`。改成按 `pending_since_us`（响铃时刻）计时。
该值在 RAM，重启后为 0，此时退回 `due` 基准：能走到那一步说明这条当天确实
响过（`fired_today` 位已落盘），判漏服是合理的。

> 教训同 D45 §7：**「15 分钟未确认」的语义必须是从响铃算起，不是从计划时刻算起。**
> 判据里出现 `now - due` 时，先问一句「due 是不是我想表达的那个起点」。

### 3. 未校时不再静默失效

时钟不可信（`< 2020-01-01`）时守卫会暂停触发，但原来**只打一条 ESP_LOGE**，
而老人看到的是正常的待机屏 —— 当天所有提醒一条不响却无人知晓。
现在每 30 分钟屏显一次「时间未校准，请连网」。

新增 `elder_ui_notice(text, emotion)`：**只屏显不发声**。与 `elder_ui_announce`
的区别是「安静地说状态」vs「有事得让他听见」；此刻多半离线，突兀的提示音
只会吓人。首次检测立即提示（用 `-1` 哨兵而不是 `0`，否则开机后要等 30 分钟）。

### 4. 未做 / 待验证

- **真机验证**：热点名（含大小写）、未校时屏显、过期跳过（需把设备时间拨到
  过去再拨回，或拔电 1 小时后开机）。
- **产品级硬件到位前**「断电+断网 → 时钟 1970」的窗口仍在，只是从「静默」
  变成「明示」。DS3231 接上后（`ELDER_RTC_ENABLE=y`）才真正闭环。

## D47：服务端 → 设备 MCP 工具通道（服药确认闭环）（2026-10-21）

### 问题：确认服药这件事，物理上没有入口

`elder_reminder_confirm()` 全仓**只有一个**调用点：`elder_bridge.cc` 的按键
回调。按键已从 GPIO0 迁到 GPIO11（原型期未接线），自研离线命令词也已随上游
回归删除。于是：

```
提醒照响 → 无人能确认 → 15 分钟升级 ESCALATED → 回执 ELDER_EV_MISSED
        → 子女端每条提醒都收到「老人漏服」
```

不是显示问题，是**每条提醒都会产生一条假告警**。D46 修掉的是「没响却报漏服」
（过期跳过），这条修的是「响了也没法确认」。

### 决定：建一条服务端 → 设备的 MCP 工具通道

设备本来就是 MCP server（`main/mcp_server.cc` 实现了 `initialize` /
`tools/list` / `tools/call`），服务端只是缺一个 client。补上之后：

```
老人说「我吃过了」
  → LLM 调 confirm_reminder 工具（tools.py）
  → session.call_device_tool() 下发 {"type":"mcp","payload":{...tools/call...}}
  → application.cc 的 mcp 分支 → McpServer::ParseMessage
  → self.elder.confirm_reminder 的 lambda
  → elder_confirm_pending_medicine() → ConfirmMedicine(idx, ELDER_CFM_VOICE)
```

### 三个必须记住的约束

**(a) JSON-RPC id 必须是整数。** 固件 `ParseMessage` 用 `cJSON_IsNumber(id)`
校验，字符串 id 会打一条 "Invalid id" 然后**直接 return** —— 服务端只会看到
超时，日志长得像「设备没响应」。`tools/test_mcp_confirm.py` 用「设备故意回字符串
id」反向钉死这条。

**(b) 确认方式要分 VOICE / BUTTON。** 原来 `ConfirmMedicine()` 硬写
`ELDER_CFM_BUTTON`。语音确认若也记 BUTTON，子女端无法区分「老人自己按的」还是
「跟小智说的」——事后复盘时这是关键信息。改成带 `method` 参数。

**(c) 同步/异步边界。** `execute_tool()` 是同步函数、跑在 `run_in_threadpool`
的工作线程里。要它发起 WS 往返，只能 `asyncio.run_coroutine_threadsafe` 把协程
投回原事件循环：
- 直接 `asyncio.run()` 会新建 loop，WS 绑在旧 loop 上，`send_text` 必抛
  "attached to a different loop"；
- 在工作线程里自旋等回包会死锁 —— 回包要靠原 loop 上的收包任务才会被处理。

### 已知限制（未修，写在这里免得下次当新 bug 查）

1. **断网期间响的提醒仍无法语音确认**（没有 LLM 可调）。此时升级成 ESCALATED
   并回执 MISSED 是**正确**语义（确实无法确认），但老人无法自救。
   产品级硬件接上 GPIO11 按键后由按键覆盖。
2. **重启会丢响铃时刻**（`pending_since_us` 是 RAM 值）。晚开机场景下若在
   响铃后又重启一次，升级计时退回 `due` 基准，可能提前判漏服。窗口很窄
   （晚开机 + 再次重启 + 15 分钟内），暂不为它改 NVS 格式。
3. `reminder.c` 的 `g` 状态**没有锁**，被提醒任务 / 按键任务 / 主任务（MCP
   工具回调走 `Application::Schedule`）三处并发访问。这是 D46 之前就存在的
   形态，本次只是多了第三个写者；单字节状态位撕裂的风险低，但「医疗级核心
   无锁」这件事本身该单独排期。

### 测试

- `tools/test_elder_host` 新增 **T13**（语音确认落 DONE、记 VOICE、此后不再报
  漏服）、**T14**（晚开机 50 分钟：要补响，但不得一响就判漏服）。
  T14 是补洞：把 `overdue` 判据改回 `(now_min - due) >= 15` 时它必须变红，
  而 T11-6（due 整点，差值 0）与 T12（走 SKIPPED 分支）**都抓不到**这个回归。
- 新增 `tools/test_mcp_confirm.py`（29 条断言）：用假 WS 把「下发 tools/call →
  回包 → 唤醒 Future → 翻译成 LLM 话术」三层一次跑通，含超时、字符串 id、
  并发串包、error/isError 各分支。

## D48：和风天气接入 —— 按需缓存，不拉全国（2026-10-21）

### 需求原话与它真正的约束

用户要求：「服务端定时任务把需要的城市天气提前拉到数据库，客户端请求时直接读
缓存，不再请求和风 API。**按需预热，不一次性拉全国**，只缓存用户真实查询过的
城市。平顶山 60 分钟内再有人查，直接返回缓存，不消耗 API 次数。」

这句话里藏着一条**计费红线**：和风按调用次数计费。「拉全国」= 一次几千次调用，
几轮就能把额度打光。所以「按需」不是优化项，是这条需求成立的前提。

用户随后明确：**不用 Redis，直接用 SQLite**。缓存落在 `weather_cache` 表。

### 决定

```
老人问「平顶山天气」
  → geo 缓存命中？（30 天）  否 → GeoAPI 一次 → 存
  → 天气缓存命中？（60 分钟）是 → 直接返回，**0 次上游调用**
  → 否 → 调和风 → 存 → 返回
```

四条性质，每条都有对应断言（`tools/test_weather.py`）：

| 性质 | 断言 |
|---|---|
| 60 分钟内重复问不花钱 | T4-4：问 11 次只能产生 1 次上游调用 |
| 冷门城市永不调用 | T6-3：预热只刷新最近 24h 被问过的城市 |
| 上游挂了给旧数据 | T5-1~4：`source=stale` + 话术带「稍早」 |
| 预热不新增查找类调用 | T6-4：预热不得新增 GeoAPI 调用 |

### 三个不显然的设计选择

**(a) 过期行不删，只不再命中。**
它是「需求记录」—— 预热任务靠 `last_hit_at` / `hits` 判断该续谁。到点就 DELETE
的话，「按需预热」会退化成「每次冷启动」，缓存等于没有。真正清理交给
`purge_stale`（保留 7 天），由预热任务顺带执行。

**(b) `payload` 存上游**原始** JSON，不存口语化结果。**
两个理由都会真实发生：文案几乎一定会改（老人听不懂「体感 33.6 度」），改文案
不该顺带清缓存逼所有城市重新计费；和风返回的字段远多于当前用到的，将来要用
紫外线/能见度，直接读老缓存即可。

**(c) 预热刷新 `count_hit=False`。**
否则「预热自己把热度刷上去」，冷门城市永远沉不下去，`hits` 排序失去意义。

### 踩到并记住的坑

1. **新版 API 成功响应没有 `code` 字段**。旧版 `/v7/*` 有 `{"code":"200"}`，新版
   `/weather/v1/*` 直接返回 `metadata`/`condition`，**只有出错时才有 code**。
   按 `code=="200"` 判成功会得到「天气永远查不到，但日志一切正常」。
2. **`iss` 与 `sub` 不能搞反**：`iss`=开发者 ID（Q 开头 10 位），`sub`=项目 ID。
   反了就是 401，而和风的 401 不会告诉你是哪个字段错了。
3. **JWT 的 `kid` 必须是标着 JWT 的那条凭据**，不能填 API KEY 的凭据 ID。
4. **PyJWT 会自动补 `typ:JWT`**。和风文档说「若包含 typ 必须为 JWT」，我们的值
   合规，不必刻意删掉。
5. **测试里 `make_cfg` 必须给非空私钥路径**，否则 `configured=False`、`get_now`
   直接短路返回，用例会「安静地通过却什么都没测到」（第一版 T4/T5/T6 全挂在
   `peek()` 返回 None 上）。
6. **城市名归一化的目标是「别切坏」，不是「完美收敛」**。因为缓存键最终落在
   GeoAPI 返回的 `location.id` 上，名字只是查 ID 的输入。不同说法各查一次 geo
   是可接受的（每城市 30 天一次），切出「维吾尔」这种查不到的词才是事故。
   `_ETHNIC_FRAGMENTS` 就是为此存在的保护。

### 私钥放哪

**项目目录之外**（仓库会推 GitHub）：`G:/workbuddy/qweather-ed25519-private.pem`。
代码默认去**仓库父目录**找同名文件，而不是写死 `G:/workbuddy` —— 写死盘符的
代码换台机器就废，还会把本机路径泄进仓库。容器部署用
`ELDER_QWEATHER_PRIVATE_KEY`（PEM 全文）覆盖。

### 已知限制

1. **首次问一个新城市要两次往返**（geo + 天气）。想消掉只能提前预热该城市，
   但那违背「不拉全国」。
2. **「俺们这儿」这类指代**靠 LLM 补城市名，补不出来会反问「您说的是哪个城市」。
   不做别名表（「帝都→北京」写不完，写几条反而给人「已经处理过了」的错觉）。
3. **老人问「明天带不带伞」依赖降水概率**。和风偶尔有 `probability` 缺失的
   情况，此时只看天气现象文字（`_umbrella` 的两条判据是「或」关系）。

## D49：语音链路的三处「老人听到的声音不对」（2026-10-21）

### 现象原话

用户真机验收后反馈三件事，按严重程度：

1. **「回复了一句『老人查天气，我要调用……』，没有直接告诉我天气，而是说他要干什么」**
2. **「声音断断续续，杂音、破音」**
3. **「经过很久很久之后才回复」**

第 1 条是**确定性 bug**，能只靠读代码定位并修死。第 2、3 条需要实测数据才能
定论，所以本轮的处理方式不同：**修掉能修的，剩下的把"测量手段"补上**。
把猜出来的结论写进文档比不写更糟 —— 后人会照着错误的方向去改。

### 一、工具轮的规划语被念出来了

**根因**：`_chat_round` 把每一轮 LLM 的 `text` 增量直接 `push_text` 给播报器。
而 function calling 的一轮里，模型常常先写一句"我打算做什么"再发 `tool_calls`
—— 那句是**模型的思考草稿，不是给老人的回答**。它被逐句合成、念了出来。

`llm_gateway.ChatResult` 的注释里其实写着这个设计意图：
「`text` 与 `tool_calls` 可以同时非空（"我帮您记一下" + 工具调用），语音链路会
把这段文本当成确认语先念出来」。**这个假设对"我帮您记一下"成立，对
"老人查天气，我要调用 get_weather" 不成立。** 两者在协议层长得一模一样，
区别只在语义。

**为什么不用「整轮扣住不播」**：那要等模型把整段说完才知道有没有 tool_calls，
首句延迟会多出整整一段生成时间 —— 而第 3 条投诉就是"太慢"。逐句安检是 O(1) 的，
**不增加任何延迟**。

**三层防御**（纵深，不是冗余）：

1. `prompts.BASE_VOICE_PROMPT` 加硬约束：不许说"我要查一下"、不许提工具/函数/
   参数/JSON、不许出现英文单词、不许用第三人称说"老人"。
2. `session._speech_block_reason()` 逐句安检，四类特征：
   - `code_ident`：snake_case（`get_weather`）或 camelCase（`createReminder`）
   - `tool_talk`：调用/工具/函数/接口/参数/JSON/API/token
   - `third_person`：`^老人 + 动作动词`
   - `self_plan`：同句里"老人…"和"我要/我需要/我先"并存
3. 整段都被拦时，改说 `UNSPEAKABLE_REPLY_FALLBACK`（"这个我一时没说明白，
   您再问一遍，我重新查"），并且**把历史里的 reply 也换成兜底话术** ——
   留着原文，模型下一轮会照着学。

**刻意不拦的东西**（误伤比漏拦更贵，会直接让老人听不到正常回答）：
`PM2.5`、`3.5 度`、"我帮您记一下"、"我查查啊"。测试 T1 里这四条是**应放**
用例，改正则时它们必须先绿。

### 二、流式路径从不 flush 缓冲区尾巴（静音 bug）

`_ReplySpeaker.push_text` 只切"带句末标点的完整句"，最后一段没有 `。！？`
的文本留在 `_buf` 里。而 `_run_turn` 的成功路径**从来没调用过 `flush_rest()`**
—— 只有非流式兜底和工具轮数用尽两条降级路径调了。

后果：模型回一句"今天晴，十四度"（不带句号），老人听到的是**彻底静音**，
而 `finish()` 照常打日志「播报完成（1 句，音频已发）」。**假绿日志**。

两个 bug 叠加，正好等于用户听到的："一句莫名其妙的自言自语，然后没声音"。

修法：成功路径在 `finish()` 之前无条件 `flush_rest()`；同时给纯标点尾巴
（只剩一个"。"）加了 `_PUNCT_ONLY` 短路 —— 那种片段送 TTS 会念出怪声，
而且**不能计入 `dropped`**（否则会误触发"整段都不可播"的兜底话术）。

### 三、TTS 返回体格式：杂音/破音最经典的两个成因

原防御只认 `RIFF`（wav）和 `{`/`[`（JSON 错误体）。漏掉两类，而这两类
**听感就是"杂音 + 破音"**：

| 厂商实际返回 | 原行为 | 听感 |
| --- | --- | --- |
| mp3 / aac（无视 `response_format: pcm`） | 字节被当采样点 | 持续沙沙声 |
| **32-bit float PCM**（不少推理框架的默认输出） | IEEE754 位模式被当 int16 | 沙沙声 + 爆音，而且很响 |

新增 `_sniff_audio()` 按魔数判别（RIFF/ID3/MPEG 同步字/ADTS/OggS/fLaC/JSON），
`_looks_like_float32()` 用统计判据（每 4 字节当 float 读，落在 [-1.5,1.5] 的
比例 >95% 即判定），压缩格式用 PyAV 解码并重采样到 24k/mono。

**float32 判据为什么可靠**：真实 int16 语音对拼成 4 字节后，float 解释的指数位
是随机的，落在 [-1.5,1.5] 的比例约 **1%**；真 float32 音频是 **100%**。
差两个数量级，没有边缘地带。测试里专门有一条"真实 int16 语音不能被误判"
—— 误判会直接把正常音频毁掉，比漏判更严重。

每种异常格式**每进程只 WARNING 一次**（`_SNIFF_LOGGED`），否则每句话刷一条。

### 四、时延：先让"慢在哪"可测量，再谈优化

原来的 `meta.llm_ms` 是从发起 LLM 到循环结束的墙钟时间，里面混着**工具执行**
和**播报阻塞**（`push_text` 是 await 的，TTS 合成期间 LLM 流读不到下一个增量）。
看这个数永远分不清谁慢。

拆成六个字段进 `Interaction.meta` 和一行 grep 得出来的日志：

| 字段 | 含义 |
| --- | --- |
| `asr_ms` | 识别整段上传往返 |
| `ttft_ms[]` | **每轮**"发出请求 → 第一个字到"（模型快慢的真指标） |
| `round_ms[]` | 每轮厂商 HTTP 往返（`ChatResult.elapsed_ms`） |
| `tool_ms` | 工具执行累计（含设备 MCP 往返） |
| `tts_first_ms` | 从 LLM 开始到**第一帧音频发出**（老人实际等待时长） |
| `tts_ms` | TTS 合成累计（串行，直接累加进总时延） |

### 五、「断断续续」：加了判决书，但没下结论

固件侧事实（读代码确认，非推断）：`OPUS_FRAME_DURATION_MS = 60`（与服务端一致），
`MAX_DECODE_PACKETS_IN_QUEUE = 40`（2.4 秒缓冲），
`MAX_PLAYBACK_TASKS_IN_QUEUE = 2`（120ms）。

每帧承载 60ms 音频，所以**服务端相邻两帧间隔 > 60ms 就意味着设备那一段没声音可播**。
新增 `max_gap_ms` 记录帧间隔峰值，超 60ms 直接打 WARNING：

- 打了 ⇒ 问题在服务端（TTS 分片慢/上游卡顿）
- 没打而老人仍觉得断续 ⇒ 问题在设备侧（OpusCodecTask 被抢 CPU 导致 I2S 欠载，
  听感是咔哒声 + 掉字；`audio_service.cc:87` 的注释记录过同类 CPU 饥饿事故）

**没有这个数，两边都只能靠猜。** 这是本轮唯一"故意不下结论"的地方。

### 本轮明确不做的事

1. **不改固件音频缓冲**（`MAX_PLAYBACK_TASKS_IN_QUEUE` 2→6）。听起来像显然的
   改进，但没有实测数据支撑，而在真机上动音频缓冲、又无法当场验证，风险
   高于收益。等 `max_gap_ms` 的数据出来再决定。
2. **不做 TTS 流水线预取**（第 N+1 句与第 N 句并行合成）。这是消掉句间空隙
   的正解，但要重写 `_ReplySpeaker` 的并发模型（协议时序、abort、异常都要重排），
   在还没有测量数据时做这件事属于盲改。
3. **不解耦 `push_text` 对 LLM 流的阻塞**。同上：先确认它到底占了多少时间。

## D50：音频下行节流器 —— 断续与响应慢是同一个根因（2026-10-22）

> 承接 D49。D49 说「断续没下结论、三条明确不做」，本轮把其中两条做了：
> 节流器落地、`push_text` 与 LLM 流的阻塞被解开。第三条（TTS 预取流水线）
> 仍然不做，理由见文末。

### 一、根因：一个"能发多快发多快"同时制造了三个症状

D49 把「断续」和「响应很久」当成两个问题分别记账。读上游
`xinnan-tech/xiaozhi-esp32-server` 的 `core/utils/audioRateController.py`
之后确认：**它们是同一个根因**——音频帧由 `await ws.send_bytes()` 直接发，
没有任何节流：

1. **断续**：帧间隔完全取决于 TCP 反压。设备 60ms 播一帧，我们 5ms 灌完
   50 帧，然后停下来合成下一句（几百 ms 到数秒）。D49 加的 `max_gap_ms`
   在真机上量到的就是这种"灌一批、停一下"。
2. **响应慢的一半**：发送是在 `push_text` 里 await 的，而 `push_text` 在
   LLM 流式读取循环里被 await。socket 一发不出去（设备读得慢 / 反压），
   下一个 LLM 增量就读不到 —— 老人等的那几秒里，很大一部分不是在等模型，
   是在等设备把上一批音频收走。
3. **`tts stop` 抢跑的风险**：一旦引入节流（异步排空），`finish()` 不等队列
   就把 stop 发出去，会插到音频前面（每句话最后几个字被吃掉，日志全绿）。

### 二、做法：照上游实现虚拟播放时钟

新增 `server/app/voice/audio_pacing.py`（`AudioPacer`），语义：

- **第 n 帧的计划发送时刻 = `_t0 + n × interval`**，`_t0` 是第一帧真正发出的
  时刻；某帧晚发**不追发**（不 burst），下一帧仍按节奏走，累积误差被消掉。
- 前 5 帧（`PRE_BUFFER_COUNT`）不等时钟直接发 —— 只为了压首句延迟。
- 控制消息（`tts start` / `sentence_start` / `llm emotion` / `tts stop`）走
  `add_json`，立即发、不占播放时间，且与音频帧**共用一条 FIFO**，
  顺序因此有保证（这正是修掉症状 3 的机制，不需要额外的锁或序号）。
- 发送在独立协程里；句间队列排空时把时钟原点回拨到当前虚拟播放位置，
  设备不会先播完积压音频再被时钟追上（听感是跳段）。

`_ReplySpeaker` 接入后：`push_text` / `flush_rest` 只入队就返回，
`finish()` 先 `wait_idle(timeout=60s)` 再发 stop。真机链路因此从
"合成一句 → 灌一批 → 停下合成下一句"变成"边合成边按 60ms 一帧放"。

### 三、三个"不许静音"的防线（本轮真正的难点）

节流器一旦失灵，症状是**老人什么都听不到而服务端一声不吭**——本项目里
最贵的那类故障。三条防线，每条都有一个对应的、变异验证过的断言：

| 防线 | 不做的后果 | 断言 |
|---|---|---|
| `_run` 里 popleft 之前再查一次队列 | 等播放时钟时协程在睡觉，`reset()`（abort）可能把队列清空 → 空 deque 上 `popleft` 抛 `IndexError` → 被外层 `except Exception` 吃掉 → 发送协程死掉 → 之后每帧堆在队列里而 `wait_idle` 立刻返回 → **全程静音、日志全绿** | `test_audio_pacing` T8 |
| 发送回调抛异常后 `_ensure_running()` 自愈；连续失败 3 次才置 `broken` | 一次 socket 抖动就永久静音；或者每帧重启一次协程变成风暴 | `test_audio_pacing` T9 |
| `finish()` 必须等排空；`broken` 时把 `_tts_ok` 置 False | `tts stop` 插到音频前面；或音频通道已死却照写"音频已发" | `test_speech_guard` T7 |

⚠️ `add_audio` / `add_json` 在 `broken` 时**直接返回、不动 `_drained`** ——
否则 `wait_idle` 会去等一个永远不会再跑的协程，把整轮会话挂死
（T9 第一版就是这么挂住的，`timeout 40` 才暴露）。

### 四、埋点：把"慢在哪"拆到能定位

D49 的 `ttft_ms` 只按**文本增量**记，纯工具调用轮一个 text 都没有
（`tool_calls` 只在 done 事件里给）⇒ 天气问句的工具轮时延整段消失，
日志里 `ttft=-`。改成**第一个事件**（不分类型）就记。新增
`积压峰值`（`tts_max_pending`）＝ 节流队列里待发帧数的最大值，它回答
"最后一句话为什么晚"（N 帧 ≈ N×60ms）。

帧间隔 WARNING 门限从 D49 的 60ms 改成 **3 帧（180ms）**：asyncio 的 sleep
粒度（Windows 约 15ms）与 TTS 分片到达节奏合起来，1~2 帧的抖动几乎每轮都有
（真机稳态 70~90ms）。拿 60ms 当门限只会每轮报警，真事故被埋掉 —— 那是
日志噪音，正是用户明确要求消掉的东西。

### 五、真机/冒烟实测（`smoke_voice` 144 过 / 0 败 / 2 跳过）

```
首句延迟（listen stop → 第一帧）= 373ms   <  LLM 整段 450ms
                                       <  第一句 TTS 合成完 534ms
时延 asr=70ms ttft=[168] round=[1010] tool=0ms 首帧=286ms tts=841ms
     帧间隔峰值=89ms 积压峰值=29帧 总=1084ms 轮数=1
打断（4 句回复中途 abort）：实际播出 1 句，随即回 listening
```

- 首句延迟仍然远小于整段 LLM / 整句 TTS ⇒ 流式没被节流拖慢
  （前 5 帧预缓冲生效）。
- 打断只播 1 句就停 ⇒ `_on_abort` 的 `reset()` 立刻作废了队列里的帧。
- 积压峰值 20~29 帧（1.2~1.8s）说明**最后一句话会晚 1 秒左右** ——
  这是节流的固有代价，换来的是不依赖设备侧 2.4s 缓冲、不受反压影响。
  设备 `MAX_DECODE_PACKETS_IN_QUEUE = 40` 本来也吃得下 29 帧，所以这一条
  记下来、不optimize。

### 六、本轮仍然不做的事

1. **不做 TTS 流水线预取**（第 N+1 句与第 N 句并行合成）。这是消掉句间
   空隙的正解，但要重写 `_ReplySpeaker` 的并发模型（协议时序、abort、
   异常全要重排），而现在的数据表明句间空隙本来就不大（稳态帧间隔 70~90ms，
   且主要来自 asyncio 粒度而不是供给不足）。等真机上出现 > 180ms 的
   WARNING 再做。
2. **不改固件音频缓冲**。同 D49：没有实测数据支撑，风险高于收益。
3. **不下"断续已解决"的结论**。本轮修掉的是服务端能修的部分（帧间隔不再
   取决于反压）。若真机上 `帧间隔峰值` 一直正常而老人仍觉得断续，
   下一步查设备侧 I2S 欠载（D49 第五条）。

## D51：本地 ASR / 向量化做成"选中即用"的预置，而不是又一个 endpoint

- **轮次**：第 51 轮（2026-10-22）
- **背景**：用户在 Docker 服务器上部署了本地 FunASR/SenseVoice（8082）与
  FastEmbed/bge-small-zh-v1.5（8080），要求"作为 AI 接口模型提供商的可选项
  存在，下拉选中本地 ASR、向量化模型时不需要填写其他信息，直接保存就能用"。
- **结论**：新增两个 `api_style`（`local_asr` / `local_embed`）与两条
  平台预置，**保存时归一化**（`providers._normalize_local_service`）补齐
  kind / endpoint / model / provider、清空 api_key、给本地档超时。
  "只传 name + api_style"即可保存并使用。
- **为什么必须单独立风格而不是塞进 `openai_compatible`**：两条本地协议与
  OpenAI 兼容**毫无共同点**——`POST {endpoint}/asr` 是 multipart 且没有
  model/language/key，`POST {endpoint}/embed` 用 `input`/`texts` 而不是
  OpenAI 的 `/embeddings` + `model`。硬套的后果是 404/400 且报错指不到真因，
  正是本项目在 TTS 侧反复吃过的亏（见 `_tts_dispatch_style` 的判据顺序纪律）。
- **边界（硬性）**：
  1. **归一化必须 create/update 共用同一个函数**。两处各写一遍，迟早出现
     "新建能直接保存、再编辑一次反而丢默认值"的漂移。
  2. **默认 endpoint 是 127.0.0.1**，只对"模型与助手同机同 netns"成立；
     Docker 里这不是默认情形，`DEPLOY.md §1.12.2` 给出三种改法。字段必须
     保持可编辑——默认值只是省一次键盘，不是锁定部署形态。
  3. **`api_key` 一律清空**，不因"管理员可能想备注点什么"而保留：本地协议
     没有鉴权头，带着一个谁也想不到来历的 Bearer 头只会让下一次换实现时
     多一个小时的排查。
  4. **`model` 只是展示名**。服务端按自己加载的 gguf / ONNX 模型工作，
     换模型要改模型服务的加载配置，不是改这一栏。
  5. 本地 ASR 的**协议报文细节不在 HTTP 层冒烟里验**（没有 ASR 调用入口），
     由 `smoke_voice` 第 15 组端到端覆盖；`test-voice` 的 ASR 分支仍然
     **不真调**（要真实录音），这条边界不许为"测试好看"而破。
- **代价/已知边界**：
  - 本地模型是串行的，高并发场景延迟 = 排队 × 单次（DEPLOY §1.12.4）。
  - 换不同维度的 embedding 模型后旧记忆语义检索自动失效（维度不符不参与
    计算），不报错、只是召回变差——已写进文档，不自动重建。
  - 前端「平台」下拉切到预置表之外的服务时，会清掉残留的 `local_*` 风格
    （否则后端按本地协议发请求，症状是"配了 Ollama 却连 8082"）。

## D52：语音调音量 / 亮度 —— 设备能力必须代理到设备（2026-10-25）

- **轮次**：第 52 轮（2026-10-25）
- **背景**：用户报「语音无法变更设备的音量大小、屏幕亮度」。老人说「声音
  大一点」，模型只会道歉。
- **根因**：不是设备不会，是**服务端没告诉模型这两个能力存在**。
  - 设备侧早就有了：`main/mcp_server.cc` 的 `AddCommonTools()` 注册了
    `self.get_device_status` / `self.audio_speaker.set_volume` /
    `self.screen.set_brightness`（仅当 `board.GetBacklight()` 非空），
    本板 `lichuang_dev_board.cc:295` 返回非空 `PwmBacklight`，所以亮度工具
    确实注册了。
  - 服务端 `voice/tools.py` 的 `TOOL_DEFS` 只有 7 个工具，**没有一个**和
    设备硬件有关。LLM 的 tools 字段里没有它，就永远不会调它。
- **结论**：在 `TOOL_DEFS` **末尾追加**三个工具，走已有的
  `device_call` 通道（D47 建的那条）：

  | 服务端工具 | 固件 MCP 工具 | 参数 |
  |---|---|---|
  | `set_volume` | `self.audio_speaker.set_volume` | `volume` 0-100 |
  | `set_brightness` | `self.screen.set_brightness` | `brightness` 0-100 |
  | `get_device_status` | `self.get_device_status` | 无 |

  **固件零改动**，存量设备立刻生效。
- **为什么 `set_volume` 同时收 `level` 和 `delta`**：老人不会说「音量调到
  50」，只会说「大点声」。`level` 是绝对值（子女在 App 里会用），`delta`
  是相对量。相对量**必须先读 `self.get_device_status` 再算**——猜当前值的
  后果是老人越喊「大点声」声音越小，他会以为设备坏了。读不到当前值就如实
  让老人说个数字，不许瞎猜。
- **边界（硬性）**：
  1. **上限 100 / 下限 0 必须服务端自己夹**。固件
     `Property("volume", Integer, 0, 100)` 的 `set_value<int>` 带范围检查，
     超范围直接 `throw std::invalid_argument` → 回 error，等于"调不动还没提示"。
  2. **超时 2.0 秒，不照抄 `confirm_reminder` 的 3.0**。这两个回调在固件里
     只是一句 `codec->SetOutputVolume()` / `backlight->SetBrightness()`，
     毫秒级；等超过 2 秒就是链路真出问题，早点失败让 LLM 换话术，别让老人
     对着"嗯……"干等。
  3. **`bool` 必须挡在 `_coerce_int` 外面**。Python 里 `True` 是 `int` 的
     子类，不挡就会被转成 1 —— 老人说「调大点」音量变成 1，是最刺耳的那种 bug。
  4. **`Unknown tool` 判成「不支持」而不是「失败」**。没背光的板子固件根本
     没注册 `self.screen.set_brightness`，这时要让模型一句话说明白、**不要
     让老人反复重试**。
  5. **`get_device_status` 的 text 是 JSON 字符串，要再 `json.loads` 一次**。
     固件 `McpTool::Call` 对 `std::string` 返回值直接塞进 `content[0].text`，
     而 `WifiBoard::GetDeviceStatusJson()` 返回的正是 JSON 文本。这一步写错
     的现象是"字段全是 None"，不报错。
  6. **只把 volume / brightness / battery 喂给模型**，不整段转发。原始 JSON
     里还有 `ssid` / `rssi` / 芯片温度，模型很可能把「rssi -60」念出来。
  7. **静音（volume=0）之后不能再"自然回应老人"**——我们自己的 TTS 也听不见了。
     这条要单独给话术，让模型只留一句字幕。
  8. **工具一律追加在末尾**（同 D47）：插在中间会让 `tools` 字段整体位移，
     prompt 前缀缓存全失效。
- **代价**：`TOOL_DEFS` 从 7 个变 10 个，每次请求多约 1KB 工具定义；
  相对量要两次往返（局域网各 50~150ms），可接受。

## D53：管理端派生量必须写在 `computed` —— 一次「所有类型都填不了模型名」的事故（2026-10-25）

- **轮次**：第 52 轮（2026-10-25）
- **背景**：用户连续两次报「服务端 AI 接入配置不能填写模型名称」，第二次
  补充「所有接入模型类型都不能填」，并说「点自定义接入点没有响应」。
- **第一次修错了**：只改了 `modelLocked()`（让它只对 TTS 上锁），没发现
  **整组派生量都不在 `computed` 里**。这是"修症状不修根因"的典型，用户
  复报就是最直接的证据。
- **根因**：`index.html` 有 17 个派生量（`vendorInfo` / `providerPreset` /
  `activePreset` / `presetModelDefault` / `modelHidden` / `modelFromPreset` /
  `modelLocked` / `endpointFromPreset` / `endpointLocked` / `apiStyleStorable` /
  `apiStyleHidden` / `apiStyleLocked` / `localService` / `showEndpoint` /
  `showApiKey` / `vendorVoices` / …）写在 **`methods:`** 里，而模板是**当值**用的
  （`v-if="!modelHidden"`、`:disabled="modelLocked"`）。Vue 3 里方法不带括号
  就是函数对象，**恒为真**，于是：
  - `v-if="!modelHidden"` → `!函数` → 恒 false → **模型栏永不渲染**（所有类型都填不了）；
  - `v-if="!apiStyleHidden"` → 恒 false → 「厂商 API 风格」栏永远隐藏；
  - `apiKeyHint` 里 `if (this.localService)` → 恒真 → 永远返回「本地服务没有密钥这一说」；
  - `applyPreset()` 里 `const p = this.activePreset` 拿到函数 → `p.endpoint` /
    `p.model` / `p.api_style` 全是 `undefined` → endpoint 被赋 undefined →
    **「改成自定义地址」点了没反应**。
- **结论**：整块搬进 `computed`（26 个 key），并立一条判据：
  **模板里当值用 → `computed`；只有事件处理器才进 `methods`**。
- **门禁**：`tools/smoke_frontend_hygiene.py` 新增 **L1b**，扫 `v-if` /
  `v-else-if` / `v-show` / `v-model` / `v-for` / `:prop` / `v-bind:` / `{{ }}`
  的**值位**，命中「名字定义在 `methods:` 里」就红。豁免三种合法写法：后接
  `(`（显式调用）、前接 `.`（成员名）、前后同时是 `(`/`,` 与 `)`/`,`（作为
  回调传给别的方法，如 `list.map(labelOfUsage)`）。**不含 `@event` / `v-on:`**
  ——那里写方法名是正确用法。
- **门禁有效性已验证**：用修复前的提交 `6dc61eb` 跑同一条规则命中 14 个，
  修复后命中 0 个。新门禁必须做过"对旧版本会红"的验证，否则只是装饰。
- **顺带**：两个入口页的 `FileResponse` 补上
  `Cache-Control: no-cache, must-revalidate`。原先只有 `etag` /
  `last-modified`，浏览器按启发式规则自己缓存，换版后用户可能一直看到旧页面
  —— 排查时极容易误判成"镜像没更新"。用 `no-cache` 而不是 `no-store`：
  页面没变仍是 304，不重传 160KB。

## D54：唤醒后补一句语音应答 —— 没有反馈，老人就会反复喊（2026-10-25）

- **轮次**：第 53 轮（2026-10-25）
- **背景**：用户要求「使用唤醒词『你好小智』之后，要用语音进行响应『你好，称呼，
  要聊点什么？』，避免用户以为没有唤醒而重复唤醒」。
- **先确认了一个事实**：这不是"锦上添花"，是**当前真的有洞**。
  本板 `sdkconfig` 里 `CONFIG_SEND_WAKE_WORD_DATA=y` ⇒ 固件走
  `application.cc` 的 `SendWakeWordDetected` 分支，而那句「叮」
  （`OGG_POPUP`）写在 `#else` 里，**压根不会播**。所以老人喊完唤醒词，
  设备一声不响，直到 LLM 答完才有声音 —— 他当然会以为没唤醒。
- **结论**：在 `_on_listen` 的 `detect` 分支排一个**延时应答任务**，
  说一句 `你好，<称呼>，要聊点什么？`，走 `_speak_reply`（固定话术通道，
  不进 LLM、不计 token、不写历史）。
- **三个刻意保守的取舍**（核心都是"宁可少说一句"）：
  1. **延时 900ms 再开口**。老人常常一口气说「你好小智，今天天气怎么样」，
     唤醒词只是这句话的开头 —— 立刻应答会把后半句吃掉，逼他重说，
     比不回应更烦人。
  2. **开口前再确认一次没人说话**，口径是 `_ms_since_loud`（距最后一个
     高能量帧多少毫秒）。**不能用 `_speech_ms`（累计语音量）**：唤醒词
     自己的尾巴也算累计值，用它判会永远跳过，等于功能从不上线。
  3. **读称呼是一次真实 `await`，之后必须再判一次**。期间可能有
     `listen stop` 把 state 推成 thinking；这时候再开口就会和这一轮的 TTS
     **抢同一条下行音频通道** —— 两路帧交错，老人听到的是破音。
     第二次检查到 `_speak_reply` 之间不许再出现 await（`_speak_reply` 在
     第一个 await 之前就把 state 置成 speaking，因此是原子的）。
- **称呼从哪来**：唯一来源 `memory.persona.tone_profile` 的
  `effective.address`（它内部已处理「人工覆盖 > 统计值」的优先级，
  这里不许再算一遍）。读不到就念无称呼版 `你好，要聊点什么？`，
  **绝不编一个**。「您 / 你」这类代词不套进句式（「你好，您，要聊点什么？」
  是病句），「您老」保留。长度在读取和出口各夹一次 16 字。
- **边界（硬性）**：
  1. 只认 `detect`，**不认 `listen start`** —— 后者每轮都发，认它就是复读机。
  2. 任何异常都吞掉：一句寒暄失败绝不能影响这一轮对话。
  3. 连续两次唤醒只留一个任务（旧的取消），不能两个一起开口。
  4. 三个旋钮全部走环境变量，`ELDER_VOICE_WAKE_GREET=0` 即完全回到旧行为，
     **现场嫌吵不需要回滚镜像**。
- **门禁**：`tools/test_wake_greet.py`（32 条，纯内存 + 临时库，不占端口），
  已进 `server-ci`。第 1 组（接线）与第 4 组（抢通道防护）做过**变异验证**：
  删掉 `detect` 里的接线 → 31/1 红；删掉第二次跳过检查 → 31/1 红；
  还原 → 32/0 绿。
- **代价 / 已知边界**：
  - 应答本身占 1.5~2s。这段时间在 `auto`（设备 AEC 关）模式下麦克风是关的，
    老人若恰好在这 2s 里开口，那句话会丢。设备 `CONFIG_USE_DEVICE_AEC=y`
    ⇒ 实际走 realtime 模式，麦克风不停、有 2s 打断宽限期兜着，风险可接受。
  - 唤醒应答会推进 `_speaking_started_at`，等于把 F2 打断宽限期重置一次。
    这是可接受的：老人真要抢话，宽限期过后照样能打断。

## D55：编译成功 ≠ 功能编进去了 —— 一次全绿的假绿（2026-10-26）

**现象**：DS1302 时钟 + WS2812 彩灯的驱动代码提交后，`firmware-build`
一路绿灯，产物也正常上传。但把 `xiaozhi.bin` 下下来做字节检索：

```
[0] DS1302      [0] DS3231      [1] elder.rtc     [1] elder.rgb
```

`DS1302` 出现 **0 次** —— 说明 `rtc_ds1302.c` 那 380 行被预处理器整块跳过，
编进去的是 `rtc.c` 里的空桩。**构建却是成功的**，因为桩同样提供
`elder_rtc_init/read/write/present` 四个符号，链接期毫无异常。

**根因**：`firmware/xiaozhi/sdkconfig.defaults` 是**生成文件**。它的 elder
段每次都由 `tools/merge_to_xiaozhi.py` 的 `SDKCONFIG_OVERLAY` 常量
**整块覆盖重写**（`append_overlay()` 先 `strip_overlay()` 再拼模板）。
把 `CONFIG_ELDER_RTC_ENABLE=y` / `DRIVER_DS1302=y` / `RGB=y` 直接写进那个
文件，在 CI 上会被覆盖回模板里的旧值（`RTC=n` / `RGB=n`），于是：

* `#if CONFIG_ELDER_RTC_ENABLE && defined(CONFIG_ELDER_RTC_DRIVER_DS1302)`
  → 假 ⇒ 整个后端消失；
* 配置自检 C1 也不报警，因为它只比 `sdkconfig`（本地生成物），
  而 CI 是从被覆盖后的 defaults 生成的，两者"一致"。

**判据：谁才是真源**。`sdkconfig.defaults` 里 BEGIN..END 之间的内容
**不是真源**，`tools/merge_to_xiaozhi.py` 的 `SDKCONFIG_OVERLAY` 才是。
改配置只改模板，然后跑 `python tools/merge_to_xiaozhi.py` 重新生成。
（同一类问题的既有教训：`main.cc` / `CMakeLists.txt` / `lcd_display.cc`
也都是注入的，`merge` 会重写。）

**为什么不能只靠"看构建绿了"**：这个失败模式的特点是
*不报错、不告警、构建成功、产物完整*，唯一症状是"烧进去功能完全没有"。
和 D53（Vue 方法写在 `methods` 里恒为真）是同一族：**语法合法、语义全错**。

**补的三道门禁**：

1. `prebuild_check.py` **C10** —— 模板拼出来的整段必须与 defaults 里的
   BEGIN..END 段逐字节相同。专拦"手改生成文件"，报错文案直接指向
   `SDKCONFIG_OVERLAY`。（负向验证：把 `CLK_GPIO` 从 4 改回 2 → C10 红。）
2. `prebuild_check.py` **C11** —— 时钟/彩灯引脚红线提前到编译前：
   DS1302 的 CLK/DAT 不得落在 GPIO1/GPIO2（板载音频 codec ES8311/ES7210
   与触摸 FT5x06 共用的 I2C 总线），RST 不得等于 `ELDER_KEY_GPIO`。
   原来只有 `rtc_ds1302.c` 的 `pins_guard()` 在**运行时**拒，那时固件已经
   烧进设备了。这条直接服务"声音不许再破音/卡顿"的硬约束。
3. `tools/check_built_config.py`（新）+ 工作流步骤 —— 编译**后**读
   `build/config/sdkconfig.h`，断言 defaults 里每个 `=y` 的
   `CONFIG_ELDER_*` 在头文件里都是 `1`，且 RTC 的驱动 choice 恰好选中一个。
   补掉 C1 的洞：C1 遇到"符号在 sdkconfig 里根本不存在"是 `continue`
   放行的（符号不存在 ⇒ 配置静默失效 ⇒ 全绿）。
   另外在「产物自检」里再往下扎一层：开关为 1 时，源文件的**独有字符串**
   必须出现在 `.bin` 里（`elder.rtc.ds1302`、`WS2812 ready on GPIO`）。
   注意 `TAG "elder.rgb"` 在 `#if` **外面**，两种形态都有，**不能**当判据
   —— 本次就是靠它一度让人以为彩灯编进去了。

**取舍**：宁可让 CI 多跑两个秒级检查，也不要再出现"绿着但没编进去"。
这类事故的排查成本远高于门禁成本（本次是从产物二进制里搜字符串才定位的）。

## D56：舍弃 DS1302，只保留 WS2812（2026-10-26）

**决定**：用户拍板不接外部时钟芯片，DS1302 硬件舍弃。彩灯（WS2812B，
DIN→GPIO10）**保留启用**——这两件事是分开的，用户只砍了时钟。

**配置落点**（记住：真源是模板，不是生成文件，见 D55）：
* `tools/merge_to_xiaozhi.py` 的 `SDKCONFIG_OVERLAY` →
  `CONFIG_ELDER_RTC_ENABLE=n`、`CONFIG_ELDER_ENABLE_RGB=y`、
  `CONFIG_ELDER_RGB_GPIO=10`；
* `firmware/xiaozhi/sdkconfig.defaults` 由 `python tools/merge_to_xiaozhi.py`
  重新生成（**不要手改**）。

**代码不删，但修对了**：`firmware/components/elder/src/rtc_ds1302.c` 保留
（Kconfig 的 `ELDER_RTC_DRIVER` 仍可选 ds1302），因为删掉会连带丢掉
Kconfig 选项和守卫逻辑，下次想接又要重写。但**不能留着带 bug 的休眠代码**，
所以这次顺手修掉了两处（都是复核时对着 esp-idf-lib 的 `ds1302.c` 查实的）：

1. **突发字节顺序错位（最隐蔽）**。DS1302 的突发顺序是**地址序**：
   秒(0x80)/分(0x82)/时(0x84)/**日-几号(0x86)**/**月(0x88)**/**星期(0x8A)**/年(0x8C)/控制(0x8E)。
   原实现按中文语序写成了 `b[3]=星期 / b[4]=日 / b[5]=月`，把日/月/星期
   整体错位。**回读自检发现不了**：读写用同一套错索引，彼此自洽、BCD 合法、
   范围也合法；只有芯片自己的日历进位会坏 —— 午夜递增的是"星期"寄存器，
   "几号"永远不动 ⇒ 掉电几天后开机，日期差好几天，而 RTC 存在的唯一意义
   就是"掉电后知道过了多久"。
2. **读字节采样点晚了一个边沿**。DS1302 在 SCLK 下降沿把位摆上 DAT，主机
   要在下一个上升沿之前读走（"下降沿输出、上升沿有效"）。原实现先拉高时钟
   再采样，等于读的是**下一位** ⇒ 整体错一位，所有读数通不过 BCD 校验，
   时钟静默降级到 NVS（用户看到的就是"装了芯片还是不准"）。
   参考 esp-idf-lib `read_byte`：先采样后打时钟。

**新增门禁 C12**（`tools/prebuild_check.py`）：静态扫 `rtc_ds1302.c`，断言
写侧 `b[3..6]` 分别是 日/月/星期/年、读侧从 `b[3]`/`b[4]` 取日/月。
放在这里是因为固件没有 C 单元测试框架，而 `prebuild_check` 是本机与 CI
共有的唯一编译前钩子。做过负向验证（把映射改回错位 → C12 红）。

**门禁现状**：C11（时钟/彩灯引脚红线）在 `RTC_ENABLE=n` 时 SKIP；
C10（模板与生成文件一致）与 C12（字节序）常开。

## D57：灯带驱动 9 颗 —— #1 做按键指示灯，#2~#9 做灯效（2026-10-27）

**硬件事实**：WS2812B RGB5050 实际接了 **20 颗级联**，但驱动只发 **9 颗**的数据
（`ELDER_RGB_LEDS 9`）。之前只亮 1 颗，是因为驱动按 1 颗发数据。

**分工**（用户原话：「第1颗灯做按钮指示灯…用2-9颗来做灯效」）：
* `#1` 专做按键指示灯，按下时呼吸；
* `#2~#9` 才是情绪/提醒闪烁/服药未确认/告警这些灯效；
* `#10~#20` 一律不驱动（送 0）。

**为什么只驱动 9 颗而不是 20**：
1. **供电**：20 颗全白约 1.2A，远超扩展口能给的电流；9 颗封顶 40% 亮度约
   60mA，安全。
2. **RMT 容量**：每颗 24 bit，1 颗 = 24 字节 = 192 个 RMT 符号。ESP32-S3 一个
   RMT 组共 8 通道 × 48 字 = 384 符号，`mem_block_symbols=64` 时驱动按 48 符号
   一块 ping-pong 流式发送。9 颗 = 27 字节 = 216 符号，仍在流式范围内
   （1 颗时 192 符号就是靠流式发出去的，已验证）。**再往上加颗数前，先确认
   `rmt_transmit` 不会出现 >50µs 断流** —— 断流会被灯珠当成复位，
   后半段颜色不更新，表现为"前面亮后面不亮"。
3. **夜里不扰眠**：整条 20 颗发光在卧室里是光污染。

**按键指示灯为什么必须独立一颗（适老化）**：
本机按键只做「确认日程完成」，**按下去不一定有结果**（当前没有待确认提醒时
什么都不做）。老人无法从"没声音"区分「按到了但没事可确认」和「根本没按到」。
一颗贴在按键旁的灯做即时反馈，是把这两件事分开的唯一办法 —— 灯亮 = 设备收到了。

取值（改动前先读，都不是随手定的）：
* **暖琥珀 `0xFFB300`**：老年人晶状体黄化、蓝光透射率下降，蓝/冷白在他们眼里
  又暗又糊；暖色辨识度和舒适度都更好。
* **呼吸周期 3 秒**（常规呼吸灯多用 2~2.4 秒）：明暗变化越慢，眩光与焦虑感越低。
* **亮度封顶 ~39%**：夜里起夜按键不刺眼，不晃醒同床的人。
* **松开后余辉 2 秒**：一次短按只有一百多毫秒，严格跟着"按住"时长走等于没反馈。

实现落点：`rgb.c` 的 `write_pixels(fx, btn)` 分两路写；`btn_color()` 的相位
从**按下时刻**算（从系统 tick 算会让每次按下落在随机相位，可能正好按在全暗那一帧）；
`input.c` 在按压起点/松开/判卡住三处调 `elder_rgb_button_indicator()`。

## D58：GPIO11 只做确认，对话开关归板载用户键（2026-10-27）

**决定**（用户拍板）：扩展口按键（GPIO11）**只有「确认日程完成」一个功能**。
对话开关不在这里，归板载用户按键（GPIO0 BOOT）。

**改之前是什么样**：`elder_bridge.cc` 的 `OnKey()` 在"没有待确认提醒"时

## D59：灯效整套重定义 + #1 按键指示灯状态机（2026-10-27）

**决定**（用户逐色逐亮度指定，改数字 = 改产品行为）：

`#2~#9` 随设备状态：

| 场景 | 颜色 | 亮度 | 效果 |
|---|---|---|---|
| 待机 | 天蓝 `#87CEFA` | 30% | 呼吸 |
| 唤醒后收听 | 蓝 `#0000FF` | 100% | 常亮 |
| 网络传输处理中 | 五彩 | 80% | **低速流水**（60°/秒，逐颗偏移 45°） |
| TTS 输出 | 深橙 `#FF8C00` | 100% | 常亮 |

`#1` 按键指示灯（**常态不亮**）：

| 条件 | 表现 |
|---|---|
| 无待确认提醒、未按下 | 熄灭 |
| 有待确认提醒 | 深橙 `#FF8C00` 100% 呼吸 |
| 按住确认键期间 | 浅绿 `#90EE90` → 深绿 `#006400`，时长 = `ELDER_BTN_CONFIRM_HOLD_MS`(3s) |
| 确认完成 | 深蓝绿 `#00CED1` 闪 3 次 |
| 中途松开没确认 | 深粉红 `#FF1493` 闪 5 次 |

**几个必须记住的实现约束**：

1. **亮度要在灯效算完之后统一乘**，不能预先调暗颜色值。呼吸和流水是动态
   算出来的，颜色预乘 0.3 之后再叠动态亮度，峰值只剩约 9% —— 看起来像灯坏了。
   落点：`rgb.c` 的 `scale_color()`，在 `fx_pixel()` 返回前统一施加。
2. **流水 = 逐颗取色，不是整条同步变色**。旧的 `ELDER_FX_RAINBOW` 是整条
   同色，语义不同，保留；新增 `ELDER_FX_FLOW`。相位按 `led_idx-1` 算，
   不能让 `#1` 占掉一格色相。
3. **四个 UI 状态共用一个优先级槽**（`ELDER_RGB_PRIO_EMOTION`），切换即替换。
   各用各的优先级会出现"说完话灯还亮着橙"——旧槽位没被清掉，优先级更高就一直压着。
   同时 ttl 从 8000 改成 **0（常驻）**：待机是长期状态，8 秒后灯灭老人只会以为坏了。
4. **`#1` 的状态机自己记住"本轮是否已出结果"**（`btn_resolved`）。确认完成的
   青色闪之后紧跟的"松开"事件不能再触发粉色闪 —— 不能指望调用方顺序永远正确。
5. **渐变时长与长按判定同源**（`elder_board.h` 的 `ELDER_BTN_CONFIRM_HOLD_MS`）。
   各写一份的话会出现"灯已经走到最深绿、按键却还没算确认"——灯在骗人，比没灯更糟。
6. **闪烁节奏 200ms 亮 / 200ms 灭**：老人要数得清次数。快速闪（80ms 级）
   既数不清，也有光敏性癫痫风险。

**"网络传输处理中"没有对应的设备状态**：realtime 模式全程停在
`kDeviceStateListening`，服务端 VAD 才决定何时开口。所以新增
`elder_on_vad_change(bool)` 由 `application.cc` 的 `on_vad_change` 转发，
配合 `s_spoke_in_turn`（本轮是否已开口）区分：

* 本轮还没开口 + VAD 静音 → 蓝（等你说话）
* 本轮开过口 + VAD 静音 → 五彩流水（在等回复）

混起来的话，老人刚唤醒就看到五彩乱转，会以为设备在自己玩。

**"没有待确认提醒时按下什么都不亮"是刻意的**：本按键只做确认。没有可确认的
东西时给正反馈，等于告诉老人"办成了"而实际什么都没发生 —— 最坏的一类欺骗。

## D60：语音调音量导致设备重启 —— `ESP_ERROR_CHECK` 打在"codec 未打开"上（2026-10-27）

**现象**：老人说「把音量调小一点」，设备**每次必现**重启。

**根因链**（不是玄学，是确定性 abort）：
1. 服务端 `set_volume` → 下发 MCP `self.audio_speaker.set_volume`；
2. 此刻设备处于 listening（输出关闭），ES8311 是 `is_open == false`；
3. `esp_codec_dev_set_out_vol()` → `_verify_codec_setting()` →
   `_verify_codec_ready()` 返回 false → 返回 `ESP_CODEC_DEV_WRONG_STATE`；
4. `BoxAudioCodec::SetOutputVolume()` 用 **`ESP_ERROR_CHECK`** 包着它
   ⇒ `abort()` ⇒ PANIC 重启。

**修复**：`BoxAudioCodec::SetOutputVolume()` 改成检查返回值 + 打 WARN，
不再 abort。值不会丢 —— `AudioCodec::SetOutputVolume()` 照样更新
`output_volume_` 并落 NVS，而 `EnableOutput(true)` 打开 codec 之后会
`esp_codec_dev_set_out_vol(output_dev_, output_volume_)` 补写一次
（本文件原本就有这一行），所以下一次开口说话时就是新音量。

**为什么不在 mcp_server.cc 里先判断"输出是否已打开"再调**：那会把
"codec 生命周期"的知识泄漏到工具层，而且 `EnableOutput(true)` 自己也会
调同一个函数 —— 真正的护栏应该在**唯一那个调用点**上。

**顺带加的诊断**：`set_volume` / `set_brightness` 各打一行日志（含
"输出已打开/未打开"）。以后再看"语音调音量到底有没有走到固件"，不用猜。

## D61：长按确认从"两步"改成"一步"，并把提示音挪出按键任务（2026-10-27）

**决定**：长按满 3 秒 = 确认完成。删除"长按挂起 → 30 秒内再短按一次"的两步流程。

**理由**：D59 的 `#1` 灯效是"按住期间从浅绿渐变到深绿，走满即完成"。
灯已经走到最深绿了却还要再按一下 —— 老人在这一步犹豫一下就超时，
失败率反而比一步高。**灯说什么，行为就得是什么。**

**同批修的隐患**：`OnPlayTone` 原先就地调 `Application::PlaySound()`，
而 `AudioService::PlaySound()` 是**同步**的（当场遍历 OGG 页、调
`codec->EnableOutput(true)` 打开 ES8311、逐帧推 I2S）。它会被两条小栈路径
同步调到：`elder_input` 任务（按键确认 → `OnReminder(DONE)` → 提示音）
和 `esp_event` 默认任务。长按确认的偶发重启就发生在这条链上。
现在统一 `Application::Schedule()` 到主事件循环（栈 8192），调用方立刻返回。

`elder_input` 栈同时从 4096 提到 **8192**，并在 `emit()` 后打一行
**栈余量**日志 —— 下次再报"按键重启"，第一眼看那行就知道是不是栈。

## D62：#10~#20 灯珠低亮度白色常亮 —— 必须显式写满整条灯带（2026-10-27）

**现象**（用户原话）：「现在是 2-20 灯珠全亮，10-20 是低亮度白色，
1-9 受控按照程序控制进行亮灭和颜色转换。」

**根因**：WS2812B 是级联的，每颗吃掉前 24 bit、把余下的转发给下一颗。
只发 9 颗（27 字节）时，**#10~#20 一个比特都收不到**，它们的 PWM 锁存器
就停在开机上电时的随机态 —— 表现正是"低亮度白色常亮"。这不是驱动写错，
而是"没被寻址过的灯珠不会自己熄灭"。

**修复**：`elder_board.h` 新增 `ELDER_RGB_CHAIN = 20`（真实颗数），
与 `ELDER_RGB_LEDS = 9`（受控颗数）分开。`render_frame()` 每帧写满 20 颗，
`#10~#20` 显式填 0，发送 60 字节 = 480 个 RMT 符号。

**为什么不是"把 ELDER_RGB_LEDS 改成 20"**：那个宏决定灯效铺几颗、流水灯的
色相怎么分布，改了等于把 8 颗灯效摊到 19 颗上。两个语义必须分开。

**顺带把 RMT 内存一次申请到整组 384 符号**：480 符号在 48 符号一块的
配置下要补块 9 次，每次必须在 4.8µs 内补上（10MHz），一次被高优先级中断
拖过 50µs 就会被灯珠当成复位。申请整组后只剩 1 次补块。申请失败自动退回
64 符号分块，功能不受影响。

## D63：结果闪烁必须用"渲染时钟"，不能用墙上时钟（2026-10-27）

**现象**：「长按 3 秒之后只显示一次深蓝绿色」，没有 3 次。

**根因**（串口抓包实锤）：确认会立刻把回执入队 → `elder_sync` 开始 HTTPS
上传，TLS 握手实测 **1.6 秒**（`251937 回执入队` → `253527 Certificate
validated`）；`rgb_task` 优先级只有 5，这 1.6 秒里**一帧都没跑**。
而闪烁窗口按墙上时钟只有 1.2 秒 —— CPU 回来时窗口早就过期了。

**修复**：闪烁改用**渲染时钟** `g.btn_anim_ms`：每帧把真实间隔累加进去，
**单步封顶 50ms**。被饿死时动画就地暂停，CPU 回来接着放完，3 次就是 3 次。
亮/灭各 250ms（原来 200ms），一次结果共 1.5s 的动画时间。

**渐变刻意仍然用墙上时钟**：它是"按住 3 秒"的进度条，必须和 `input.c` 判

—— 灯在骗人，比不亮更糟。

## D64：`Settings` 不再因 NVS 打不开而 abort（2026-10-27）

**现象**：「语音要求声音大一点，造成重启。」

**现场**：
```
I (324827) MCP: set_volume -> 90（输出已打开，立即生效）
I (324827) AudioCodec: Set output volume to 90
ESP_ERROR_CHECK failed: esp_err_t 0x1107 (ESP_ERR_NVS_INVALID_HANDLE)
file: "./main/settings.cc" line 63  func: Settings::SetInt
abort() was called at PC 0x40384527 on core 1
```

**根因**：`Settings` 构造函数**丢弃了 `nvs_open` 的返回值**。打不开时句柄停在
0，`SetInt` 里的 `ESP_ERROR_CHECK(nvs_set_i32(0, ...))` 必然拿到
`ESP_ERR_NVS_INVALID_HANDLE` → abort。本工程 `nvs` 分区只有 **0x4000（16KB，
3 个可用页）**，而 elder 的提醒表（~1KB 一条 blob）每次状态变化都整块重写，
最容易把页吃干净。

**修复（两层）**：
1. `Settings` 检查 `nvs_open` / `nvs_commit` / `nvs_set_*` 的返回值，失败只打
   日志、退化成"本次运行不持久化"，**绝不 abort**。为保存一个音量值而重启，
   对一个提醒吃药的设备代价完全不成比例（重启期间听不见提醒、回执可能丢）。
2. `BootDiag` 每次开机打印 NVS 已用/可用条数 —— 判断分区是否吃满的**唯一
   直接证据**。可用条数长期 <20 就该扩容 nvs 分区（那需要改分区表，
   属于整机重刷，单独评估）。

## D66：加 gamma 2.2 表 + 灯效四态重定义（2026-10-28）

**用户需求**（原话）：「那就添加 gamma 表吧。顺便把待机改为五彩幻彩灯效，
进入待机状态至待机 1 分钟为 60% 亮度，超过 1 分钟为 30% 亮度。唤醒后收听为
#00BFFF（深天蓝），TTS 输出为深橙 #FF8C00 色 70% 亮度。网络传输处理中为从
2-9 轮流亮起的五彩灯效，20% 亮度。」

### 一、gamma 表：`scale_color()` 原来是纯线性乘法

用户上一轮问「GPIO10 的 WS2812B 是不是控制不了亮度」。真实原因**不在驱动**，
在三层错位的叠加：

1. **协议层**：WS2812B 每通道 8 位、256 级，亮度当然可控。
2. **物理层**：内置恒流源，占空比太窄（值 1~8）时实际表现是闪烁 + 三色失衡。
   所以表里 0~14 一律映射到 0/1，**感知亮度低于约 8% 就看不见**，这是硬件下限。
3. **感知层（真正的锅）**：人眼亮度感知近似 gamma 2.2，而原来的
   `scale_color()` 是 `通道 × level / 255` 的**线性乘法**。
   写 30% 出来人眼看着约 58%；写 55% 看着约 76%。"调了没反应"是错觉 ——
   调了，但暗部被压得太厉害、亮部又被拉得太高。

**做法**：`GAMMA_LUT[256]`（`[round(255*(i/255.0)**2.2) for i in range(256)]`，
256 字节常量放 flash）+ `level_to_linear()`。此后 `elder_rgb_request_ex()` 的
`level` 参数语义变成**感知亮度**。

**关键坑：gamma 只能作用在"亮度系数"上，不能逐通道做。**
逐通道 gamma 会让三个通道在暗部的非线性不一致，颜色会偏（暗绿变墨绿、
暗蓝发紫）。正确顺序是「先算整体该暗多少 → 再等比乘到 RGB」，色相不变。

**第二个坑：灯效自身的调制不能再过一遍 gamma。**
呼吸相位、轮流亮起的通断本来就是线性波形，再过 gamma 会让暗部占比过大，
呼吸看起来像"眨眼"。所以拆成两个函数：`scale_color()`（过 gamma，给基准
亮度用）与 `dim_color()`（纯线性，给灯效调制用）。`fx_pixel()` 末尾合成：
`dim_color(c, level_to_linear(s->level) * mod / 255)`。
历史上这里连着调了两次 `scale_color()`，加表之后会变成 gamma 套 gamma、
暗部直接消失。

实测映射：感知 20% ⇒ 线性 2.7%（7/255）、30% ⇒ 7.1%（18）、55% ⇒ 26.7%（68）、
60% ⇒ 32.5%（83）、70% ⇒ 45.5%（116）。

### 二、四态重定义

| 状态 | 灯效 | 亮度 |
|---|---|---|
| 待机（0~1 分钟） | `ELDER_FX_RAINBOW` 五彩幻彩，整条同步，约 20 秒一圈 | 60% |
| 待机（超过 1 分钟） | 同上，自动降亮 | 30% |
| 唤醒后收听 | `ELDER_FX_SOLID` `#00BFFF` 深天蓝 | 55% |
| 网络传输处理中 | `ELDER_FX_CHASE` #2~#9 轮流亮起（每颗一色） | 20% |
| TTS 输出 | `ELDER_FX_SOLID` `#FF8C00` 深橙 | 70% |

**新增 `ELDER_FX_CHASE`**：同一时刻**只有一颗亮**，亮点每 150ms 前进一格，
8 颗一轮 1.2 秒；色相按灯位固定（#2 红 → #9 紫，每颗 45°），于是"轮流亮起"
的同时颜色也在依次变化。与既有的 `ELDER_FX_FLOW` 区别：FLOW 是"8 颗都亮、
彩虹沿灯带流动"，CHASE 是"只有一颗亮、亮点在跑"。用户要的是后者。

**待机 1 分钟降亮放在 `rgb_task` 里做，不让上层 60 秒后再调一次**：
待机期间**没有任何上层任务在跑**（会话已结束、唤醒词还没来），没人能来改。
`g.idle_dim` + `g.idle_since_ms` 由 `elder_rgb_set_ui_state(IDLE)` 从**非待机
状态**进入时重置 —— 于是"刚说完话放下设备"时是 60%（老人能确认它回到待机
了），1 分钟后悄悄降到 30%（夜里不刺眼）。降亮的判据里带
`s.fx == ELDER_FX_RAINBOW`，别人用 RAINBOW 做别的灯效时不会被误降。

**幻彩速度 55ms/度 ≈ 20 秒一圈**：待机是长期状态，颜色变化太快在余光里会
一直"动"，夜里尤其让人睡不踏实。

## D67：待机改 Twinkle、传输中改流星 + 修掉 hsv2rgb 的色相分区 bug（2026-10-28）

**用户需求**（原话）：「待机幻彩换成 Twinkle，流星替掉现在的 CHASE。星光用
随机彩色。提交 GitHub 进行固件编译，编译完成后刷入硬件。」

### 一、`ELDER_FX_TWINKLE`（待机）

每颗灯一个**独立的伪随机节拍**：亮 220ms 后快速衰减，周期按灯位散列在
1.2~3.0 秒之间。8 颗灯合计点亮占比 10.25%，平均同时只亮 0.8 颗。

两个关键约束，都是"看起来像不像星光"的分水岭：

1. **绝对不能用 `rand()`**。`rgb_task` 每 30ms 调一次 `fx_pixel()`，
   `rand()` 会让同一颗灯的相位每帧跳变 —— 出来的不是星光，是雪花噪点。
   必须用 `led_idx × 2654435761`（Knuth 乘法常数）做纯函数散列，
   同一 idx 每帧结果完全一致，8 颗灯之间又互相错开。
2. **颜色必须"每闪一次换一个"，不能每帧算一次**。用"第几个周期"
   （`t / period`）参与散列 ⇒ 同一周期内颜色恒定、下一轮才换色。
   每帧算的话，220ms 的闪亮会被切成 7 段不同颜色，看着像坏点。

为什么比整条幻彩更适合待机：幻彩是**整条**一直在变色，余光里"一直在动"，
夜里躺着看会一直吸引注意力；星光绝大部分时间是黑的，只在某处亮一下 ——
"安静但不死"。

### 二、`ELDER_FX_METEOR`（网络传输中）

一个亮头 + 拖尾沿灯带跑过去，头部最亮、尾部线性衰减。拖尾 4 格（含头部），
每 90ms 前进一格，一轮 8 格 + 4 格出尾 + **2 格空档** = 14 格 ≈ 1.26 秒。

**那 2 格空档是必需的**：不留空档的话尾巴还没走完、头就从起点冒出来，
变成"头尾相接的循环"，看上去像一条虫在爬，不是流星。

**单颗流星必须是一个颜色**（流星不是彩虹），但连续几颗换色
（按"第几颗流星"散列）⇒ 整体仍是用户要的"五彩"。实测 6 颗的色相：
0°红 → 137°绿 → 274°紫 → 51°黄 → 188°青 → 325°洋红。

### 三、顺带修掉的真 bug：`hsv2rgb()` 的色相分区

原来写的是 `region = h / 43` + `rem = (h % 43) * 6` —— 那是 **hue 取 0~255**
的实现（255/6 ≈ 43）。而本文件所有调用方传的都是 `% 360` 的**角度**。后果：

| 传入 | 应该是 | 实际输出 |
|---|---|---|
| 180° | 青色 | `rgb(48,0,255)` 蓝紫 |
| 240° | 蓝色 | `rgb(255,0,105)` 粉红 |
| 300° | 洋红 | `rgb(255,0,3)` 纯红 |

258°~359° 全部落进 `default` 分支、拿 region 5 的公式配错的相位。
也就是说**整条灯带从来没有出过蓝色和青色**，"五彩"其实只有红橙黄绿。

修正：`region = h / 60`（6 个 60° 扇区）、`rem = (h % 60) * 255 / 60`。
修正后 0/60/120/180/240/300 → 红/黄/绿/青/蓝/洋红，全部正确。

这个 bug 在只有"幻彩"的时候不容易被认出来（反正一直在变），但 Twinkle 用
**随机彩色**会让它立刻暴露：2/3 的色相都会跑偏成暖色。

### 四、验证方法（没有字符串可 grep 的功能）

Twinkle / Meteor / hsv2rgb 都不往二进制里写任何字符串，`grep -a` 那套
完全失效。这次用 **Python 复算波形 + 源码常量表字节匹配**：
把 `fx_pixel()` 的公式在 Python 里逐行重算，输出每个时刻每颗灯的峰值通道值，
再和设计意图对比（点亮占比、空档步数、色相序列）。

## D68：半置信复核窗口过期 = 本地跳过、云端一个字不发（2026-10-28）

### 一、需求原话

> 「半置信后不按按钮就跳过该次事件，仅在用户网页端和用户手机APP上做标记。」

D65 定下的两档置信度里，语音确认只是**半置信**（`ELDER_RMD_HALF_CONFIRMED`）：
设备会提示老人长按按钮复核，按了才是全置信。但当时没定义"**一直不按**
会怎样"——于是设备就无限期橙色呼吸 + 每 10 分钟闪一次，夜里一直折腾他。

### 二、结论：新增独立状态 `ELDER_RMD_HALF_EXPIRED`

```
PENDING → CONFIRM_WIN → ESCALATED
      ↘ HALF_CONFIRMED（语音） → DONE（按了按钮）
                              ↘ HALF_EXPIRED（窗口过了没按 = 跳过本次）
```

本地语义和 `SKIPPED` **完全一样**（不闪灯、不算待办、不算完成），
区别只有一个：**不上报**。就为这一个区别，它必须是独立取值。

### 三、为什么不能复用 `ELDER_RMD_SKIPPED`（这是本决策的核心）

`SKIPPED` 经 `elder_sync_on_reminder_state()` 会上报
`ELDER_EV_SKIPPED`，而那条事件的 `note` 在 sync.c 里**写死成 `"stale"`**
（语义是"设备离线错过了"）。如果 HALF 超时转 SKIPPED，会同时错两件事：

1. 服务端刚在 HALF 那一刻收到的 **`CONFIRMED` + `method=VOICE`** 被**覆盖**
   成「跳过」—— 子女端从此看不出老人说过"我吃过了"；
2. 理由写成"设备离线错过"，而事实是"设备在线、老人没按按钮"。

医疗场景里"老人说了什么"是不能丢的信息。所以 `sync.c` 给
`ELDER_RMD_HALF_EXPIRED` 写了一个**显式空 case**（不是靠 `default` 兜）：
写出来是为了让"这里**有意**不上报"成为代码里的显式决定，将来有人给
`default` 加日志或兜底上报时不会被静默带偏。

### 四、为什么窗口是 10 分钟

- 老人可能正在倒水、找药，手也不利索，给 1~2 分钟等于逼他手忙脚乱；
- 正好与 nag 的「每 10 分钟闪 10 秒」对齐 —— 窗口末尾那次闪灯就是最后一次
  提醒，闪完不按就安静，不需要额外定时器。

### 五、硬约束：跳过 ≠ 完成

`done_today` **绝不置位**。语音是半置信，万一误识别成"吃过了"还置完成，
等于替老人谎报服药。这是 D65「两档置信度」存在的全部意义，不能在这里破。

### 六、nag 是全局单例，停之前必须查

`rgb.c` 里只有一个 `g.nag_active`。转 `SKIPPED` / `HALF_EXPIRED` 时必须：

```c
if (!has_pending_confirm()) elder_rgb_reminder_nag_stop();
```

无条件停会把「B 还在响」的闪灯一起关掉。此刻 `g.state[idx]` 已经是新状态，
`has_pending_confirm()` 不会把自己算进去，判断正好。

### 七、三个"待确认"判据必须不含新状态

`has_pending_confirm()` / `has_pending_medicine()` /
`elder_reminder_first_ringing()` 都只列
`PENDING / CONFIRM_WIN / ESCALATED / HALF_CONFIRMED`。
漏加一个就会变成"还在提示按按钮、按下去说没有待确认"；
多加一个就会变成"已经跳过了还在催"。

### 八、`half_since_us[]` 只放 RAM，不落盘

理由：状态机 `state[]` 本身就是 RAM 的，重启后全回 IDLE；而 `fired_today`
是落盘的，所以重启后这条提醒不会重响、也就不会再有复核窗口。
落盘一个和 `state[]` 生命周期不一致的时刻，只会在跨重启时给出错误的窗口起点。

基准取值 `half_since_us ?: pending_since_us`（响铃时刻，更早）
⇒ 只会让窗口更早到期，是安全的方向。

### 九、网页/APP 上到底显示什么

当前实现：HALF 那一刻上报 `CONFIRMED + method=VOICE` ⇒ 网页/APP 显示
**「语音确认」**；超时跳过**不上报** ⇒ 那个标记原样保留。
这正好对应用户说的"仅在网页端和手机APP上做标记"——标记就是"语音确认"。

⚠️ 如果用户想要的是**另加一个「未复核」标记**（让子女能区分"语音说了并按了
按钮"和"语音说了但没按"），那需要动服务端：`ConfirmMethod` 追加一个值
（不许重编号），由设备在 HALF_EXPIRED 时**上报一条新事件**而不是不发。
这一条待用户确认，固件侧不做假设。

### 十、验证

- 宿主测试 **T13** 改：语音确认后 5 分钟（窗口内）**不得**提前跳过、
  不得升级 ESCALATED，且仍选得中（能按键复核）；
- 新增 **T13b**（8 条断言）：落 `HALF_EXPIRED`、不得 ESCALATED、
  **必须是 HALF_EXPIRED 而不是 SKIPPED**、`done_today` 绝不置位、
  `pending_today` 清掉、`nag_stop` 被调用、`first_ringing == -1`、
  确认方式仍记 VOICE；

  `undefined reference` 0 个）—— 新增的 `elder_rgb_reminder_nag_stop()`
  桩没漏。这是本机唯一能做的验证（无宿主 gcc），最终以 CI 的
  `elder-host-test` job 为准。
