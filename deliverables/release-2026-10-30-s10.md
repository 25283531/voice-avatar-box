## ② ELDER_REMINDER_MAX 静默截断

**问题**：`firmware/components/elder/src/sync.c` 的 `parse_reminders()` 里，
内层和外层各有一个 `if (n >= ELDER_REMINDER_MAX) break;`。服务端把每条规则的
`times_of_day` 展开后超过 16 条的部分被**静默丢弃** —— 用户在 APP 上配了第 17 条提醒，
设备上永远不响，串口也没有任何一行日志。这类"配置成功但不生效"的故障，事后只能靠猜。

**做法**（只碰计数逻辑，**未触任何音频通路**）：
- 新增 `int wanted`，在内层循环里**先记账再判容量**（`wanted++` 后
  `if (n >= ELDER_REMINDER_MAX) continue;`）。先记账是为了让"本该有多少条"与
  "实际装了几条"是同一个口径，日志里的差额才是真实丢弃数（把无效时刻也算进去
  会让告警虚高，反而没人信）。
- 外层去掉提前 `break`，数组满了也继续走完剩余规则 —— 否则 `wanted` 数不全，
  告警就报不出"到底丢了几条"。剩余规则只做一次 `sscanf` 计数，代价可忽略。
- 末尾一条 `ESP_LOGW`：服务端下发 X 条 / 本机装下 Y 条 / **丢弃 Z 条** / 上限值。

数组定长是硬约束（`elder_reminder.h` 的 static assert），所以**照旧丢弃**，
只是不再沉默。

**取证**：
- CI `firmware-build` 编译通过（固件一律 CI 编，本机不编）。
- 二进制取证：新固件 `xiaozhi.bin` 含 `提醒超过本机上限`（命中 1 次），
  上一版 `fw-a407119` 为 0 次。`SHA256SUMS` 7/7 OK。
- 真机：`tools/flash_app.py` 写入 `0x20000`，`Hash of data verified`；
  设备正常启动，`RTC_SW_SYS_RST` 0 次，WiFi 连上、OTA 检查通过、
  MCP 工具注册、唤醒词加载、`设备就绪`，堆空闲 7.7MB。

**真机验证（生产数据上做的，已还原）**：

在服务端给这台设备临时插入一条带 **17 个时刻**的提醒（`schedule_kind=ONCE` +
`once_date=今天`，17 个时刻全部是今天已过去的 00:10~08:10 ⇒ `expand_occurrences`
在未来 36 小时排出 **0 个实例**，所以它不会真的响）。设备原有 1 条提醒（08:00），
合计 18 个时刻。复位后串口打出：

```
W (12013) elder.sync: 提醒超过本机上限：服务端下发 18 条时刻，本机只装下 16 条，
        **丢弃 2 条**（ELDER_REMINDER_MAX=16）。被丢弃的提醒在这台设备上不会响，
        请在 APP 里减少提醒条数或合并时刻
I (12023) elder.reminder: 提醒表已合并：后端 16 条 + 本地 0 条 = 16 条
I (12073) elder.sync: 同步完成，16 条提醒，300 秒后再次同步
```

数字对得上：`wanted=18`、装下 16、丢弃 2。**改之前这条日志是不存在的**（静默丢弃）。

还原：删掉测试提醒（物理删除，不进软删除审计）+ 清掉它带出来的 15 条
`reminder_events`（设备对"已过期"实例回执时按 `(reminder_id, due_at)` 补建的），
再复位设备。终态与基线逐项一致：`users=2 / devices=1 / reminders=1 /
reminder_events=39 / reminder_audits=2`，全库无"临时"字样残留；
复位后 `提醒表已合并：后端 1 条 + 本地 0 条 = 1 条`，告警不再出现。
服务器上的临时脚本也已删除。

## ③ web 前端"打不开" / 页面内 "Failed to fetch"

三条**互相独立**的成因，都已定位并修复。

### 成因 1：`fetch` 默认永不超时 + 把英文原文抛给用户

两个页面的 `api()` 都没有 `AbortController`，错误直接 `this.err = e.message`。
连接被静默丢弃时请求永远挂着，页面停在加载态，服务端一条日志都没有
（请求根本没到）。用户看到的就是"打不开"或页面里一行 `Failed to fetch`。

修法（`static/user.html`、`static/index.html` 各一套）：
- 20s 硬超时（`AbortController` + `setTimeout`）；
- **只对幂等方法重试一次** —— POST 有真实副作用，重试等于"点一次建两条"；
- `netErrText()` 把 `AbortError` / `Failed to fetch` 翻译成人话；
- 登录那处裸 `fetch` 单独补超时（不能走 `api()`，401 语义不同）。

门禁：`tools/smoke_frontend_hygiene.py` 新增 L5a–L5e 五条。L5e 只在**有登录入口的
文件**里断言（管理端没有登录表单，硬要求会得到一条永远红的假断言）。
**注意传 `script` 不是 `tpl`** —— `tpl` 是剥掉 `<script>` 之后的模板，`api()` 不在里面，
传错会让断言永远"找不到 api()"。负向验证：删掉 `AbortController` → L5a 精确变红。

### 成因 2：CORS `allow_origins=["*"]` + `allow_credentials=True` 不合法

本服务全走 `Authorization: Bearer`，服务端**一个 Cookie 都不发**（全仓 grep 不到
`set_cookie`），凭据模式根本用不上。而两者同时成立时，Starlette 在**简单请求**上会同时
发 `ACAO:*` 和 `ACAC:true` —— 被浏览器规范明确禁止，调用方只要用凭据模式，响应被
**整体丢弃**，控制台连 4xx 都看不到。改 `allow_credentials=False`。

验证：`Access-Control-Allow-Origin: *`、**无** `Access-Control-Allow-Credentials`；
预检 `OPTIONS` 返回 200 且方法/头齐全。

### 成因 3：Caddy 通告 h3 但 443/udp 未发布 + 响应完全不压缩

- `Alt-Svc: h3=":443"; ma=2592000` 让浏览器缓存 QUIC 通告 30 天，但 compose 只映射
  `443/tcp`，公网 UDP 443 实测 0.02s 回 ICMP 不可达。浏览器每次先试 QUIC、失败、
  再回落 TCP。→ `servers { protocols h1 h2 }`。
- 首页 HTML 106KB、Vue 运行库 158KB 原先**原样下发**。→ `encode gzip zstd`
  （`application/octet-stream` 的固件 OTA 不在默认匹配里，不会被压）。

**服务端自测（`build-out/verify_caddy.py`，9 项）改前 6/9 → 改后 9/9**：
三种 SNI（无 SNI / SNI=IP / SNI=域名）握手成功、状态 200、响应是 HTML、
无 `Alt-Svc`、`content-encoding=gzip`（传输 34552B / 解压后 109184B = 31.6%）、
20 次全部成功。

## 固件烧录事故与恢复（本轮最大教训）

**事故**：烧录中途 `Write timeout`，app 分区被写成半截，设备进入每 ~28ms 一次
`RTC_SW_SYS_RST` 的自复位循环。**刷机前它是好的** —— 是我把它弄坏了。

**排障过程中的三个错误判断**（都值得记住）：

1. **以为是复位时序不对，其实不是根因**。花了很久在 DTR/RTS 组合上打转，
   而真正的根因是 **CH340K 这座桥在连续写数据时会卡死**。
2. **`DTR=1 且 RTS=1` 是"两条线都不动作"态**，我一开始拿它复位，芯片压根没复位。
3. **两线必须同一瞬间切换（gap=0）**：`DTR=0,RTS=1` 保持后同时写 `DTR=1,RTS=0`
   ⇒ `boot:0x3 (DOWNLOAD(USB/UART0))`、输出仅 143B；中间插 20ms ⇒ 退回
   `boot:0xb (SPI_FAST_FLASH_BOOT)` 继续崩。

**真正的解法**：这块板子同时挂着两个串口，**COM5 = 芯片原生 USB-Serial-JTAG
（`303A:1001`，序列号就是芯片 MAC）**。同一条 esptool 命令换到 COM5 一次就过：
`Wrote 2995488 bytes (compressed 1669457) at 0x00020000 in 25.1 seconds`，
`Hash of data verified.`。`tools/boot_capture.py` 一直用的就是 COM5 ——
是 `build-out/flash_app.sh` 走 COM11 把大家带偏了。

**沉淀**：新增 `tools/flash_app.py`（默认 COM5/460800，只写 app@0x20000 保留 NVS，
`--full` 写整片；端口不存在时列出可用串口并标明哪个口适合烧录）。
两条路径都实测过。

**收尾状态**：设备正常启动、无复位循环、堆空闲 7.7MB。
注意：CH340 的 DTR 留在低电平（IO0 低）时，芯片一复位就进下载模式、串口全静默 ——
"刷完没日志"先查这个。
